<objective>
**As a** lifter who trains a program I designed myself, **I want to** create a named program on my
phone and have it exist on my other device too, **so that** the program I actually train is the one
the app knows about, wherever I open it.

This is the phase's tracer slice: the thinnest path that touches every layer Phase 4 will modify —
shared contract vocabulary, the server-side sync apply path, local SQLite, and the Programs tab —
wired end to end and verified against a real Postgres row.

Purpose: `routine`, `routine_day` and `routine_exercise` have Drizzle schemas and pull-side
PowerSync rules but **no server-side push apply path**. They sit in `PUSH_DEFERRED_TABLES` and
`sync.service.ts`'s `TABLE_MAP` has no entry for them. PowerSync's push reports success once the
server acknowledges receipt of the op, not once a row is written, so today every program the builder
would write disappears silently between the phone and Postgres, with no client-visible error. That
gap gates all four of this phase's success criteria. This plan closes it for the aggregate root and,
in doing so, proves the architecture the remaining ten plans expand into: `applyBatch` has to
support a **second aggregate-root family** beside `workout_session`, and it currently hardcodes
`workoutSession` in four places.

No REST endpoint writes a routine: `SyncModule`/PowerSync is the sole ingress for per-user,
offline-mutable data (D-04), and this plan fills in the Programs tab without restructuring
navigation or introducing a `Platform.OS` branch (D-07).

Output: a routine you can create offline, see on the Programs tab, and find in Postgres.
</objective>
