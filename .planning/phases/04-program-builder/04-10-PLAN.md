<objective>
**As a** lifter opening the app before a session, **I want to** see the next workout in my active
program with its target muscles and its rep and RIR targets for the week I am actually in, **so that**
I know what I am doing today without opening the builder.

Purpose: PROG-09 is the last requirement that turns the authored program into something the app tells
you. D-20 fixes the mechanism — position is **derived** from logged history at read time, never
stored — because a stored cursor is one more mutable synced row for two offline devices to disagree
about, while a derived position cannot conflict and self-heals after a skipped or duplicated session.

The research flagged two cases D-20 does not answer and CONTEXT.md does not specify: what happens
when the most recently logged day has since been deleted from the routine, and what happens when a
time-off cycle sits between two training cycles. Both are resolved here, explicitly, with tests.

Upcoming workouts live on Home rather than on the Programs tab (D-27): Programs stays about
authoring and managing, and `apps/mobile/app/(tabs)/index.tsx` stops being a placeholder here.

Output: a Home tab that leads with the next workout, and a pure resolver whose every edge is asserted.
</objective>

    `apps/mobile/lib/programs/__tests__/next-up.test.ts` — pure, no database, no rendering. Every case
    passes days, cycles and history as plain arrays.

    Countable history:
    - `countableHistory([], days)` is `[]`.
    - A session whose `status` is not `'completed'` is excluded.
    - A session whose `routineDayId` is null is excluded — a one-off workout is not part of the rotation.
    - A session whose `routineDayId` names a day **not** in the current day list is excluded. This is the deleted-day rule, and it is what makes deleting a day rewind the rotation instead of leaving the resolver with nothing to find "the day after".
    - History is returned ordered by `localDate` then `startedAt` then `id`, so two sessions on the same day have a total, stable order.

    Cycle span:
    - `cycleSpan({kind:'training'}, 3)` is `3`; `cycleSpan({kind:'deload'}, 3)` is `3` — a deload is trained, so it consumes a full rotation of days.
    - `cycleSpan({kind:'time_off'}, 3)` is `0` — nothing is logged during time off, so it consumes no rotation positions and its length is measured in days instead.

    Empty and degenerate inputs:
    - `resolveNextUp({ routine: null, ... })` is `{ kind: 'no-active-program' }`.
    - A routine with zero days is `{ kind: 'no-days' }`.
    - A routine with days but zero cycles and no history is `{ kind: 'workout', cycle: null, day: days[0] }` — with no cycles the rotation simply repeats and every target resolves to its base.
    - The same routine after `dayCount` completed sessions is `{ kind: 'workout', cycle: null, day: days[0] }` again — a cycle-less program loops.
    - A routine with exactly one cycle and no history yields that cycle and `days[0]`.
    - The next day after `n` countable sessions in a cycle-less program is `days[n % dayCount]`.

    Cycle walking:
    - Days `[A,B,C]`, cycles `[W1 training, W2 training]`, 0 sessions -> `W1`, day `A`.
    - 2 sessions -> `W1`, day `C`.
    - 3 sessions -> `W2`, day `A` — the rotation rolls into the next cycle exactly at the boundary, and 2 and 3 sessions are both asserted so the off-by-one is pinned.
    - 5 sessions -> `W2`, day `C`.
    - 6 sessions -> `{ kind: 'program-complete', lastCycle: W2 }` — the block does not silently loop back to cycle one.
    - Days `[A,B,C]`, cycles `[W1 training, Deload deload, W2 training]`, 3 sessions -> the deload cycle, day `A`, with `kind: 'workout'` — a deload is a workout.
    - The same at 6 sessions -> `W2`, day `A`.
    - Deload placed **first** (`[Deload, W1, W2]`), 0 sessions -> the deload, day `A`; deload placed **last** (`[W1, W2, Deload]`), 6 sessions -> the deload, day `A`. Both PROG-05 placements resolve, and neither needs a column of its own.

    Time off:
    - Days `[A,B,C]`, cycles `[W1 training, Off time_off durationDays 7, W2 training]`, 3 sessions, last session `localDate` 3 days ago -> `{ kind: 'time-off', cycle: Off, daysRemaining: 4 }`.
    - The same with the last session 7 days ago -> the walk continues past the time-off cycle to `W2`, day `A`.
    - The same with the last session 8 days ago -> also `W2`, day `A` — being over is over; `daysRemaining` never goes negative.
    - Exactly 6 days ago -> still time off with `daysRemaining: 1`; exactly 7 days ago -> `W2`. The boundary and one step either side are all asserted.
    - A time-off cycle reached with **no** completed session in history measures from the routine's own start reference passed in as `today`, yielding the full duration remaining rather than throwing.
    - A time-off cycle with a null `durationDays` (which the builder refuses to create, but which a sync from another client could deliver) is skipped rather than blocking the walk forever, and the skip is reported so the caller can surface it.
    - Two consecutive time-off cycles resolve to the first one while it is active and to the second one after the first elapses.

    Determinism:
    - Cycles sharing an `orderIndex` are walked in ascending `id` order, and days sharing an `orderIndex` are visited in ascending `id` order, so the same inputs always produce the same answer.
  </behavior>

    import, no `Date.now()`. Every input is an argument, including `today` as an ISO `YYYY-MM-DD`

    Export the result union:
    - `{ kind: 'no-active-program' }`
    - `{ kind: 'no-days' }`
    - `{ kind: 'workout', cycle: ProgramCycle | null, day: ProgramDay }`
    - `{ kind: 'time-off', cycle: ProgramCycle, daysRemaining: number }`
    - `{ kind: 'program-complete', lastCycle: ProgramCycle | null }`

    Export two helpers so the two subtle rules are separately assertable:
    - `countableHistory(sessions, days)` — filter to `status === 'completed'`, non-null
      `routineDayId`, and a `routineDayId` present in `days`; sort by `localDate`, then `startedAt`,
      then `id`. **The day-membership filter is the deleted-day answer** (RESEARCH Pitfall 5a): a
      session logged against a day that no longer exists stops counting, so the rotation rewinds by
      one position and the resolver never has to find "the day after" a day that is gone. Record that
      in the SUMMARY as the resolution of the flagged case, alongside the alternative that was
      rejected — keeping the session countable and falling back to the first day of the current
      cycle, which loses the correspondence between session count and position and makes the answer
      depend on which day was deleted.
    - `cycleSpan(cycle, dayCount)` — `dayCount` for `training` and `deload`, `0` for `time_off`.
      **A deload is trained** (RESEARCH assumption A5, adopted here): a deload week is a lighter week
      you still perform, which is why D-12 makes it a cycle kind rather than a gap. Record it as an
      adopted assumption in the SUMMARY so a later phase that disagrees knows where to look.

    `resolveNextUp({ routine, days, cycles, history, today })` walks the cycle list in
    `sortByOrderThenId` order, carrying `remaining = countableHistory(...).length` and a `clockDate`
    equal to the last countable session's `localDate` (or `today` when there is none):

    - For a `training` or `deload` cycle: when `remaining >= dayCount`, subtract `dayCount` and
      continue; otherwise return `{ kind: 'workout', cycle, day: days[remaining] }`. `remaining` is
      strictly below `dayCount` at that point, so the index is always in range — that is the
      structural reason this function cannot throw on a day list of any size.
    - For a `time_off` cycle reached with `remaining === 0`: with a null `durationDays`, skip it and
      continue; otherwise compute `elapsed` as whole days between `clockDate` and `today` and return
      `{ kind: 'time-off', cycle, daysRemaining: durationDays - elapsed }` when `elapsed < durationDays`,
      and otherwise continue the walk. `daysRemaining` is clamped at a minimum of 0 and never
      negative. A `time_off` cycle reached with `remaining > 0` is impossible (its span is zero, so
      the walk only reaches it once the preceding cycles are consumed) — assert that invariant with a
      defensive branch that continues rather than throwing.
    - When the walk runs out of cycles: `{ kind: 'program-complete', lastCycle }`. **The program does
      not loop.** A finished block is a fact the user should be told, and silently restarting it would
      make "which cycle am I in" answer differently for the same history depending on how long ago the
      block ended.
    - With zero cycles: the rotation repeats indefinitely — return
      `{ kind: 'workout', cycle: null, day: days[remaining % dayCount] }`. This is what makes a
      program with no cycles a valid program.

    Compute day differences from the `YYYY-MM-DD` local-date strings, not from timestamps — the
    device already stamps `local_date` at session start (LOG-22) precisely so calendar-day arithmetic
    does not go through a timezone. Do not introduce a date library.

    **`docs/program-vocabularies.md`.** Add a "Where you are in the program" section recording: that
    position is derived and never stored, and why; that a session against a deleted day stops
    counting; that a deload consumes rotation positions and time off does not; that a time-off cycle
    is measured in calendar days from the last completed session; and that a finished block reports
    completion rather than looping.
