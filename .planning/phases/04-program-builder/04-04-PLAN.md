<objective>
**As a** lifter who runs one program at a time, **I want to** mark which program is active and stop
progression from moving its numbers, **so that** the app always knows which block I am running and I
can hold my prescriptions still when I want to.

Purpose: PROG-08 and PROG-10 need three schema facts that do not exist yet —
`user_preference.active_routine_id` (D-14), `routine.progression_frozen` (D-16), and a
`routine.status` vocabulary narrowed to `draft | ready` with a real database constraint behind it
(D-15). It also has to build `user_preference`'s server-side apply path, which
`packages/api-contracts/src/sync.ts` currently attributes to Phase 6: if this phase waits for Phase 6,
activation cannot sync across devices at all.

Building that apply path surfaces a defect the research did not: `user_preference`'s primary key is
`user_id`, and `apps/api/src/db/schema/catalog.ts` records in a code comment that
`SyncService.applyBatch` resolves every row as `eq(table.id, op.id)` and that PowerSync's local
schema gives every managed table one `id` column — so a table without one is **unwritable through
the sync path**. That is a one-way decision this phase has to make, and it is the checkpoint below.

Output: the data model that makes "which program is active" and "is progression allowed to move it"
true offline, on two devices, with a Postgres constraint behind the status vocabulary.
</objective>

  <name>Checkpoint: how `user_preference` becomes writable through the sync push path</name>
  <decision>How does `user_preference` become writable through the sync push path?</decision>
  <context>
`user_preference`'s Postgres primary key is `user_id` and it has no `id` column.
`apps/api/src/sync/sync.service.ts`'s `applyBatch` reads and upserts every row as
`eq(table.id, op.id)`, and `apps/api/src/db/schema/catalog.ts` carries an explicit comment
recording why `user_exercise_preference` was given a single TEXT `id` primary key instead of a
composite one: *"SyncService's applyBatch resolves every row as eq(table.id, op.id), and
PowerSync's local schema gives every managed table one id column — a composite PK would be
unwritable through the sync path."* `user_preference` is in exactly that position today. Nothing
in the repository currently writes it — grep confirms zero writers in `apps/api/src` and
`apps/mobile` outside the schema declarations — so both options are available now and neither
will be after this table starts carrying real rows.

Undo cost if this is wrong: a primary-key migration on a table PowerSync already syncs, plus a
coordinated client change, plus Phase 6 (which owns `default_equipment_profile_id`) inheriting
whichever shape is chosen. This is a one-way door, which is why it is a checkpoint rather than a
planner decision.

Existing evidence for option A: `apps/api/src/sync/__tests__/conflict-policy.spec.ts` already
exercises a `user_preference` op with `id: 'user-1'` — the id-is-the-user-id convention is
already assumed by a shipped test.
  </context>
  <options>
    <option id="option-a">
      <name>Give `user_preference` a TEXT `id` primary key equal to `user_id` (recommended)</name>
      <pros>`applyBatch`'s generic id-keyed path keeps working for every table with no special case. Matches `user_exercise_preference`'s documented shape exactly. The local PowerSync-managed table stops disagreeing with its Drizzle declaration, since PowerSync gives every managed table an `id` column regardless. Phase 6 extends an apply path that already works.</pros>
      <cons>Changes the primary key of a table that is already in `SYNCED_TABLES`; `drizzle-kit push` will drop and recreate the constraint and may prompt. Establishes `id === user_id` as a wire contract every client build reads.</cons>
    </option>
    <option id="option-b">
      <name>Special-case `user_preference` in `applyBatch`, keying its upsert on `user_id`</name>
      <pros>No schema change to a shipped table and no primary-key migration.</pros>
      <cons>Becomes the first table in `TABLE_MAP` that cannot use the generic path, forcing a parallel branch in the existing-row read, the tombstone check, `resolveConflict` and `patchAwareSet`. Worse, PowerSync still gives the local table its own `id`, so the op arriving on the wire would carry a PowerSync-generated uuid unrelated to the user, which the server would have to ignore — the exact shape that produces a row that exists but cannot be found.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a or option-b</resume-signal>
