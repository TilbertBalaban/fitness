<objective>
**As a** lifter with more than one program, **I want to** keep them in a library where I can duplicate
one to start the next block, archive the ones I am not running, restore them later, and say which one
is active — and freeze the active one so progression stops moving its numbers, **so that** the
everyday screen stays about the one program I am running.

Purpose: PROG-07, PROG-08 and PROG-10 are the last three requirements without a surface. 04-04 built
the data — the active pointer, the freeze flag, the narrowed status vocabulary and their sync apply
path — but nothing reaches them from the app. D-26 splits the two concerns: the Programs tab is the
active program, and a separate library screen holds everything else and the archive. D-28 puts
duplication at creation time, where it is actually useful.

Output: a program library with duplicate, archive, restore and activate, a create flow that offers
blank or duplicate, and a freeze switch on the active program.
</objective>

      this rather than re-deriving it.
    - `clearActiveRoutine(userId, db)` — one update setting `activeRoutineId` to null.
    - `setProgressionFrozen(routineId, frozen, db)` — one update writing only that column. Freeze is
      orthogonal to both `status` and the active pointer; writing either alongside it would collapse
      three independent facts into one and reintroduce exactly what D-14 and D-16 exist to prevent.
    - `archiveRoutine({ userId, routineId }, db)` — set `archivedAt` to `new Date().toISOString()`,
      then read `user_preference` and, when its `activeRoutineId` equals this routine, clear it. Two
      writes, conditionally. Never a delete: `HARD_DELETE_FORBIDDEN` on the server already rejects a
      routine delete, and logged sessions reference this program's days by id with no foreign key, so
      a destroyed routine orphans history that cannot be reconstructed.
    - `restoreRoutine(routineId, db)` — one update setting `archivedAt` to null. Restoring does not
      activate; the user activates explicitly.
    - `markRoutineReady(routineId, db)` — one update writing `status` from the imported
      `ROUTINE_STATUSES` tuple. This is the "I have finished authoring this" transition; a draft that
      is never marked ready is still a real, synced, usable program, so nothing gates on it.

    **`apps/mobile/lib/db/programs/duplicate-routine.ts` (new).** One function per D-18's scope, not
    a copy loop per call site — a single implementation is testable once for "did every child get a
    new id and a rewritten parent" instead of trusting several call sites to do it identically.

    - `duplicateRoutine({ sourceRoutineId, name }, db): Promise<DuplicateResult>` — read the source
      tree through `loadProgramTree` (five queries, bounded), then build **one id map per table**:
      source cycle id -> new id, source day id -> new id, source exercise id -> new id. Insert the new
      routine first, then cycles, then days, then exercises, then overrides, rewriting every foreign
      key through the maps. The new routine gets `createdFromTemplateId: sourceRoutineId` (the column
      already exists and is unused), `status: 'draft'`, `progressionFrozen: false`,
      `archivedAt: null`, `source: 'user'`. It writes nothing to `user_preference`.
    - `duplicateDay({ routineDayId, name }, db)` — read the day, its exercises and their overrides;
      insert one new day at `appendOrderIndex` over the routine's existing day indexes, then the
      exercises with rewritten `routineDayId`, then the overrides with rewritten `routineExerciseId`
      and **unchanged** `cycleId` — the duplicated day lives in the same program and therefore under
      the same cycles.

    Every inserted row's id is a fresh `generateClientId()` (D-03), issued before any network round
    trip. Return the new routine id (or new day id) so the caller can navigate to it.

    The id-map discipline is the whole correctness argument: a foreign key rewritten from the wrong
    map, or not rewritten at all, produces a copy whose children point back into the source program.
    That is invisible until the user edits one and both change. The source-id-membership assertion in
    `<behavior>` is what catches it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| direct URL load of `/programs/*` | Expo Router mounts a route by URL on web; an unregistered or unguarded route mounts regardless of session state |
| duplicate operation -> foreign keys | A copy whose children point back at the source silently binds two programs together |
| archive -> the active pointer | Two rows that must not disagree about whether a program is both archived and active |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-52 | Elevation of Privilege | `/programs` routes on a signed-out session | high | mitigate | The segment layout collapses every `/programs/*` route into one `programs` route, and root-stack registers it exactly once inside `Stack.Protected guard={signedIn}` — the T-03-58 pattern already applied to `/exercises`. Asserted by a route-guard test and by a grep proving no second guard exists inside the segment layout. |
| T-04-53 | Tampering | duplicated rows pointing at the source program | high | mitigate | One id map per source table and a test asserting that no inserted foreign key is a member of the source id set — the only assertion that catches a missed map entry, which is otherwise invisible until the user edits one copy and both change. |
| T-04-54 | Repudiation | archive implemented as a delete | high | mitigate | `archiveRoutine` writes a timestamp and is grep-asserted to contain no delete against `routine`; the server's `HARD_DELETE_FORBIDDEN` rejects a delete op independently. Logged sessions reference this program's days by id with no foreign key, so a destroyed routine orphans unreconstructable history. |
| T-04-55 | Tampering | an archived program left as the active one | medium | mitigate | `archiveRoutine` clears the pointer in the same call when it named the archived routine, and `partitionRoutines` classifies archived over active regardless, so a stale pointer arriving from another device cannot present an archived program as active. |
| T-04-56 | Tampering | freeze collapsing into status or the active pointer | medium | mitigate | `setProgressionFrozen` writes exactly one column, asserted by inspecting the update payload; the lifecycle suite asserts that freezing leaves both `status` and `activeRoutineId` untouched. |
| T-04-57 | Denial of Service | duplicate on a large program | low | mitigate | The source is read through `loadProgramTree`'s fixed five queries and written as one grouped insert pass per table; the query count is asserted identical for a 3-exercise and a 30-exercise source. |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package. |
