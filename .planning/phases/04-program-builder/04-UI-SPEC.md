# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn is not applicable. Unchanged from Phase 1/3: this is React Native + React Native Web, and shadcn's Radix primitives cannot run inside a native `View`/`Text` tree. `components.json` correctly does not exist. |
| Component library | Hand-rolled RN components under `apps/mobile/components/`, extending the exact set Phase 1/3 shipped (`PrimaryButton`, `TextField`, `SelectField`, `FilterChipRow`, `SearchField`, `ExerciseListRow`, `DetailSection`, `ArchiveDialog`, `ErrorBanner`, `NavBackButton`). This phase adds `CycleStrip`, `DayDeck`, `ExerciseSlotRow`, `ExercisePickerModal`, `DragHandle`/`DragHandle.web`, a generalized `RoutineActionSheet` (archive/restore/duplicate/delete-draft), and a `NextUpCard` — every new component styles itself against the same NativeWind token set, none introduces a second visual language. |
| Icon library | `@expo/vector-icons` (`Ionicons`), unchanged. Per Phase 1 D-06/Phase 3's established rule: an icon is used only where its color does not need to dynamically track theme state through a prop the icon library owns — in that case `useThemeColors()` resolves the color and is passed as the `color` prop (the existing chevron/checkmark pattern), never a NativeWind className on the icon itself. This phase's new icons (drag-handle grip, deload/time-off cycle-chip glyphs) follow the identical mechanism. |
| Font | System default, unchanged — no `fontFamily` override exists or is introduced this phase. |

**Design decisions this document resolves that CONTEXT.md left open** (discretion items, not re-litigated with the user — bounded, reversible, decided here per the established design system):

1. The three cycle-strip chip tones (D-12/D-22 required "visually distinct," didn't name the tones) — see **Cycle Strip**.
2. The shape of numeric target entry (D-25 said "inline," didn't say stepper vs. free-text) — resolved as steppers, which also resolves the "what does a blank target mean" and "can an exercise save with no targets" discretion items structurally — see **Exercise Slot Row**.
3. Discarding a draft: **Delete** (real, per D-05's carve-out) vs. **Archive** (per D-05) — resolved by whether any session has ever been logged against the routine — see **Program Library**.
4. Freeze and Duplicate need no confirmation dialog; Archive and Delete Draft do — see **Confirmations**.
5. A phase-wide no-truncation rule for every *new* Phase 4 surface (see **Phase-Wide Rules**, R4) — this is a deliberate divergence from Phase 3's `ExerciseListRow`, which truncates exercise names to one line for scan density in a dense search list. That truncation is not overturned — the picker in this phase reuses `ExerciseListRow` verbatim and inherits it unchanged — but every genuinely new Phase 4 row (the slot row, the cycle chip, the library row) wraps and grows instead, because this phase's hard constraint explicitly names "the numeric target inputs on the slot row" as the hardest wrap-and-grow case, and because these are authoring surfaces without a fixed scan-density requirement.

## Spacing Scale

Declared values (already shipped in `apps/mobile/tailwind.config.js`, multiples of 4 — inherited unchanged):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing |
| md | 16px | Default element spacing |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

**Exceptions inherited, still binding:**
- **48×48px minimum hit target** on every interactive element — carries forward unchanged, and this phase is the densest test of it yet: the drag handle grip, each stepper's +/- buttons, the cycle-strip chips, the library row's action-menu trigger, and the picker's per-row checkmark all hold the floor.

**New exceptions this phase introduces:**
- **The numeric stepper's readout container has no fixed width.** `min-width: 32px`, unbounded max-width, `flex-shrink: 1`; the flanking +/- buttons are `flex-shrink: 0` and stay fixed at 48×48 regardless of OS font scale (they are glyph buttons, not scaled text) — see **Exercise Slot Row**.
- **`Switch` (native RN control) is exempt from the manual 48×48 padding pattern** used elsewhere — its own native hit target already satisfies both platforms' accessibility minimums. Wrap it in a `Pressable` label row of at least 48px height so tapping the row label (not only the switch thumb) also toggles it — see **Freeze Toggle**.

## Phase-Wide Rules

Extends Phase 1's R1–R3 (still binding: wrap-and-grow, ~3s web cold-start bound, explicit-submit-may-block/passive-check-may-not). This phase adds:

- **R4 — New Phase 4 surfaces never truncate.** Every component this phase introduces (`CycleStrip`, `DayDeck`, `ExerciseSlotRow`, `ExercisePickerModal`'s own chrome, `NextUpCard`, the library row) wraps and grows at any OS font scale — no `numberOfLines`, no `ellipsizeMode`. This does not retroactively change `ExerciseListRow`, which the picker reuses unmodified and which keeps its Phase-3-approved one-line truncation for scan density in a dense search list; R4 governs only rows this phase adds.
- **R5 — Structural validity over inline validation.** Wherever a numeric target has a min/max pair (rep range, RIR range), the stepper pair is built so an invalid state (min > max) cannot be entered in the first place — see Exercise Slot Row. No inline validation-error copy exists for these fields because there is nothing to reject.
- **R6 — Local-first surfaces have no loading state for already-seeded data.** Every read this phase performs (routine tree, cycle list, catalog for the picker) is a synchronous local SQLite query, identical in kind to Phase 3's catalog reads. None of these renders a spinner; only the top-level screen's very first paint may show a brief skeleton (reusing the exact 3-row skeleton pattern already shipped in `programs.tsx`).

## Correction Note — Shipped Programs Tab (04-01)

`04-01-PLAN.md` shipped `programs.tsx` as a tracer: an inline name field + "Create Program" button above a `FlashList` of **every** non-archived routine, each row showing its raw `status` string. This was correct scope for a tracer slice and is sound as far as it goes, but three things must change as later plans in this phase extend it — recorded here so the plan for 04-02/04-11 treats them as corrections, not fresh decisions:

1. **Scope narrows from "all programs" to "the one active program."** Per D-26, the Programs tab becomes the active-program screen. The current `FlashList` of every routine is the shape that belongs on the new `library.tsx` route (see Program Library below), not on the tab. The tab shows either the active program's builder (cycle strip + day deck) or, if `user_preference.active_routine_id` is null, an empty state pointing at the library/new-program flow.
2. **Program creation moves off the tab.** The inline `TextField` + `PrimaryButton` "Create Program" pair currently living in the tab's `ListHeaderComponent` belongs on the D-28 new-program flow (`new.tsx`) instead — the active-program tab should be "about authoring and managing" the one active program, not about starting new ones.
3. **Status text needs human-readable copy.** The shipped row renders `item.status` verbatim ("draft" / "ready"). Wherever status is still shown post-correction (the library row), it must render Title Case ("Draft" / "Ready"), Label role — never the raw lowercase enum value.

Everything else about the shipped screen — the `PrimaryButton` submitting-state pattern, the `TextField` error contract, the four-state derivation shape (`error`/`loading`/`empty`/`populated`), the skeleton-row loading treatment — is sound and is the pattern every new screen in this phase reuses.

## Cycle Strip (D-09, D-12, D-22)

A horizontally scrolling row of chips pinned above the day deck: `1  2  3  Deload  4 · Time off`. Selecting a chip re-renders the day deck below with that cycle's resolved targets (D-10) without losing day position.

**Empty state — the strip is absent, not empty.** A routine with zero `routine_cycle` rows (a legitimate, common case — a non-periodized program never needs cycles at all) renders **no strip at all**, mirroring `FilterChipRow`'s existing "render nothing, not an empty heading" convention. The day deck below reads base `routine_exercise` targets directly with no cycle context. The strip only ever appears once the user has created at least one cycle.

**The three chip tones — resolved (this phase's own design call, not a CONTEXT.md decision):**

| Kind (`routine_cycle.kind`, from `api-contracts` `CYCLE_KINDS`) | Border | Fill | Icon (Ionicons, `useThemeColors()`-resolved) | Notes |
|---|---|---|---|---|
| `training` | `border-foreground-muted` (unselected) / `border-accent` (selected) | `bg-surface` | none | Identical shape to `FilterChipRow`'s existing chip |
| `deload` | Same border colors as `training`, but `border-style: dashed` | `bg-surface` | `trending-down-outline`, 16px, leading the label | Dashed border reads "temporary/reduced" without a new hex |
| `time_off` | `border-foreground-muted` always (never accent, even when selected) | `bg-surface/60` (reduced opacity — the chip visually recedes) | `moon-outline`, 16px, leading the label | Selection is shown by a small foreground-muted underline indicator instead of an accent border, since accent is reserved for "trainable content ahead," which time off explicitly isn't |

Selection state is drawn identically across all three (accent border + icon tint, except `time_off`'s underline variant) — **kind** and **selection** are orthogonal visual dimensions, never conflated.

**Sizing and overflow:** chips hold the 48×48 minimum. The strip scrolls horizontally and chips never wrap to a second row (wrapping would push the day deck's vertical position unpredictably on every selection). A long cycle name widens its chip (R4 — grow, never truncate); it does not force a second line inside the chip.

**Naming:** cycle name is required non-empty at creation, matching `routine`'s own name requirement (Correction Note pattern) — there is no "unnamed cycle" state to design for. New deload/time-off cycles are pre-filled with a sensible default name ("Deload", "Time off") that stays user-editable.

## Exercise Slot Row (D-25) — the phase's highest-value contract

Tapping a collapsed row expands it in place to reveal sets / rep range / RIR range / rest. No modal, no screen change; neighbouring rows stay visible.

**Collapsed state:** exercise name (Body, R4 — wraps fully, does not truncate, unlike the picker's reused `ExerciseListRow`) plus a single muted summary line (Label, `text-foreground-muted`):
- All six target fields null → **"No targets set."**
- Any subset set → **"{sets} sets · {repMin}–{repMax} reps · {rirMin}–{rirMax} RIR · {rest} rest"**, with an em dash (`—`) standing in for any individual null field (e.g. `"3 sets · 8–12 reps · — RIR · 1:30 rest"`). This is the concrete resolution to the open "what does a blank target mean" discretion item: **null means deliberately unprescribed, and always renders as `—`, never coerced to `0` or omitted silently.**

**Expanded state — four stepper fields, each a labelled row:**

| Field | Range | Step | Display |
|---|---|---|---|
| Sets | 1 and up, no upper bound | 1 | Plain integer |
| Rep range (min + max steppers, side by side) | 1–50 each | 1 | `{min}–{max}` |
| RIR range (min + max steppers, side by side) | 0–6 each (6 represents the open-ended "6+" of LOG-06's future scale, kept consistent for Phase 8) | 1 | `{min}–{max}` |
| Rest | 0:00 and up | 15s | `M:SS` (e.g. `1:30`), never raw seconds |

**R5 in practice — min/max pairs cannot go invalid.** Incrementing a range's min stepper above the current max also increments max to match; decrementing max below the current min also decrements min to match. The pair is always internally consistent by construction — there is no inline "min must be ≤ max" error state anywhere in this row, because that state cannot be reached.

**Stepper anatomy:** `[−]  {value}  [+]`, each `[−]`/`[+]` a 48×48 `Pressable` with an Ionicons glyph (`remove`/`add`), color resolved via `useThemeColors()` exactly like the existing chevron/checkmark pattern — never a hardcoded literal. The `{value}` readout has no fixed width (`min-width: 32px`, `flex-shrink: 1`) so it grows at large OS font scales without clipping; the buttons stay fixed at 48×48 regardless of font scale, since they are glyph-driven, not text-scaled.

**Max-font-scale layout (the hard case named explicitly in this phase's constraints):** the rep-range and RIR-range rows lay out `flex-row flex-wrap`. At default font scale the min-stepper and max-stepper sit side by side on one line; at large accessibility font scales, once the readout text grows enough that the pair would compress the +/- buttons below their 48×48 floor, the pair wraps — the max stepper drops to its own line beneath the min stepper, rather than the row scrolling horizontally or any control shrinking below the touch-target floor. This is the concrete, testable statement of "wrap-and-grow, never truncate" for this row.

**Saving with no targets at all is allowed.** An exercise can be added and left entirely untargeted (all six fields null) — the collapsed row's "No targets set" summary is a normal, supported state, not an error.

## Day Deck & Drag Handle — Platform Contract (D-21, D-23)

**Day Deck:** `react-native-tab-view`'s `TabView`, `renderTabBar={() => null}` (the cycle strip is a separate, pinned component, not this library's own tab bar). Per `04-RESEARCH.md`, this library ships its own native/web split internally (`react-native-pager-view` on native, `PanResponder` on web) — **no `DayDeck.web.tsx` sibling is needed for the paging mechanism itself.** Each page is a vertical, non-virtualized list of that day's `ExerciseSlotRow`s (day exercise counts are small; `FlashList` is not needed here the way it is for the ~900-row catalog).

- **Empty (zero days in the routine):** the deck is replaced by a single "Add your first day" prompt, not an empty pager.
- **A day with zero exercises:** that page shows an inline "Add exercises to this day" prompt (opens the Exercise Picker Modal) instead of an empty list — distinct from the zero-days case above.
- Comparing two days is one swipe (D-21's own framing) — no jump-to-day index affordance ships this phase; sequential swipe is the only navigation this phase commits to.

**Drag Handle:** ships as two files per `docs/platform-modules.md`'s `.web.tsx` convention — `DragHandle.tsx` (native: `react-native-gesture-handler` + `react-native-reanimated` pan gesture, pending the spike `04-RESEARCH.md` flags as this phase's largest unbudgeted risk) and `DragHandle.web.tsx` (pointer-events-based drag, the sanctioned web escape hatch if the spike finds gesture-handler's web story has gaps). **Both files must render pixel-identical appearance** — a grip glyph (`reorder-three-outline` or the nearest available Ionicons reorder/grip glyph), 48×48 hit area, trailing edge of the row, color resolved via `useThemeColors()` — so a user moving between native and web perceives the same affordance even though the underlying gesture mechanics differ. The grip's hit region is disambiguated from the row's own tap-to-expand region so pressing the grip never also triggers expand/collapse.

- **Interrupted drag** (app backgrounded mid-gesture, or a drop outside a valid target): the row springs back to its last confirmed position. Nothing partially persists — no error banner, this is a gesture affordance detail, not a data-integrity concern (D-01's snapshot-on-use and the `order_index` write only ever happen on a completed, valid drop).
- **Native drag behavior is unobservable in this environment** — no Xcode, no Android SDK (per this phase's stated environment constraint). The web pointer-based drag in `DragHandle.web.tsx` is the only interaction this phase can actually exercise end to end, and per the environment constraint that must be treated as the meaningful check for D-23 at this phase's gate; the native path rests on typecheck plus correct API usage and is recorded in `.planning/WINDOWS.md`, deferred to ROADMAP Phase 999.1.

## Exercise Picker Modal (D-24)

Full-screen, opened from the "Add exercises to this day" prompt (Day Deck empty-day state) or an explicit "Add Exercises" control on a populated day page. Reuses the Phase 3 catalog screen's `SearchField` + `FilterChipRow` + `ExerciseListRow` verbatim, in multi-select mode.

- Each row gets a selection affordance identical to `SelectField`'s existing checkmark pattern (checkmark icon, accent-tinted, shown when selected) — `ExerciseListRow` itself is not forked; the checkmark is composed around it.
- **Selections persist across search/filter changes.** Selecting rows under one filter, then changing the filter or search query, does not clear prior selections — this must be stated explicitly since it is the easiest thing to get wrong in a multi-select-over-a-filtered-list pattern.
- A persistent footer bar shows the running count and the CTA: **"Add Exercise"** (exactly one selected) / **"Add {N} Exercises"** (many). Zero selected **disables** the CTA rather than hiding it, so the action stays discoverable.
- Empty search results reuse Phase 3's exact "No exercises found" / "Try a different search term or clear your filters." copy — not a new string for this modal.
- Zero-result and load-failure states inherit `ExerciseListRow`'s and the catalog screen's existing, already-approved contract unchanged (R4 does not apply here — this modal's list content is the reused Phase 3 component, not a new Phase 4 row).

## Home "Next Up" Card (D-27, D-20, PROG-09)

Lives on the Home tab (`index.tsx`, a placeholder today). Shows the single next workout derived from logged history (D-20) — **not** a list of several upcoming workouts, despite PROG-09's plural "upcoming workouts" wording; D-27's own decision text ("the next workout and its resolved targets") narrows this to one card. This is a scope clarification worth stating plainly, not an open question — the requirement is satisfied by showing the immediate next workout with its resolved targets, not a multi-workout list.

**States:**
- **No active program set:** card reads **"No active program"** / "Build or activate one to see what's next." with a link into the Program Library.
- **Populated (happy path):** day name (Heading), a row of read-only target-muscle chips (visually identical to `FilterChipRow`'s chip shape but non-interactive — no `accessibilityRole="button"`, no `onToggle`, no selected state), then one line per exercise: **"{exercise name}: {sets} × {repMin}–{repMax} reps @ {rirMin}–{rirMax} RIR"**, with the same em-dash-for-null convention as the slot row's collapsed summary.
- **Currently in a `time_off` cycle:** the card reads **"You're on scheduled time off."** in place of any workout content — muted styling, no target-muscle chips, no exercise lines.
- **The `04-RESEARCH.md` Pitfall-5 edge case (the most-recently-logged day has since been deleted from the routine):** resolves silently to "first day of the current cycle" per D-20's own fallback rule — this never surfaces as a user-visible error state; the card simply renders that fallback day's resolved targets as if it were the normal next day.
- **No "Start Workout" action ships this phase.** Starting a session is Phase 5's scope (LOG-01) — the card is read-only informational content in Phase 4.

## Program Library (D-26, D-28, PROG-07)

`library.tsx` holds every program except the currently-authoring active one's dedicated tab view (the active program is still listed here too, badged, for activate/deactivate symmetry). Two sections, each rendered only when non-empty (mirrors `DetailSection`'s own-empty-omits-header convention): **"Your Programs"** and **"Archived"**.

- **Empty (no programs besides — or including — the active one):** "No other programs yet." + a link into the New Program flow.
- **Loading:** reuses the exact 3-row skeleton already shipped in `programs.tsx`.
- **Error:** reuses the exact "couldn't load" heading/body pattern already shipped in `programs.tsx`, reworded for programs generically.
- **Populated row:** program name (R4 — wraps, no truncation), status (Title Case per the Correction Note), an **"Active"** badge (accent-filled, Label role) on at most one row across the whole screen, and a trailing 48×48 **"•••"** action-menu trigger opening a `RoutineActionSheet` with: Activate (hidden on the already-active row), Duplicate, Rename, and either Archive or Restore depending on `archived_at`, or Delete instead of Archive per the rule below.
- **Archived rows:** visually receded (`opacity-60`, matching the cycle strip's `time_off` treatment for visual-language consistency — "archived" and "off" read the same way: present but not active).

**New Program flow (`new.tsx`, D-28):** two choices, **"Start Blank"** and **"Duplicate Existing."** On a truly empty account (D-28's own language), Duplicate Existing is disabled with inline copy explaining why ("You don't have another program to duplicate yet."), and Start Blank is the only live path. Choosing Duplicate Existing opens a picker of non-archived programs as the source (this sub-picker's own "no eligible source" case collapses to the same disabled-Duplicate treatment). Program name reuses `TextField`'s exact error/submitting contract from the shipped tracer.

## Freeze Toggle (D-16)

An always-visible switch on the active-program screen only, labelled **"Update Program"** per the MacroFactor precedent this decision is modeled on (`FEATURES.md` line 39) — Label role, `text-foreground-muted`, positioned beside a native `Switch` (`trackColor.true` = accent). Wrapped in a `Pressable` row of at least 48px height so tapping the label also toggles it (the `Switch` control itself is exempt from manual 48×48 padding per the Spacing exception above).

**No confirmation dialog on toggle, either direction.** Freeze is a reversible boolean (D-16), not a destructive action — toggling it takes effect immediately, exactly like the Phase 1 Appearance control.
