<objective>
**As a** lifter building the program I actually train, **I want to** give it named training days and
put ordered exercises in each one, **so that** the shape of my week is the shape the app knows.

Purpose: 04-01 proved a routine root reaches Postgres. This plan expands that proven slice down the
tree — `routine_day` and `routine_exercise` — which is where the sync apply path stops being a copy
of an existing pattern and starts being new work: `routine_exercise` chains through **two**
intermediate levels to its owner, one deeper than the `session_exercise -> workout_session` case the
existing code was written against.

It also resolves the `order_index` question CONTEXT.md left to Claude's discretion. Contiguous
integers are the obvious implementation and they are wrong here: a drag rewrites every row in the
list, and two devices reordering the same day offline each push a full rewrite that row-level LWW
then interleaves into an order neither user asked for.

Output: days and exercises you can add, remove and reorder, that survive a round trip to Postgres,
and a builder read path that opens the whole tree in three queries.
</objective>

    **`apps/mobile/lib/db/programs/order-index.ts` (new).** The ordering decision CONTEXT.md left
    open, resolved as **integer gaps**, not fractional indices. Both approaches solve the
    offline-reorder-conflict problem; integer gaps were chosen because `routine_day.order_index` and
    `routine_exercise.order_index` are already `integer NOT NULL` on both Postgres and SQLite, so this
    needs no column widening, no change to `sync.service.ts`'s `isNonNegativeInteger` validator, and
    no divergence from `session_exercise.order_index`, which stays an integer. Record that reasoning
    in the SUMMARY as the answer to the discretion item — a later reader must be able to see that
    fractional was considered and why it lost.

    Export, all pure and all synchronous:
    - `ORDER_INDEX_GAP = 1024`
    - `appendOrderIndex(existing: number[]): number` — `GAP` for an empty list, otherwise `max + GAP`.
    - `midpointOrderIndex(before: number | null, after: number | null): number | null` — with both
      present, return `Math.floor((before + after) / 2)` when `after - before >= 2`, else `null`;
      with only `after`, return `after - GAP` floored at… no, return `Math.floor(after / 2)` when
      `after >= 2`, else `null` (inserting before the current first row must not produce 0 or a
      negative index, since the server rejects a negative `order_index`); with only `before`, return
      `before + GAP`; with neither, return `GAP`.
    - `needsRenumber(before: number | null, after: number | null): boolean` — true exactly when
      `midpointOrderIndex` would return `null`.
    - `renumberOrderIndexes(orderedIds: string[]): { id: string; orderIndex: number }[]` — assigns
      `(i + 1) * GAP`.
    - `sortByOrderThenId<T extends { id: string; orderIndex: number }>(rows: T[]): T[]` — ascending
      `orderIndex`, ties broken by ascending `id`, returning a new array. Every read path in this
      phase sorts through this function so an LWW-produced tie can never render differently on two
      renders of the same data.
