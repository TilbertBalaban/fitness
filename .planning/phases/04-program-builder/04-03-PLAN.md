<objective>
**As a** lifter filling in a training day, **I want to** pick several exercises from the catalog at
once and set each one's sets, rep range, RIR and rest without leaving the day, **so that** building a
day from empty is one pass instead of a dozen round trips through a picker.

Purpose: 04-02 gave days and exercises a persistence and sync path but no way to choose an exercise
or prescribe anything. This plan closes both — D-24's full-screen multi-select picker over the Phase
3 catalog, and D-25's inline-expanded target entry — and settles the discretion item CONTEXT.md left
open about what a blank target means.

Output: a day you can fill from the catalog in one action, and per-exercise targets you can set in
place with the rest of the day still on screen.
</objective>

  <action>
    **`apps/mobile/lib/db/programs/targets.ts` (new).** This module answers the "what does a blank
    target mean" question CONTEXT.md left to Claude's discretion. The answer, recorded here and in
    the SUMMARY so Phase 5 and Phase 8 inherit it: **null means deliberately unprescribed, never
    zero, and the builder always allows it.** Nothing downstream may substitute a default for a null
    target; a null reaching `log-set.ts` is snapshotted as null, and a null reaching the progression
    engine means "the user did not prescribe this dimension".

    Export:
    - `interface TargetDraft` — the five fields as `number | null`.
    - `type TargetFieldError = 'whole-number' | 'negative' | 'not-a-number' | 'min-above-max' | 'below-minimum'`
    - `parseTargetField(raw: string): { value: number | null } | { error: TargetFieldError }` — trim;
      empty is `{ value: null }`; reject a value that is not a finite number (`not-a-number`), that
      is not an integer (`whole-number`), or that is negative (`negative`). Parsing never applies a
      per-field minimum.
    - `validateTargets(draft: TargetDraft): Partial<Record<keyof TargetDraft, TargetFieldError>>` —
      `targetSets` below 1 is `below-minimum`; `targetRepMin` below 1 is `below-minimum`;
      `targetRir`/`targetRestSeconds` have no lower bound beyond non-negative;
      `targetRepMax` below `targetRepMin` (both present) is `min-above-max`. Every field being null
      yields an empty object.
    - `async function setExerciseTargets(routineExerciseId: string, draft: TargetDraft, db: WriteDb = getPowerSync()): Promise<void>` —
      run `validateTargets`, throw an `Error` naming the first offending field when it is non-empty,
      and otherwise issue exactly one `update(routineExercise).set({...all five...}).where(eq(id))`.
      Write all five columns every time, including the nulls: a partial write would leave a stale
      value behind for a field the user just cleared.

    Range ordering is enforced **here and not in `sync.service.ts`** on purpose. An `invalid_field`
    rejection is terminal — the client completes the crud transaction and the write is gone — so a
    server-side range check would silently discard a legitimate offline write the moment a range rule
    ever changed. The server validates shape (non-negative integer or null); the builder validates
    intent. Record that split in the SUMMARY.

    Copy the `db: WriteDb = getPowerSync()` seam and the `generateClientId` import convention from
    `days.ts`. No new dependency, no new validation library.
  </action>
