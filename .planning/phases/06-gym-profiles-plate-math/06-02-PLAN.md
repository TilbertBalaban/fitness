<objective>
Complete the pure contract the rest of the phase and all of Phase 8 depend on: an achievability
rounder whose direction is always an explicit argument, nearest-loadable neighbours for the
not-loadable state, and the one named predicate that decides what the equipment band shows for a
given exercise.

Purpose: GYM-06 ("only ever shown loads their gym can produce") is not a UI rule, it is this
module. Every consumer — the plate strip, the tap-to-autofill prefill, warm-up generation, and
Phase 8's recommendations — must round through one function with one definition, or the guarantee
degrades to "usually".

Output: `achievability.ts`, `band.ts`, the not-loadable neighbours filled into `solvePlateBreakdown`,
and an additive rounding hook on `warmupSets` that leaves every existing caller byte-identical.
</objective>

database handle, no React import and no module-level mutable state — the same contract

Export `RoundDirection = 'nearest' | 'down' | 'up'` and
`roundToAchievable(targetKg: string, loads: string[], direction: RoundDirection): string | null`.
The direction is a required positional argument with no default value — per D-10, a rounder that
silently defaults is exactly the bug this decision exists to prevent, and `warmupSets`' own comment
already records what a silent round-down costs. For `'nearest'`, a target exactly halfway between
two achievable loads resolves to the **lower** one; document that tie rule as a why-comment and
note that it deliberately differs from `roundToIncrement`'s ties-toward-positive-infinity rule in
`packages/pr-rules/src/warmup.ts`, which stays as it is. Return null rather than the raw target when
no achievable load exists in the requested direction — a caller that would then display the raw
target must decide that consciously, not inherit it.

Export `achievableBarbellLoads(inventory: ResolvedInventory): string[]` — the ascending, deduplicated
set of totals reachable from the bar plus any subset of the recorded pairs, bounded by
`EQUIPMENT_PROFILE_LIMITS`, computed in the same integer scale `solvePlateBreakdown` uses so the two
can never disagree about what is loadable. Export equivalents for the other two inventory kinds:
`achievableDumbbellLoads(inventory)` (the recorded dumbbell weights) and
`achievableMachineLoads(machine)` (inclusive `stackMinKg`..`stackMaxKg` stepped by
`stackIncrementKg`, plus `baseResistanceKg` when configured; a machine with no increment yields

of the same ascending set so a value can never appear as a neighbour that the solver would then
refuse to break down.

Extend the solver tests with the neighbour cases and write `achievability.test.ts` covering every
