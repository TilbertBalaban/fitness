Write `docs/equipment-profile-shape.md` following the exact section structure
`docs/catalog-load-types.md` establishes — a project reader should not be able to tell the two were

Cover four shapes: the three `equipment_profile` JSON columns and the session's
unavailable-equipment column. For each, give a field table naming every field, its type, whether it
is nullable, its unit, and what an absent value means. State plainly that counts are recorded in
*pairs*, not individual plates, and why — a bare count would be ambiguous and every breakdown would
silently be out by a factor of two. State that every decimal is an exact decimal string in canonical
kilograms at the project's canonical scale, and that a numeric value is rejected rather than
coerced, so the exact-fraction guarantee the units module provides is never bypassed.

Record where enforcement lives and where it does not: these shapes have no Postgres constraint at
all, the contract package's type guards plus the sync push validator are the only backstop, and the
same is true of the equipment-type vocabulary they reference. That asymmetry with the load-type
vocabulary is deliberate and documented in the source, and a reader who assumes a database
constraint will catch a bad write is wrong.

Record the serialize and deserialize rule: the Postgres columns are real JSON while the local
mirror stores them as text, so every read and write on both sides routes through the one pair in
the contract package, and an inline conversion at a call site is a defect. Name the size limits and
say that a payload past them is rejected rather than truncated.

Finish with the extension rule: adding a field to any of these shapes is additive only, an existing
field is never repurposed, and a shipped field is never removed — client builds in the field read
this wire contract, and a rename is a break, not a refactor.
