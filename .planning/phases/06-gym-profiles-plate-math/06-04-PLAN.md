Let the user describe their actual gym: the bar, the plates they own and how many pairs of each,
the dumbbells on the rack, and the machines with their stack ranges and starting resistance.

the two routes, and a real-browser proof that a gym created and edited through the UI reads back
correctly.

    - Changing the draft's unit reinterprets nothing already entered: the stored canonical values are held, and only their displayed representation changes.
    - `upsertPlateDenomination(draft, weight)` with a weight already present increments nothing and creates no second row; it returns a draft whose plate list length is unchanged.

    - `toEquipmentProfileDraft` drops plate rows whose pair count is zero and machine rows whose name is blank, so an abandoned add never persists as an unnamed entry.
    - A draft exceeding any limit in `EQUIPMENT_PROFILE_LIMITS` is reported as not saveable rather than silently truncated.

`GymProfileDraft` holds `name`, `nativeUnit`, `barWeight` as a display-unit string, and three

display-unit stack fields). Everything the user sees is a display-unit string; everything stored is
canonical kilograms, converted only at this boundary through `toCanonicalKg` and `fromCanonicalKg`.
That is D-03's one conversion boundary — no other module in this plan converts.

new draft and mutates nothing. Denominations are keyed by their canonical value, not their typed
string, so entering the same weight twice in different notation merges rather than producing two
rows the solver would then have to order arbitrarily.

selected, and every list within its `EQUIPMENT_PROFILE_LIMITS` bound. There is no inline field-level

except for the name, which follows the existing form convention of a single field error.

Sort the emitted plate list descending and the dumbbell list ascending before handing it to the
write helper, so what the solver later reads is already in the order `resolveInventory` guarantees

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-10 | Tampering | editor draft to profile conversion | medium | mitigate | `toEquipmentProfileDraft` emits only exact decimal strings produced by `toCanonicalKg`, which throws on anything that is not a non-negative decimal, so a malformed field can never reach the JSON columns as a number or a free string. |
| T-06-02 | Denial of Service | inventory list length | medium | mitigate | `isGymProfileSaveable` refuses a draft past `EQUIPMENT_PROFILE_LIMITS`, so the client cannot author the oversized payload the server validator would reject; the two bounds come from the same constant. |
| T-06-11 | Tampering | machine entry identity | low | mitigate | Machine entries carry a client-generated id assigned once at creation, so a rename cannot orphan a session's unavailability reference to that machine. |
</threat_model>
