<objective>
Persist the program cycle a session was started against, end to end, so "Also update my program"
writes the row the displayed value actually resolved from (D-15, LOG-15).

`resolveWriteBackTarget` already branches override-vs-base correctly and is unit-tested both ways.
Its only production caller hands it a hardcoded null cycle id for every programmed session, so the
override branch is dead code in practice and the user's persistent edit lands on the base
`routine_exercise` row even when the session's cycle carries a `routine_exercise_cycle_target`
override — which then keeps shadowing the edit on every future cycle (WINDOWS #123, VERIFICATION
gap 1).

This is the phase's tracer slice: one thin path touching every layer the gap work touches —
Postgres schema, the SQLite mirror, the server sync apply path, the client write funnel, the client
read query, and both screen call sites — wired for keeps, not prototyped. 05-12 supplies the
browser-real end-to-end proof against a live database; this plan's own verification is the
composed-unit slice plus the live schema push.

Purpose: make write-back land on the correct row for programs that use Phase 4's per-cycle
overrides — exactly the programs Phase 4's own success criteria say this app must support.
Output: a `cycle_id` column on both schemas, stamped once at session start, read back through
`LiveSessionRow`, and threaded to `TargetsSheet` at both screen call sites.
</objective>

<user_decision_note>
The approach is **user-locked**: persist `cycle_id` on `workout_session`, stamp it once in
`startSession`, thread it from the session row through `useWorkoutScreen` -> `ExercisePageData` ->
`TargetsSheet`. In-memory threading of the cycle id captured at `handleStartWorkout` time was
explicitly rejected, because a restored session (force-quit and relaunch, SC4) re-reads the session
from the database and would silently regress to the base row on every restore. Do not re-litigate
this and do not offer alternatives.
</user_decision_note>

<assumption_delta_decision>
**Signal:** the deterministic scan returned `{"detected": true, "signals": [{"kind": "chosen", "term": "chosen"}]}`.
Beyond the literal snippet, this plan *is* a `chosen`-family transition: the session's cycle
identity moves from derived-and-discarded (computed inside `handleStartWorkout`, used to freeze the
prescription, then thrown away) to persisted-and-authoritative (a stored column every later read
resolves against).

**Now-primary noun:** the session's cycle identity — "which program cycle was this session started
in" — is now a first-class, stored property of `workout_session`, not a transient argument.

**Decision: `promote`.** The stored column becomes the single source of truth for the session's
cycle, and the transient argument is demoted to its input. Every read of "which cycle" (write-back
resolution today; any later progression or analytics read) goes through the column, never through a
re-derivation from routine position and history. `add-alongside` was rejected: keeping a
re-derivation path beside the column is precisely the shape that produces two answers for one
question after a routine is edited, and it would silently reintroduce the restored-session
regression the user's locked decision exists to prevent.

**Suggested (not required) invariant test:** *every programmed session resolves write-back against
the cycle it was actually started in, for both the override and the base case.* Task 2 already
carries the override/base pair as unit cases; 05-12 raises the same invariant to browser-real
end-to-end. If a future phase adds a second session-creation path that skips the stamp, that pair
goes red rather than the regression landing silently.
</assumption_delta_decision>
