  <name>Task 1: Confirm the four one-way schema and vocabulary doors before they are walked through</name>
  <decision>How Phase 5's new session state is modelled in Postgres and in the shared contract package. Four coupled choices, all one-way once rows exist: (a) notes as three nullable text columns vs. a separate note table; (b) pause accounting as `paused_at` + `accumulated_paused_seconds` on `workout_session`; (c) promoting `workout_session.status` to a published vocabulary that adds `paused` and gains a Postgres CHECK; (d) `PR_TYPES` as a published four-value vocabulary with its own CHECK on `personal_record.pr_type`.</decision>
  <context>
CONTEXT.md delegates schema shape to Claude's discretion, but D-09 makes each of these a published contract the moment it lands: the value goes into a not-null column, a Postgres CHECK is built from it, the local SQLite mirror copies it, and every client build in the field reads it back. Undoing any of the four after rows exist is a data migration, not a refactor — which is exactly the definition of a one-way door, so it is confirmed here rather than discovered in Phase 9 when `personal_record` rows written under one rule set meet Phase 10's reconciliation (PITFALLS §11).

What the recommended option costs to undo: notes-as-columns → a table extraction plus a backfill; pause-pair columns → recomputing every finished session's duration; `status` vocabulary → rewriting every row holding a value the new CHECK rejects; `PR_TYPES` → rewriting or discarding every `personal_record` row.
  </context>
  <options>

      <name>Recommended: three note columns, pause pair on workout_session, status vocabulary with `paused`, PR_TYPES with a CHECK</name>
      <pros>Every other per-row annotation in this schema is already a plain nullable column (`cue_text`, `instructions_text`); adding a note table would add a join and another root-family entry in `sync.service.ts` for zero behavioural gain.
