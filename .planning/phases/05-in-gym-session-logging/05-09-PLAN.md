## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| History list read → local database | A paged read discloses the signed-in user's own past sessions |
| destructive row action → multi-table delete | One action removes rows across three tables |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-09-01 | Information disclosure | `loadHistoryPage` | medium | mitigate | The page query filters `workout_session` by the authenticated user id and children resolve only through that page's session ids, matching `loadNextUp`'s existing shape; there is no cross-user read path. |
| T-05-09-02 | Tampering | `deleteSession` | high | mitigate | The three deletes run inside one local transaction, so an interruption cannot leave `logged_set` rows pointing at a removed `session_exercise`. The action is gated behind the shipped destructive confirmation with its explicit cannot-be-undone copy. |
| T-05-09-03 | Tampering | `duplicateSession` | medium | mitigate | Every copied row receives a fresh `generateClientId` value; a source row id is never reused, so a duplicate can never overwrite the source through the sync apply path's id-keyed upsert (D-04). |
| T-05-09-04 | Denial of service | history list growth | medium | mitigate | The list is virtualised with `@shopify/flash-list` and the read is a cursored two-query page; a user with years of history pays the same per-page cost as one with a week (PITFALLS §13). |
| T-05-09-05 | Repudiation | `renameSession` | low | accept | A user renaming their own training log is the intended behaviour; there is no audit requirement in this single-user product. |
</threat_model>
