`apps/mobile/lib/db/personal-record.ts`:
`logPersonalRecord({ userId, exerciseId, prType, value, loggedSetId, achievedAt }, db)` — mirrors `logSet` exactly: generate a client id with `generateClientId`, insert, return the id. No read-modify-write, no batch buffer. `value` is written as a decimal string, matching how `weight_kg` is stored, so a lifetime of aggregation cannot accumulate binary-float error.
`loadPriorBestByExercise(exerciseIds, beforeSessionId, db)` — one batched read returning a `Map<exerciseId, PriorBest>`: select the user's completed, non-warm-up `logged_set` rows for those exercises from sessions OTHER than the one being summarised, via `inArray`, then fold each exercise's rows with `foldPriorBest`. One query for every exercise in the session, never one per exercise (PITFALLS §13).
`detectPrsForSession(sessionId, userId, db)` — loads the session tree, loads the prior bests, then for each completed non-warm-up set in `logged_at` order evaluates `detectPrs(candidate, priorBest)` and, for every returned `DetectedPr`, calls `logPersonalRecord` with `loggedSetId` set to that set's id. After each detection, fold the just-evaluated set into the in-memory `PriorBest` so a session containing two progressively heavier sets records the SECOND as the heaviest-weight PR and not both — the prior best must advance within the session, not only between sessions.
`loadSessionPersonalRecords(sessionId, db)` — selects `personal_record` rows whose `logged_set_id` is in the session's set ids. Use the precise join, not an `achieved_at >= started_at` time window, which would sweep in a concurrently-synced row from another device.

`apps/mobile/lib/db/summary-query.ts`:
`loadSessionSummary(sessionId, userId, db)` returning `SessionSummary` with `{ session, durationSeconds, musclesTrained, breakdown, personalRecordsBySetId }`. Build it on `loadSessionTree` plus two more selects for `exercise_muscle_mapping` and `muscle_group` (the join `next-up-query.ts` already performs for exactly this purpose) plus `loadSessionPersonalRecords`. Assemble in memory. The whole aggregate is a fixed number of selects regardless of session size.
`musclesTrained` counts an exercise only when it has at least one COMPLETED, non-warm-up set.
`breakdown` is one `ExerciseBreakdown` per exercise with at least one completed set, carrying `{ exerciseId, exerciseName, completedSetCount, totalReps, topWeightKg, volumeKg, bestE1rmKg }`. `bestE1rmKg` is the maximum non-null `estimated1RM` across the exercise's completed working sets, or null when every set is past the validity cutoff — null is a real answer here, not a missing value (D-31). Exercises with zero completed sets are omitted. An exercise whose `removed_at` is stamped but which has completed sets IS included, because those sets stay in the user's history.
`durationSeconds` comes from `elapsedWorkoutSeconds` with the session's `started_at`, `accumulated_paused_seconds` and `ended_at`, so a session finished while paused reports the same duration the header showed.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local `logged_set` history → `personal_record` write | Derived records are computed on-device from user-owned rows and become durable, syncable rows |
| summary render → correction write | The summary screen writes back into the same tables the live screen owns |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08-01 | Tampering | `logPersonalRecord` | high | mitigate | `pr_type` values originate from `detectPrs`, whose union is the `@fitness/api-contracts` `PR_TYPES` tuple, so an out-of-vocabulary value is a compile error locally and is rejected twice more on the way to Postgres: by `hasInvalidField` (05-03) and by `personal_record_pr_type_check` (05-02). |
| T-05-08-02 | Spoofing | `personal_record.user_id` written locally | high | mitigate | The client writes its own user id, and the server's `toPersonalRecordValues` (05-03) overwrites it from the authenticated session regardless of payload, so a tampered local row cannot be attributed to another account (ASVS V4). |
| T-05-08-03 | Tampering | `loadSessionPersonalRecords` join | medium | mitigate | Records are joined by `logged_set_id` against the session's own set ids rather than by an `achieved_at` time window, so a row synced concurrently from another device cannot be misattributed to this session's summary. |
| T-05-08-04 | Denial of service | summary aggregate on a large session | medium | mitigate | The aggregate is a fixed number of selects with `inArray` batching; the constant-query-count assertion in Task 1 is the regression gate (PITFALLS §13). |
| T-05-08-05 | Repudiation | client-computed PR values | low | accept | Phase 10 owns authoritative server-side reconciliation and cross-device PR authority; this phase's rows carry `reconciled_at` null precisely so that later pass can identify them. |
</threat_model>
