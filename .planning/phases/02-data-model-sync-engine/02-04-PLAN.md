<objective>
**As a** person who trains in a pound gym and reads their history in kilograms, **I want to** see every
weight in the unit I chose without my logged numbers quietly changing, **so that** a year of training data
still adds up.

`PITFALLS.md` §10 is the failure this exists to prevent: convert on every read, round on every write, and
after a few hundred sets a lifetime total is wrong by an amount nobody can account for. D-04 answers it
structurally — kilograms as decimal are the single source of truth, conversion happens only at the
input and display boundary, and aggregation never converts at all.

Plan 02-02 already made the storage half true by column type: `logged_set.weight_kg` is `numeric`, which
cannot hold a binary float. This plan makes the code half true, and puts the conversion in exactly one
place so there is no second one to drift.

The module lands in `packages/api-contracts` rather than in the mobile app, because canonical-kilogram
storage is a contract both sides have to agree on: the server validates incoming decimals against it and
the progression engine in Phase 8 will round recommendations against a gym's real increments using the
same factor. A copy in each app is the drift `PITFALLS.md` §10 describes, one level up.

Purpose: PLAT-08 and the unit half of roadmap success criterion 5.
Output: one conversion boundary, and a stored value that cannot move.
</objective>

    `packages/api-contracts/src/units.ts` exports `WeightUnit` as `'kg' | 'lb'`, `CANONICAL_KG_SCALE` as 3

    column scale is a rounding difference nobody will find — and `DISPLAY_SCALE` as
    `{ kg: 2, lb: 1 }`. Export `KG_PER_LB` as the exact definition of the international avoirdupois pound:
    a pound is defined as exactly zero point four five three five nine two three seven kilograms, so write
    it as an exact integer numerator and denominator pair, not as a decimal literal that the language will
    immediately turn into the nearest binary float.

    Every conversion is integer arithmetic on `BigInt`. Parse the input decimal string into a scaled
    integer, multiply or divide by the factor's integer numerator and denominator, round half-up at the
    target scale, and render back to a fixed-scale decimal string. Nothing in the module may go through a
    JavaScript number for a weight value — `parseFloat`, `Number`, `toFixed` and floating-point
    multiplication all reintroduce the representation `numeric` was chosen to eliminate. The signature
    surface reflects this: every weight crosses the boundary as `string | null`, never as `number`.

    `toCanonicalKg(value, unit)` takes the user's typed value in their display unit and returns the exact
    canonical kilogram string at `CANONICAL_KG_SCALE`, or null for null and empty input. It throws on a
    negative value and on anything that is not a decimal number — a set logged at a nonsensical weight is a
    bug to surface, not a value to coerce. `fromCanonicalKg(kg, unit)` takes stored kilograms and returns

    display string with its unit suffix, and renders a null weight as an em dash so a bodyweight exercise
    reads as having no external load rather than as zero kilograms.

    The pound display scale of one decimal is deliberate and is what makes the round trip stable: it is
    finer than any real plate increment, and coarse enough that re-entering a displayed pound value maps
    back to the kilogram value it came from. Prove that rather than asserting it — the fixture table in the
    tests should span the values a real gym produces, including the small dumbbell increments where the two
    unit systems align worst.
