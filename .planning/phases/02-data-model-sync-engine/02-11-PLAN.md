<objective>
Close the seam where a rejected write disappears: make the client actually read what the server said,
and make the server survive a malformed op without taking the rest of the batch down with it.

**As a** lifter who reconnects after a session in a basement gym, **I want to** be told when something
did not sync, **so that** I never find out months later that a workout the app said was saved was
silently thrown away.

Purpose: `02-REVIEW.md` found two defects that compound into the worst failure in this phase. CR-01 —
`SyncConnector.uploadData` reads only the HTTP transport outcome and never the response body, so
every per-op rejection arrives inside a 200, `outcome === 'ok'` fires, `transaction.complete()`
permanently removes those entries from the local outbox, and `sync-status.ts` reports a successful
push. CR-04 — `session_exercise` ops get no field validation and `applyBatch` has no error boundary,
so one bad foreign key throws out of the per-aggregate transaction, past the loop over the remaining
aggregates, and out to a NestJS 500, which `classifyAuthOutcome` reads as `offline`, which makes
PowerSync resend the identical poisoned batch forever. CR-03 supplies the ammunition: 9 of 12
`SYNCED_TABLES` have no apply path, so their ops are the rejections CR-01 is blind to.

Output: a client that distinguishes "the server refused this" from "the network was down", a server
that turns a poisoned aggregate into data instead of a 500, and an explicit, tested contract for
which tables the push path actually applies.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → `POST /v1/sync/push` | Untrusted op payloads reach validation, then the database |
| Server response → client outbox decision | The response body now decides whether a durable local write is destroyed |
| Database driver → `applyBatch` | Constraint violations surface as thrown errors inside a request |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-40 | Denial of Service | `applyBatch` poison-pill retry loop | high | mitigate | Per-aggregate try/catch converts a database error into `rejected` entries; terminal rejections complete the transaction so the identical batch is not resent forever; both halves asserted in `poison-pill.e2e-spec.ts` and `offline-write.test.ts` |
| T-02-41 | Tampering | Silent loss of a rejected write | high | mitigate | `uploadData` parses the response body and only completes on an empty or all-terminal rejected array; an unparseable body leaves the transaction queued |
| T-02-42 | Information Disclosure | Caught database error text in the push response | medium | mitigate | The caught error is logged server-side with the aggregate root and op ids; the response body carries only the existing `SyncRejectionReason` enum value |
| T-02-43 | Denial of Service | Unbounded `rejectedOps` growth on the client | medium | mitigate | `recordRejectedOps` keeps a capped in-memory list, dropping oldest |
| T-02-44 | Spoofing | Ownership decisions during the new validation path | low | accept | `session_exercise` validation runs ahead of, and does not alter, the existing per-aggregate ownership resolution that `concurrent-edit.e2e-spec.ts` covers |
</threat_model>
