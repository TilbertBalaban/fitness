<objective>
**As a** person who logs sets on my phone and reviews them in the browser, **I want to** see the same
workout in both places without pressing anything, **so that** the two devices are one training log.

This is the last unproven layer in the phase, and the only one gated on something outside the repository.
Everything before it works with no sync service at all: local writes, the crud queue, and the drain through
this project's own push endpoint are all self-contained, which is exactly why they were sequenced first.
Pull is different. A second device learns about the first device's writes through the PowerSync Service
reading Postgres logical replication, and that service has to be running somewhere.

Task 1 puts that choice in front of the developer rather than assuming it, because both viable options cost
something real. Self-hosting means installing a container runtime on this machine, which currently has
none. PowerSync Cloud's free tier means creating an account and exposing the local Postgres to the internet
so the hosted service can replicate from it, and free-tier instances deprovision after a week idle.
Deferring is also legitimate: PLAT-04's merge semantics are already proven at the protocol level by plan
02-03's two-device test, so what is actually missing without this plan is the transport, not the
correctness.

Purpose: PLAT-03's cross-device half and PLAT-04's transport half.
Output: two devices that converge on their own.
</objective>

    Follow the option Task 1 selected.

    On the self-hosted path: install a container runtime through Homebrew, add a `powersync` service to
    `docker-compose.dev.yml` beside the existing Postgres and Mailpit entries, and configure it from
    `ops/powersync/powersync.yaml` with Postgres as its own bucket storage backend — the second database
    engine `STACK.md` warned about is no longer required. Reconfigure the local Postgres for logical
    replication and create a dedicated replication role for the service; do it with `psql` and
    `brew services`, not by hand-editing files the developer will have to remember. On the cloud path:
    the instance itself is `user_setup`, and this task's work is the configuration and the token endpoint.

    `ops/powersync/sync-rules.yaml` defines one bucket per user, selecting from each table in
    `SYNCED_TABLES` by the token subject's user id. Every bucket's selection is filtered by `user_id` —
    there is no global bucket and no unfiltered table, because a sync rule that forgets its filter streams
    another account's training history to a device and no client-side check would catch it. For
    `logged_set` and `session_exercise`, which carry no `user_id` of their own, partition through their
    owning `workout_session`. `muscle_group` and `exercise_muscle_mapping` are not in any bucket: they are
    catalog content delivered by the first-install download D-01 reserves, not per-user synced data.

    `apps/api/src/sync/powersync-token.ts` exports `SYNC_TOKEN_TTL_SECONDS` — five minutes — and
    `mintSyncToken(userId)`, returning a JWT whose subject is that user id, signed with
    `POWERSYNC_JWT_SECRET` and with an audience the service is configured to accept. Throw at startup if
    the secret is unset rather than minting an unsigned token: a service that accepts an unsigned token is
    a service that will stream any account's data to anyone who asks. Keep the lifetime short — the client
    re-requests through `fetchCredentials` whenever the service says the token expired, so a long lifetime
    buys nothing and widens the window on a leaked token.

    Add a `@Get('token')` handler to the existing `SyncController` returning
    `{ token, endpoint }`, where `endpoint` is `POWERSYNC_URL`. It reads the user id from the
    authenticated session only. Do not accept a user id as a parameter, a header or a body field — a
    token endpoint that mints for whoever is named in the request is the whole attack.

    Add `POWERSYNC_URL`, `POWERSYNC_JWT_SECRET` and `EXPO_PUBLIC_POWERSYNC_URL` to `.env.example` with the
    same explanatory comment style the existing entries use, including that the public variable must be an
    origin both a browser and a device can reach.

    Write the token suite as a failing test first, one case per behaviour line, using the existing spawn
    harness and the sign-up-then-sign-in flow for two distinct users.

    `disconnect()` on sign-out. Local writes still never wait on any of this: with the service unreachable,

    1. Start the stack: the API (`pnpm --filter api dev`), the sync service, and the web client

    2. Open the web app in a normal browser window and in a second, separate profile or private window.
       Sign into the same account in both. Both are now the two devices.
    3. In window A, start a workout and log three sets. Within a few seconds, without reloading or clicking

    4. In window B, change the weight on the second set. Window A should show the new weight, again without

       existing workout, and still let you log a set. It should not hang, and it should not warn you about
       anything you cannot act on.
