<objective>
Make a bodyweight set survive the trip from the phone to Postgres as what it actually is: a set with
no external load, not a set of zero kilograms.

**As a** lifter doing pull-ups, **I want to** log my sets without inventing a weight, **so that** my
volume and PR history stay truthful instead of counting a phantom zero-kilogram lift.

Purpose: `02-REVIEW.md` CR-02 traced the null weight end to end and found it corrupted on every path.
On insert, PowerSync's `CrudEntry` contract omits null columns from `opData`, so the server sees an
absent field and the weight mapping's zero-string fallback turns it into `0.000` in a `NOT NULL`
column. On update, the validator runs a non-negative-decimal check against an explicit null, which
fails, and the whole op is rejected. WINDOWS #20 records the coercion and WINDOWS #21 records the
still-`NOT NULL` Postgres column; closing this needs both halves plus a schema push, because build
and typecheck pass without the push — the types come from the schema file, not the live database —
which is precisely how this reaches verification looking green.

Output: a nullable column, a mapping and validator that tell absent, null and zero apart, and an
end-to-end suite that proves it against real Postgres.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Relaxing logged_set.weight_kg to nullable is a one-way door</name>
  <decision>Drop the `NOT NULL` constraint on Postgres `logged_set.weight_kg`, or keep it and close CR-02 a different way.</decision>
  <context>
Relaxing a `NOT NULL` constraint is trivially easy in one direction and effectively irreversible in
the other. The moment real bodyweight sets exist with a NULL weight, re-adding `NOT NULL` requires
deciding what value those historical rows take — and there is no correct answer, because the whole
point of the change is that no number is the right stand-in for "no external load". Reversibility
rating: **one-way**.

The mobile SQLite mirror was already relaxed in plan 02-04 (`apps/mobile/lib/db/schema.ts` declares
`weight_kg` nullable with an explicit comment that a bodyweight exercise carries no external load),
and `packages/api-contracts/src/units.ts` `toCanonicalKg` already returns null for an absent weight,
and `formatWeight` already renders null as an em dash specifically because "zero would read as a
logged weight of zero". So Postgres is the last holdout, and every other layer already committed to
this shape.

The alternative is real but worse: keep `NOT NULL` and encode "no external load" as a sentinel — a
separate boolean column, or a magic negative value. That trades an irreversible constraint change for
a permanently ambiguous data model, and it contradicts three layers that already decided otherwise.
  </context>
  <options>
    <option id="drop-not-null">
      <name>Drop `NOT NULL` on `logged_set.weight_kg`, keeping `numeric(8,3)`</name>
      <pros>Matches the local SQLite schema, the units contract and the display layer, all of which already treat null as the representation of no external load. A genuine zero stays expressible and distinct.</pros>
      <cons>Irreversible in practice once bodyweight sets exist. Every read path that assumes a non-null decimal must be checked.</cons>
    </option>
    <option id="keep-not-null">
      <name>Keep `NOT NULL` and introduce a separate marker for "no external load"</name>
      <pros>No irreversible constraint change; existing read paths keep a guaranteed decimal.</pros>
      <cons>Two columns now encode one fact and can disagree. Contradicts the mobile schema, `toCanonicalKg` and `formatWeight`, all of which would need reworking. CR-02's corruption is not actually closed until every one of those is changed too.</cons>
    </option>
  </options>

  <behavior>
    - PUT a `logged_set` with `weight_kg` absent from `data` → Postgres stores SQL NULL; a read returns null.
    - PUT a `logged_set` with `weight_kg` of `'0'` → Postgres stores `0.000`; a read returns a zero decimal, not null.
    - Both of the above in one batch → both apply, and reading them back yields one null and one zero, still distinct.
    - PATCH a `logged_set` with `weight_kg` explicitly `null` → the op appears in `applied`, not in `rejected`, and the stored weight becomes NULL.
    - PATCH a `logged_set` changing only `reps`, with `weight_kg` absent → the previously stored weight is byte-identical afterwards.
    - PUT with `weight_kg` of `'-5'` → rejected `invalid_field`.
    - PUT with `weight_kg` of `'abc'` → rejected `invalid_field`.
    - A conflict-logged overwrite where the incoming weight is null → `sync_conflict_log` records a JSON null for that field.
  </behavior>
  <action>
Drop `.notNull()` from `loggedSet.weightKg` in `apps/api/src/db/schema/session.ts`, leaving
`numeric('weight_kg', { precision: 8, scale: 3 })`. Do not change precision, scale, or any other
column.

In `sync.service.ts`, change the weight mapping inside `toLoggedSetValues` so it produces `null`
when `d.weight_kg` is either absent or explicitly null, and `String(d.weight_kg)` otherwise. The
current zero-string fallback must be gone entirely — an absent weight means the lifter recorded no
external load, which under PowerSync's `CrudEntry` PUT contract is exactly how an absent value
arrives, since a PUT omits null columns from `opData`. Widen the declared return type of
`toLoggedSetValues` so `weightKg` is `string | null`, and let the resulting type error at the insert
and `onConflictDoUpdate` call sites guide you to every site that assumed a non-null decimal.

Add `isNonNegativeDecimalOrNull` beside the existing `isNonNegativeDecimal` and use it for the
`weight_kg` field only, inside `hasInvalidField`'s `logged_set` branch. Leave `reps` and `set_index`
on the existing non-null integer check — those columns stay non-nullable and an explicit null for
either must keep failing. Do not relax `isNonNegativeDecimal` itself; a second caller would inherit
the widened rule silently.

Prevent a partial edit from clobbering the weight: for an op whose `op` is `PATCH` and whose `data`
does not carry a `weight_kg` key at all, omit `weightKg` from the object handed to
`onConflictDoUpdate`'s `set`, so an edit that only changes reps leaves the stored weight untouched.
Use a `weight_kg` key-presence check on the raw `data` object, not a truthiness or undefined check on
the mapped value — absent and explicitly-null must stay distinguishable at this point, and a
truthiness check would also swallow a legitimate zero.

Fix the conflict-log value construction in the same file: the `winningValue` weight currently
stringifies whatever arrives, which turns an explicit null into the four-character spelling of null,
and `losingValue` reads `stored.weightKg` through a type that no longer matches the column. Type both
as `string | null` and pass a real null through rather than a stringified one.

Author `apps/api/test/null-weight.e2e-spec.ts` covering every line of the behavior block above,
following `sync-push.e2e-spec.ts`'s harness exactly: spawn the built API on a free port, create a
throwaway account with a runtime-generated email, push through `POST /v1/sync/push`, and assert the
stored value by querying Postgres directly through the `pg` client so the assertion sees the column,
not an API projection. Never hardcode a credential; reuse the existing `PASSWORD` constant pattern
and `freshEmail` helper.

Do not run the schema push in this task — Task 3 owns it, and the suite will fail against the live
database until it runs. That failure is expected and is the point: it is what proves the push is
load-bearing rather than decorative.
