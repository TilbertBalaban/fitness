<objective>
**As a** person who logged sets on my phone and then corrected one in the browser, **I want to** end up
with a correct workout and no set quietly missing, **so that** I can trust the log enough to train from it.

`02-CONTEXT.md` names this the one place two of the project's own research documents disagree.
`ARCHITECTURE.md` §3 prescribes row-level, sequence-keyed last-write-wins and rejects anything fancier.
`PITFALLS.md` §1 warns that last-write-wins silently destroys logged sets. `02-RESEARCH.md` Decision 2
reconciles them, and this plan implements that reconciliation:

- Two *different* sets never collide at all. Each has its own client UUID row, so both apply. This is most
  of the real-world case and needs no conflict logic whatsoever.
- The *same* completed set edited on both devices is rare and is resolved by row-level last-write-wins on
  the server-assigned sequence — **and** writes a durable `sync_conflict_log` row holding the value that
  lost. That is the difference between "no logged set silently lost" being a hope and being a structural
  property: nothing is destroyed without a recoverable trace, and no CRDT machinery is needed to get there
  (D-07 still holds).
- Session and preference metadata get plain last-write-wins with no log. `PITFALLS.md` §1 explicitly
  accepts that granularity for low-stakes fields, and logging every preference flip would drown the signal
  that matters.

This plan also settles deletes, which neither research document covered, and it does so by deviating from
`02-RESEARCH.md` Decision 3 in one specific way — see Task 3's reasoning.

Purpose: PLAT-04 and roadmap success criterion 2.
Output: a merge rule with a paper trail, and the automated two-device test that proves it.
</objective>

  <action>
    This task deliberately departs from `02-RESEARCH.md` Decision 3 on one point, and the reasoning belongs
    in the code review as much as here. Decision 3 argues that PowerSync's own delete operation is the
    tombstone, so a hand-rolled tombstone table would duplicate a guarantee the sync protocol already
    provides — and for the *pull* direction that is right: a device that already holds a row learns of its
    removal through the same ordered mechanism it learns of any other change. But the resurrection case in
    `02-CONTEXT.md` is a *push*-side race that PowerSync never sees: device B edited the row while offline,
    device A deleted it, A's delete lands first, and B's queued write then arrives at our own push endpoint
    and recreates the row. PowerSync is not in that path — our `SyncModule` is. So the tombstone is not
    duplicating the protocol; it is covering the one direction the protocol does not own. `02-RESEARCH.md`
    flags this claim as its thinnest (assumption A2) and asks for exactly this test.

    On a DELETE op: verify ownership, delete the row, and call `recordTombstone(tx, { userId, table, rowId, deletedServerSeq })`
    inside the same transaction. Make it idempotent — a second delete of the same id succeeds and does not
    add a second tombstone row.

    Before applying any PUT or PATCH, call `isTombstoned(tx, table, rowId, userId)`; when it returns true,
    reject that op with `deleted` and do not write. Scope the lookup by user, so one account's tombstone
    can never suppress another account's row with a coincidentally equal id.

    A DELETE for a `workout_session` must take its whole aggregate with it inside one transaction. The
    foreign keys already cascade at the database level, but write the tombstones for the removed children
    explicitly rather than relying on the cascade alone — a child with no tombstone is a child that a
    still-offline device can push back into existence, which is the same hole one level down.

    Do not add delete handling for `exercise` or `routine`. Those carry `archived_at` and are never
    hard-deleted, because archiving one must leave its past logged sets intact and correctly attributed.
    An op attempting to delete either is rejected `invalid_field`.

    Append these cases to `concurrent-edit.e2e-spec.ts` rather than starting a new suite — they are the same
    scenario family and share its fixtures.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| B1: client → NestJS API | Delete ops and edit ops both arrive as client-controlled JSON and both can target any id the client names |
| B2: NestJS → Postgres | The overwrite and its audit row must commit or roll back together |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-08 | Repudiation | overwrite of a completed set | medium | mitigate | Every value-changing overwrite of a completed `logged_set` writes a `sync_conflict_log` row inside the same transaction as the overwrite, so a destroyed value is always recoverable and an overwrite is always attributable to a server sequence. |
| T-02-14 | Tampering | delete of another user's row | high | mitigate | A DELETE op re-verifies ownership before removing anything, exactly as an UPDATE does; an e2e case asserts a cross-user delete is rejected and the row survives. |
| T-02-15 | Denial of Service | tombstone poisoning across accounts | medium | mitigate | `isTombstoned` is scoped by `user_id`, so one account cannot suppress another account's row by tombstoning a colliding id. An e2e case covers it. |
| T-02-02 | Tampering | client-supplied ordering | high | mitigate | `resolveConflict` reads no timestamp from either side; ordering is the server-assigned sequence assigned at arrival. Asserted by a source-level gate as well as by the reversed-order e2e case. |
| T-02-16 | Information Disclosure | conflict log contents | low | accept | The log holds the user's own training values and is scoped by `user_id` with no read surface in this phase. Accepting is appropriate at ASVS L1 because no endpoint exposes it yet; a future recovery UI must scope its read by session user. |
