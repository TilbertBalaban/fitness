<objective>
**As a** person two years into training with this app, **I want to** open it and see my history without
waiting, **so that** the app stays usable exactly as it becomes valuable.

`PITFALLS.md` §2 names the failure: a sync engine tested against a handful of hand-entered workouts, which
first shows problems past a few thousand logged sets — roughly six to twelve months of real training. That
is not an edge case; it is where every user of this app ends up, including its author. Roadmap criterion 3
asks for one to two years, and `02-CONTEXT.md` asks for the budget to be assertions in the suite rather
than prose in a summary.

The corpus also does something the other plans cannot: it is the only thing in this phase that exercises
the model against realistic data. A schema that looks fine against three hand-typed sets is where
`PITFALLS.md` §9 lives — so the generator spans every load type and set type the schema can express, and if
one of them cannot be represented, that is a finding about the schema, not about the generator.

Purpose: roadmap criterion 3, and the guard against `PITFALLS.md` §13's N+1 queries on nested workout data.
Output: a realistic dataset, and numbers that fail when they get worse.
</objective>

## Flagged assumptions

`02-RESEARCH.md` assumption **A1** is load-bearing in this plan and is not resolved. The corpus shape
(eighteen months, about four sessions a week, about fifteen sets a session, roughly 4,650 logged sets) and
the latency targets below are the researcher's reasoned starting point, tagged `[ASSUMED]`, not measured
against a competitor or against real usage:

| Metric | Proposed target |
|---|---|
| Push of a full session's batch against the seeded corpus | under 2 seconds |
| Full read of the corpus for one user | under 5 seconds |
| Push of a single set | under 500 milliseconds round trip |
| Queries issued to read one session with its exercises and sets | at most 3, independent of set count |

`02-CONTEXT.md` delegated every open call in this phase to the planner, so these are adopted rather than
escalated to a checkpoint. They live in one exported constant so changing them is a one-line edit, and the
query-count ceiling is the one that matters most — it is a structural property rather than a machine-speed
measurement, so it will not go flaky on a different machine.

    `apps/api/src/seed/corpus-shape.ts` holds the numbers and nothing else: `CORPUS_SHAPE` with the span in
    months, sessions per week, exercises per session, sets per exercise and the fixed random seed; and
    `PERF_BUDGET` with the four targets from the table above. Both the generator and the assertion suite
    import from here, so a change to the corpus cannot silently invalidate the budget it is measured
    against.

    `apps/api/src/seed/generate-corpus.ts` is a standalone script, not a Nest provider. Repeat the dotenv
    bootstrap from `drizzle.module.ts` — a script run through `ts-node` outside Nest's bootstrap does not
    get the environment loaded for it. Add `"seed:corpus": "ts-node src/seed/generate-corpus.ts"` to
    `apps/api/package.json`.

    The generator is deterministic. Use a seeded pseudo-random generator, so the same seed produces the
    same corpus on every machine and a latency change is a real regression rather than a different dataset;
    the platform's built-in unseeded random source must not appear anywhere in this file, in code or in a
    rationale note. Do not add a faker dependency for this: the values needed are weights, reps,
    RIR, dates and a few dozen exercise names, and a small seeded generator in this file is less surface
    than a package.

    Realism is what makes the corpus worth having. Generate a routine with three or four days, then walk
    eighteen months of calendar forward at roughly four sessions a week, skipping the occasional week the
    way a real trainee does. Each session snapshots its prescription onto its `session_exercise` rows and
    logs sets that drift against it — most sessions near the target, some short, some over. Progress the
    working weights slowly across the span so trend queries have something real to read. Vary the shapes
    deliberately: at least one exercise of every `load_type` the schema declares — external weight,
    bodyweight, bodyweight plus added load, assisted, time-based, distance-based — and at least one
    instance of every `set_type` including warm-ups, drop-set chains linked by `parent_set_id`, and
    unilateral sets carrying a `side`. Include one session that crosses midnight, so the corpus itself
    contains the LOG-22 case. If any of these cannot be represented in the schema, stop and report it: that
    is `PITFALLS.md` §9 surfacing, and it is worth more than a seeded database.

    Write the corpus through `SyncService.applyBatch` in batches sized under `SYNC_MAX_BATCH_OPS`, not
    through direct Drizzle inserts. Data that entered by a path the app never uses proves nothing about the
    path the app does use, and going through the ingress means the generated rows passed the same
    ownership and validation checks real data does. It also means the generator's own runtime is a first
    measurement of push throughput.

    Weights come from `toCanonicalKg` so they are exact decimals. A corpus of floats would make the
    drift assertions in plan 02-04 meaningless the moment anything aggregated it.

    Guard the destination. The script takes the target user's email as an argument, refuses to run when
    `DATABASE_URL` is not a localhost or explicitly-named development database, and refuses to run when the
    target account already has workout sessions unless a `--reset` flag is passed. A seed script that can
    quietly write thousands of fabricated workouts into a real account is a footgun, and this one will be
    run repeatedly by someone who also uses this app to train.
  </action>

    Write the failing assertions first, one per behaviour line, then make them pass — including by fixing
    the read path if the query count is over the ceiling, because that is the finding this suite exists to
    produce.

    Seed the corpus in the suite's setup by invoking the Task 1 generator, so the fixture is real and
    reproducible rather than a fixture file that drifts from the generator. Give it its own account so it
    cannot collide with the other e2e suites' users.

    and assert against `PERF_BUDGET`'s ceiling. Then assert the same count holds for a session with three
    sets and one with thirty. That second assertion is the one that actually catches an N+1: a fixed
    ceiling can be satisfied by a fast-but-linear implementation on a small fixture, while an invariant
    count as the child rows grow cannot.

    Measure latency with `process.hrtime.bigint()` around the operation, warming the connection with one
    discarded call first so a cold pool does not count as a regression. Latency assertions run on whatever
    machine happens to be executing them, so keep them as the loose outer guard and let the query-count
    invariant be the strict one — that is the assertion that is genuinely portable.

    Make a missing corpus a failure, never a skip. A perf suite that skips itself when its fixture is
    absent reports green while asserting nothing, which is exactly what the suite-integrity reporter exists

    fast, it is broken, and the seeded corpus is the first dataset in this project large enough for that
