<objective>
**As a** person training with no signal, **I want to** start a workout on my phone and have it reach my
account by itself once I am back on the network, **so that** I never have to think about whether my
training log made it off the device.

This is the phase's tracer. It wires one row — a `workout_session` — through every layer this phase will
touch: local SQLite under PowerSync, the crud queue, the backend connector, the existing `apiFetch`
request path, a NestJS `SyncModule`, a Drizzle transaction, and Postgres. One path only. No batching, no
child rows, no pull, no conflict policy. Everything else in Phase 2 expands outward from this slice.

Leading with it is deliberate. `02-RESEARCH.md` flags PowerSync's React Native **Web** support as beta,
needing non-standard Metro configuration and manually placed worker assets — and this machine has no Xcode
and no Android SDK, so web is the only target that can be run at all. If that leg does not work, we learn
it here, after one commit, rather than after ten layers already depend on it. The fallback is WatermelonDB,
which `STACK.md` already documents, and Task 1 is where that door is opened deliberately rather than by
default.

Purpose: PLAT-02 and PLAT-03, and the architectural go/no-go for every plan after this one.
Output: a workout started offline, arriving in Postgres with the id the client gave it.
</objective>

## Flagged assumptions (probe-surfaced, unresolved)

The deterministic edge probe classified **PLAT-03** as `unclassified` and left it `unresolved`. An
unclassified row is never auto-resolved, so it is surfaced here rather than dropped:

> **PLAT-03 — "User's offline changes sync automatically once connectivity returns, without any manual
> sync action."** The probe could not assign an edge category, so no boundary, ordering, or precision
> predicate was derived automatically. The planner's reading is that its real edge axis is **trigger and
> retry**, not data shape: what counts as "connectivity returns" (D-09 answers: the existing
> transport-failure branch, not a new connectivity concept), and what happens when a drain is already in
> flight when the next trigger fires (PowerSync serialises crud transactions; the connector never starts a
> second drain concurrently, because `getNextCrudTransaction` hands out one transaction at a time and the
> connector completes or abandons it before returning). **Assumption:** no additional unlisted edge exists
> on this requirement. If the developer disagrees, the place to add coverage is Task 3's behaviour block.

Two further assumptions this plan inherits and does not resolve:

- **Open question 1 from `02-RESEARCH.md`** — whether PowerSync web works cleanly against this exact Expo
  SDK 57 / RN Web combination is genuinely unknown. Task 3's `expo export --platform web` gate is the test.
- **Open question 2 from `02-RESEARCH.md`** — whether `@op-engineering/op-sqlite` supports React Native's
  New Architecture cannot be verified on this machine at all (no Xcode, no Android SDK). It is installed
  because `@powersync/react-native` requires it as a peer, and it is **not** exercised at runtime by
  anything in this phase. Record it in `.planning/WINDOWS.md` as an unrun-verify item, following the
  precedent Phase 1 set for its own native gaps.

    `apps/api/src/sync/sync.controller.ts` declares `@Controller('sync')` without `@AllowAnonymous()`, so it
    participates in `/v1` versioning and the existing global `MinClientVersionGuard`. It exposes one
    `@Post('push')` handler typed `SyncPushRequest -> Promise<SyncPushResponse>` that reads the
    authenticated user id from the request's session and delegates to `SyncService.applyBatch(userId, batch)`.
    The controller does no validation of its own beyond the batch-size ceiling.

    `apps/api/src/sync/sync.service.ts` injects `DRIZZLE`. `applyBatch` resolves the owning user **from the
    authenticated session only** and ignores any `user_id` present in an op's `data` — a client-supplied
    ownership field is never trusted, on insert or on update. It rejects ops whose `type` is not in
    `SYNCED_TABLES`, then applies the batch inside a single `db.transaction`, one op at a time, using an
    upsert keyed on the client UUID so a replayed op yields one row rather than a duplicate-key error. For
    a `PUT` or `PATCH` against an id that already exists, it re-reads the row's `user_id` inside the same
    transaction and rejects with `not_owner` if it does not match; an already-accepted id is not treated as
    already-owned. It assigns `server_seq` from the `sync_seq` sequence on every applied op and returns the
    highest value assigned. A rejection is reported per op in the response rather than failing the whole
    batch, except `batch_too_large`, which rejects the request whole so a client cannot half-apply an
    oversized push.
