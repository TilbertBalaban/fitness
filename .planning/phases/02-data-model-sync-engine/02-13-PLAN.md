<objective>
Close the PATCH-clobber defect: make the sync apply path write only the columns a PATCH actually
named, on all three tables the push leg applies, instead of writing a fully-defaulted row every time.

**As a** lifter who edits one field of a set, or taps "finish workout", **I want to** change only what
I touched, **so that** the app never quietly rewrites the rest of the record — the start time, the
day the workout belongs to, how many reps I actually did — behind my back.

Purpose: `02-VERIFICATION.md`'s single remaining gap, and `02-REVIEW.md`'s CR-01. `toLoggedSetValues`,
`toSessionExerciseValues` and `toWorkoutSessionValues` compute every column with a `??` default, and
`onConflictDoUpdate` writes that whole object on every op. The only guard that exists,
`loggedSetUpdateSet`, strips exactly one column (`weightKg`) on exactly one table. Every other column
on `logged_set`, and every column on `workout_session` and `session_exercise`, is reset the instant a
PATCH omits it. A realistic `{status, ended_at}` finish-workout PATCH would reset `started_at` to the
PATCH's receive time, `local_date` to the wrong calendar day, `timezone` to `UTC`, and
`device_id`/`routine_day_id`/`equipment_profile_id` to null — a direct hit on **LOG-22**, one of this
phase's own requirements, and on roadmap criterion 2's words ("no logged set silently lost").

This is not speculative. It already fires inside a passing test: `null-weight.e2e-spec.ts`'s
reps-only PATCH case resets the seeded row's `set_index` to 0 and `completed` to false right now, and
the test never looks. No shipped client emits such a PATCH (`log-set.ts` only inserts), so nothing in
the app as delivered is broken today — but PATCH is a first-class `SyncCrudOpType` on the public
`POST /v1/sync/push` endpoint for all three `PUSH_APPLIED_TABLES`, and it is the exact shape the next
edit-a-set or finish-a-workout screen will send.

Output: one field-presence-aware update-set builder shared by all three tables, kept exhaustive by
the type system, proven by a real-Postgres suite that is committed red and turns green on the fix.

**Shape note (no tracer task).** This phase's tracer shipped in 02-01 and again in 02-09; the
architecture is proven and in production use. This is a scoped correction to the `set:` clause of one
service, so the plan is expansion-only. Task ordering is red-then-green rather than
implementation-then-test, because the verification report's own requirement is that the new coverage
**fail before the fix and pass after** — a committed reproducer is the artifact that proves it.
</objective>
