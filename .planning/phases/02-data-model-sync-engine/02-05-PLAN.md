<objective>
**As a** person whose phone died in the middle of a workout, **I want to** reopen the app and find every
set I had logged, **so that** a crash costs me nothing.

Two guarantees are proven here, and both are the kind that everyone believes is true until the day it is
not.

The first is PLAT-07: a set is durable the instant it is logged, not when the workout is finished. Plan
02-02 made `logSet` write immediately for exactly this reason; this plan is where that becomes an
assertion.

The second is roadmap criterion 4, re-scoped by `02-RESEARCH.md` Decision 5. That criterion was written
assuming a hand-rolled local database with versioned SQL migrations. Under PowerSync the client schema is
applied as SQLite views re-derived on every boot, so there is no migration runner to test — and writing one
would be spending real effort on machinery the protocol makes unnecessary while leaving the thing that
genuinely is at risk untested. What is at risk is the crud queue: the durable record of writes that have
not been pushed yet. If redefining the client schema across an app update loses queued writes, a person who
updated the app on the train after training offline has lost that workout. That is what this plan tests,
against a database populated *before* the change.

A note on the test vehicle, because it is the hard part. This machine has no Xcode and no Android SDK, so
the web target is the only one that can run at all. These suites must open a real PowerSync database — a
durability test against a mock proves nothing at all, and it is better to halt and say so than to ship a
green that means nothing.

Purpose: PLAT-07, the durability half of PLAT-02, and roadmap criterion 4.
Output: two suites that fail if a write can go missing.
</objective>

## Flagged assumptions

One truth in this plan is authored as a **backstop**, and it will still be unverified when this plan ends.
Named verbatim, so the gap is not paraphrased away later:

> "A set whose write had not committed when the process died is absent entirely, and one that had
> committed is present with every field populated — there is no half-written row."

**Why the suite cannot close it.** These tests run inside the Jest process that also owns the database, and
Jest offers no way to terminate that process at an arbitrary instruction boundary — least of all part-way
through SQLite's own commit. What Task 1's last behaviour line actually exercises is a *graceful* close
landing between two writes: the completed writes come back, the interrupted one does not. That is the
recoverable case. Genuine crash consistency — no torn row after a kill mid-commit — is a property of
SQLite's journal/WAL recovery that this suite relies on rather than proves. The only honest way to close it
is a real device, a real force-quit and a human watching, and this machine has neither Xcode nor an Android
SDK.

**So the marker stays as written.** `verification: backstop` means an unconfirmed truth abstains to
`human_needed` at verify time instead of passing silently, which is the correct outcome here: do not
downgrade it to a plain truth on the strength of the close-and-reopen case, and do not delete it because
the suite is green. Task 1's summary must carry it forward by name with this reason attached, so the next
reader inherits a stated gap rather than rediscovering it.

  <action>
    The starting state has to be a *populated* database, not an empty one. Roadmap criterion 4 says so
    explicitly, and it is the whole difficulty: an empty database survives any schema change trivially, so a
    suite that starts empty is a suite that cannot fail. Seed a session with several sets and leave the
    writes unpushed so they are sitting in the crud queue, then close, redefine the schema, reopen, and
    assert against what is there.

    Build the changed schema by constructing a second `Schema` object from a modified copy of the local
    table definitions rather than by editing `apps/mobile/lib/db/schema.ts` — the suite has to hold both
    the before and after shapes at once, and editing the shared module would change the app's real schema
    to run a test.

    Cover three shapes of change, because they fail differently: an unchanged schema, which is the control
    and proves the vehicle can detect a difference at all; an added nullable column, which is the common
    real upgrade; and a removed column, which is the one people assume is safe. In every case assert the
    original rows are all still present, and assert the crud queue's depth and order are unchanged.

    Then push the surviving queue through `uploadData` with `apiFetch` doubled to return an `ok` outcome,
    and assert every pending operation is reported applied. Surviving the reopen is only half the guarantee
    — a queue that survives but can no longer be drained has still lost the workout.

    Do not write a `PRAGMA user_version` migration runner for the synced tables. PowerSync's client schema
    is re-derived as views on every boot, so there is nothing to migrate; building one would be effort spent
    on machinery the protocol makes unnecessary, and it is `02-RESEARCH.md`'s named anti-pattern for this
    phase. If a future change genuinely needs data transformed on the client, that is a distinct problem
    and a distinct plan.
