<objective>
**As a** lifter at a gym whose smallest dumbbell jump is 4 kg, **I want to** be told to grind out more reps
before I am asked to jump, **so that** the app's suggestions match my equipment instead of fighting it.

08-02 shipped the preference as data and UI; 08-04 finished the engine's decision rules. This plan closes
the loop between them: the engine gains its one branch on the preference, and the value travels from the
`user_preference` row through the workout screen's existing read into `recommendNextPrescription`. Until
this plan lands, the dial in Profile persists a value nothing reads — which is precisely the
tested-but-unwired shape this project has failed verification for twice, so this plan's acceptance criteria
name the call site rather than the function.

Purpose: make PRGR-04's setting actually change what the lifter is told.
Output: a single preference branch in the engine, and the wiring that feeds it.
</objective>

    - Under the widen-the-rep-range mode, a surplus performance logged at the top of the rep range raises the load and resets the rep target to the bottom of the range.

  <action>
1. **`packages/progression-engine/src/preference.ts`** — `ProgressionStep`, a small union saying what the
next prescription should change (advance the rep target at the same load, or raise the load and return to
the bottom of the range), and `resolveProgressionStep({ performance, prescription, preference })` returning
it. This is D-07's *only* branch point; do not scatter the condition through `recommend.ts`. Keep the
function free of inventory and snapping — it decides *what kind* of step to take, and `snap.ts` decides
what weight that step lands on.

The two modes differ only in when the load moves. Widening the rep range first walks the rep target up
through the range and moves the load only once the top is reached — textbook double progression, and the
gentler mode for a lifter whose plate inventory is coarse, which is why D-07 makes it the default.
Preferring to match the previous weight reaches for the same load again with the rep target advanced,
moving the load on the same ceiling condition. Both converge on the same guard: a load increase always
returns the rep target to the bottom of the range. Comment that guard once, where it is enforced, stating
that the pairing is what bounds the progression — an implementation that raised load while keeping the rep
target would ratchet without limit.

2. **`packages/progression-engine/src/result.ts`** — add `preference: ProgressionPreference` as a required
field on `RecommendInput`, imported from `@fitness/api-contracts` rather than retyped, and append
`range_widened` to `RecommendationBasis`. Making the field required rather than optional is deliberate: an
optional preference would let a caller silently get the default forever, which is exactly how a shipped
setting becomes a setting that does nothing.

3. Write `src/__tests__/preference.test.ts` covering every case in `<behavior>`, driving both modes across
the same prescriptions so the difference between them is visible in the test names.
