<objective>
**As a** lifter whose gym has 20 kg jumps between dumbbells, **I want to** tell the app to squeeze more reps
out of a weight before jumping up, **so that** its suggestions match how I actually train instead of forcing
a jump my equipment cannot soften.

This plan ships D-07 end to end as data and UI: the vocabulary, the column on both sides of the sync
boundary, the push validator, the getter/setter pair and the Profile dial. It deliberately stops short of
the engine reading it — `recommendNextPrescription` gains the preference branch in 08-05, once both this
plan and the engine's negative-case rules exist. Shipping the dial first means the value is already
present and already synced by the time the engine reads it, and it keeps this plan's files completely
disjoint from the tracer's so the two run in parallel.

Purpose: give PRGR-04 a real, persisted, synced, user-settable home before anything reads it.
Output: a two-value preference on `user_preference`, settable from Profile, defaulting to double
progression.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client PowerSync upload -> `sync.service.ts` `user_preference` branch | A push can carry any string in a `text` column. Every sibling closed-vocabulary column on this row (`weight_unit`) is already membership-checked here; an unchecked new one would be the odd column out. |
| local `user_preference` row -> `loadProgressionPreference` | A row synced from a future build, or corrupted locally, can hold a value this build does not know. |
| TypeScript schema -> live Postgres | The gap only a live-database read closes; a column present in one and absent from the other compiles cleanly. |
