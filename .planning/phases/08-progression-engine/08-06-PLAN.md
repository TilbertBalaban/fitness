<objective>
**As a** lifter who will one day have their history recomputed on a server, **I want to** know the server and my
phone agree about what I should lift, **so that** the number does not change depending on which device I
happened to open.

Success criterion 6 — "the same rule code runs on client and server, so a recommendation can never differ
between them" — is the kind of claim that rots silently. D-08 answers it the way this project answered
Phases 4 and 7: prove it, do not assert it. One fixture table, three runners, and a failing case in CI
rather than a surprise in a gym.

The pattern-mapper found **no precedent for this anywhere in this repository**: no file here is currently
imported by both an `apps/api` test and an `apps/mobile` test, and neither `@fitness/pr-rules` nor
`@fitness/plate-math` has ever been imported from `apps/api` at all, despite the architecture doc
describing both as both-sides packages. This plan invents that path rather than copying one, and it also
has to reconcile two different test-file naming conventions between the two apps.

It then closes PRGR-11 the way this repo's standard demands: a real browser, a real local database, the
context set offline, and a recommendation on screen. Not a mock, not an assertion that it would work.

Purpose: make the parity claim and the offline claim both executable.
Output: the phase's client/server parity proof and its end-to-end offline proof.
</objective>
