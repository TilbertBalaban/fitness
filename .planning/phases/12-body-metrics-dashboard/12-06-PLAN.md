<objective>
Let the user build a before-and-after from two of their own photos and get it out of the app —
shared on native, downloaded on web — without a byte ever reaching a server.

Purpose: BODY-05 is the visible payoff of BODY-04, and it is also the place where D-15's honesty
requirement bites hardest. A photo whose bytes live on another device cannot be composited here, and
the picker has to say so structurally rather than by failing after the user taps it (D-19/R28).

Output: the platform-split composite module, its pure layout helper, the three-step
`/photo-composite` screen, and a Playwright spec proving the web canvas path produces a real
downloadable artifact.

**Shared-seam ownership.** This plan is the wave-4 owner of `apps/mobile/app/__durability.web.tsx`
and `apps/mobile/playwright.config.ts`'s `durability` `testMatch` array. **Append only — never
rewrite, never reorder, never remove an existing entry.** It does not touch
`apps/mobile/lib/db/test-support.ts`: 12-03's `seedProgressPhoto` and `readProgressPhotosRaw` are
reused as-is. `apps/mobile/package.json` was last touched by 12-03 in wave 2.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device photo bytes -> rendered composite -> OS share sheet or browser download | Photo bytes leave the app's own storage into a user-initiated share or download. This is the only sanctioned exit and it is user-driven, never automatic. |
| stale deep link -> `/photo-composite` | A link may arrive on a device that holds fewer than two of the referenced photos' bytes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-25 | Information Disclosure | `composite.web.ts` / `composite.ts` output path | high | mitigate | Output goes only to a user-initiated OS share sheet or a user-initiated browser download; no network call exists in either sibling. Asserted by the negative-import criteria in Task 1 and by 12-03's standing prohibition that photo bytes never enter a request. |
| T-12-26 | Denial of Service | `/photo-composite` reached with insufficient on-device photos | medium | mitigate | `deriveCompositeScreenState` returns `not-enough-photos` and renders an explicable empty state rather than attempting a render against missing bytes. |
| T-12-27 | Tampering | photo uris passed into the canvas draw | medium | mitigate | Inputs come only from `getPhotoUri` over the app's own store, keyed by `storage_key` values that originate in `photoStorageKey`; no user-supplied uri reaches the draw call. |
| T-12-28 | Information Disclosure | EXIF/GPS metadata surviving into the shared artifact | low | accept | Both output paths re-encode through a canvas or a view snapshot, which does not carry the source EXIF block forward. Canon data-minimization concern — breadcrumbed to `/gsd-secure-phase` in 12-03's threat model rather than minted here. |

**Canon breadcrumb:** no bespoke prohibition is minted for this plan. The photo-bytes-never-leave
constraint is owned by 12-03's prohibition block and covers this surface's inputs; the only new exit
here is an explicitly user-initiated share, which is the feature.
</threat_model>
