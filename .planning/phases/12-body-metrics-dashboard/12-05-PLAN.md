<objective>
Turn the Home tab into a dashboard: a new synced `dashboard_widget` table end-to-end, a
forward-compatible dispatch host, the six-widget catalog built entirely from surfaces Phases 9 and 10
already shipped, and a first-run default that reproduces today's Home exactly.

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Confirm the one-way widget-layout storage shape (D-21)</name>
  <decision>
    Store dashboard layout as a new synced `dashboard_widget` table with one row per widget, rather
    than as a JSON array on an existing `user_preference` column.
  </decision>
  <context>
    D-21 is rated **one-way** in `12-CONTEXT.md`: once the table ships and
    `ops/powersync/sync-rules.yaml` carries its pull query, changing the storage shape is a Postgres
    migration plus a client schema change plus a sync-rules change plus a PowerSync Service restart —
    and the rows are already on devices.

    The project's standing rule points at the table. Phase 11's D-10 (`excluded_exercise`) and
    `user_preference.active_routine_id` both chose a row or a column over a packed list for the same
    reason: under row-level LWW a multi-value list packed into one column loses concurrent offline
    edits wholesale, and reordering is precisely the edit two devices are most likely to make
    independently. A JSON array would mean the last device to sync wins the entire layout.

    The cost of the table is real and worth naming: a new Postgres table, a new client table, a new
    sync-rules query, seven more registration points in `sync.service.ts`, and a PowerSync Service
    restart that this environment cannot verify (deferred to ROADMAP Phase 999.1).
  </context>
  <options>
    <option id="row-per-widget">
      <name>New `dashboard_widget` table, one row per widget (recommended, D-21 as written)</name>
      <pros>Concurrent offline reorders and toggles converge per-row instead of clobbering the whole
      layout; identical in shape to `excluded_exercise`, `personal_record` and `equipment_profile`, so
      it introduces no new resolution class; `position` reuses the existing `order-index.ts`
      arithmetic unchanged.</pros>
      <cons>A migration, a sync-rule change and a service restart; three more tables' worth of
      registration boilerplate; the restart is unverifiable in this environment.</cons>
    </option>
    <option id="json-on-preference">
      <name>A JSON array column on `user_preference`</name>
      <pros>No new table, no sync-rule change, no service restart, no registration boilerplate;
      `user_preference` already syncs both ways.</pros>
      <cons>Directly contradicts the project's standing row-per-item rule; two devices reordering
      offline produce a whole-column LWW where one user's entire layout silently disappears; the
      failure is invisible until it happens and unrecoverable when it does.</cons>
    </option>
  </options>
  <resume-signal>Select: row-per-widget, json-on-preference, or describe an alternative</resume-signal>
</task>
