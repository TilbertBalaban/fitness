<objective>
Let the user shape the dashboard: add a widget, remove one, drag them into the order they want, and
end up with nothing if that is what they want.

Purpose: DASH-02 is why `dashboard_widget` is a table rather than a JSON column. Reordering is
precisely the edit two devices make independently offline, and a row-per-widget shape is what lets
those converge. This plan also proves the picker in a real browser against a real `@powersync/web`
database, which is the only way the drag interaction and the position arithmetic are jointly
falsifiable.

Output: `DashboardWidgetPicker`, the add/remove/move write helpers built on the existing order-index
arithmetic, the picker mounted on Home's `Edit` control, and a Playwright spec covering all three
operations.

**Shared-seam ownership.** This plan is the wave-5 owner of the three append-only shared seams:
`apps/mobile/app/__durability.web.tsx`, `apps/mobile/lib/db/test-support.ts` and
`apps/mobile/playwright.config.ts`'s `durability` `testMatch` array. **Append only — never rewrite,
never reorder, never remove an existing entry.** `apps/mobile/app/(tabs)/index.tsx` was restructured
by 12-05 in wave 3 and is extended here by mounting the picker on the `pickerOpen` flag 12-05 already
holds; 12-08 mounts the quick-action sheet on the sibling `quickActionsOpen` flag in wave 6.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| picker interaction -> `dashboard_widget` writes | Local writes that immediately enter the sync queue; each must be scoped to the authenticated user's own rows. |
| two offline devices -> row-level LWW | Concurrent independent reorders converge per row; the shape of the table is itself the mitigation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-29 | Tampering | `addWidget` / `removeWidget` / `moveWidget` | high | mitigate | Every read and write is scoped by `userId` as well as row id; a widget id the user does not own resolves to no sibling and writes nothing. 12-05's server-side ownership re-check rejects any push targeting a foreign row `not_owner`. |
| T-12-30 | Tampering | `addWidget` with an out-of-vocabulary kind | medium | mitigate | `addWidget` writes nothing for a kind outside `WIDGET_KINDS`; 12-05's `hasInvalidField` branch is the server-side backstop, and the host's filter-before-map means even a row that somehow arrived would be skipped rather than fatal. |
| T-12-31 | Denial of Service | interrupted renumber leaving duplicate positions | low | accept | `sortByOrderThenId` breaks ties by id, so a half-written renumber renders in a stable total order — the list is not the one the user dragged to, but nothing looks broken. This is the documented, accepted behavior `moveDay` already carries. |
| T-12-32 | Repudiation | concurrent offline reorders | low | accept | Row-level LWW ordered by server sequence resolves each widget's position independently; no widget is lost. This is the property D-21 chose the table shape for, and it is asserted as a `must_haves` truth rather than as a runnable test (two live devices are unavailable here — routed to ROADMAP Phase 999.1). |
</threat_model>
