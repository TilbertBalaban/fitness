## Screen decomposition (Claude's Discretion, recorded)

CONTEXT.md leaves the wizard's screen decomposition open. The decision taken here:

- **One route, `/programs/generate`, with an in-screen phase state** — `answering` then `previewing`
  — rather than two routes. A separate preview route would have to carry a whole
  `GeneratedProgramTree` across a navigation boundary, which on web means serialising it into a URL
  or holding it in a module-level singleton; both are worse than one screen holding it in state, and
  neither buys anything, since the preview is never deep-linked (it does not exist until Generate
  runs).
- **Steps within the answering phase are sections on one scrollable form, not paged steps.** There
  are seven inputs and five of them have defaults; paging them would turn a thirty-second task into
  seven screens. The step ORDER is still declared in `generation-wizard.ts` so the form's section
  order is data rather than JSX arrangement.
- **The routine name is edited in the preview phase, not the answering phase**, because its default
  is derived from the answers and a user should see the name they are about to save next to the
  program they are about to save.

**`WizardAnswers`** carries `trainingGoal`, `experienceLevel`, `daysPerWeek`, `sessionLengthMinutes`,

n of 4, four training cycles, empty emphasis, seed 0. Record in a comment that `auto` and

still gets a sensible program.

**`validateWizardAnswers(answers): WizardValidationError | null`** returns a token from a small
union — `goal-required`, `level-required`, `days-out-of-range`, `session-too-short`,
`session-too-long`, `cycles-out-of-range`, `split-unsupported`, `emphasis-unknown-group`,
`deload-interval-invalid` — plus a `fieldErrorMessage(error)` mapper, copying the
`validateCycle`/`cycleErrorMessage` shape from `apps/mobile/lib/db/programs/cycles.ts`. Bound every
numeric field against `GENERATION_INPUT_LIMITS` imported from the generator rather than retyped
literals, so the wizard and the runtime guard can never disagree. Check the split pair against
`resolveSplitTemplate`'s own result rather than against a copied matrix — the wizard asks the table,
it does not hold a second opinion about it.

**`buildGenerationInput(answers, context)`** where `context` carries the loaded
`GenerationCatalog`, the resolved `ResolvedInventory | null` and the `excludedExerciseIds` array.
It assembles a `GenerationInput` and nothing more — it performs no I/O and no validation of its own,
because `validateWizardAnswers` runs first and `isGenerationInput` runs last. Pass the emphasis map
through unchanged: a group the user never touched is absent, and absent means normal in
`applyEmphasis`; materialising nineteen explicit `normal` entries would make a later default change
invisible.

**`nextVariantSeed(seed: number): number`** is pure arithmetic on its argument — an increment, not a
random draw — so the Regenerate sequence from any starting seed is reproducible and a user who
regenerates three times and prefers the first result can get it back. Record that reason in a
comment.

**`defaultGeneratedRoutineName(goal, splitPreference)`** returns an editable human-readable label
combining the two, trimmed, never whitespace-only for any pair.

**`describeDegradation(entry: DegradationEntry): string`** returns one plain sentence per entry kind
naming the day or muscle group affected and what was reduced. Write the copy so it describes what
the app did and why, never what the user lacks — a day trimmed for time says the session length left
room for fewer exercises, not that the user does not train long enough.
