<objective>
**As a** lifter with a shoulder that will not tolerate overhead pressing, **I want to** record that
exclusion once against my account, **so that** no program generated on any of my devices ever
prescribes it.

This plan builds the server half of GEN-03: the `excluded_exercise` synced table, its registration
across every push and pull touchpoint, the schema push that makes it real in Postgres, and an
executed end-to-end proof that a second user cannot reach the first user's rows.

`excluded_exercise` is a strict subset of `user_exercise_preference`'s footprint — same
`id`/`user_id`/`exercise_id` columns, same single-TEXT-primary-key constraint, same unique index on
the pair, same singleton-aggregate-root treatment, same legitimate hard delete — with
`never_suggest` and `archived_at` dropped and a plain `created_at` in their place. Every file below
already contains the exact line to copy; nothing here is invented.

Deliberately NOT in this plan: the device-side SQLite mirror, the client read/write helper and the
exclusion UI (11-03), and the generator's own exclusion filter, which already exists and is unit
tested in 11-01 against a supplied id list. This plan makes those ids real and synced.

Purpose: give exclusions a durable, per-user, conflict-safe home before any UI writes to it.
Output: a synced table that round-trips a push and refuses a cross-user one.
</objective>

  <behavior>
    - A signed-in user pushing an `excluded_exercise` PUT whose payload claims a different `user_id` gets the row stored against their OWN user id; the claimed id appears nowhere in the stored row.
    - A push whose payload omits `exercise_id` is rejected with reason `invalid_field`, and no row exists for that op id afterwards.
