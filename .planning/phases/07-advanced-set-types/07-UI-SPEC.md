## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn is not applicable. Unchanged from Phases 1–6: React Native + React Native Web, shadcn/Radix cannot run inside a native `View`/`Text` tree. `components.json` correctly does not exist. |
| Component library | Hand-rolled RN components under `apps/mobile/components/`, extending the exact set Phases 1–6 shipped. This phase **extends in place**: `SetRow.tsx` (badge generalization, indentation, per-row remove control), `SessionActionSheet.tsx` (four new conditional action rows), `ExerciseStrip.tsx` (superset link badge), `ExercisePage.tsx` (superset partner chip). This phase **adds**: `SetTypePickerSheet` (the D-01 bottom sheet), `ChangeSetTypeDialog` (the D-09 destructive confirm, `ArchiveDialog`-shaped). No new component introduces a second visual language — every one styles itself against the same NativeWind token set. |
| Icon library | `@expo/vector-icons` (`Ionicons`), unchanged. Per Phase 1 D-06: an icon is used only where its color does not need to dynamically track theme state through a prop the icon library owns — `useThemeColors()`/the local `GLYPH_COLORS` pattern resolves the color and is passed as the `color` prop, never a NativeWind className on the icon itself. |
| Font | System default, unchanged — no `fontFamily` override exists or is introduced this phase. |

**Design decisions this document resolves that CONTEXT.md left open** (bounded, reversible, decided here per the established design system and D-01/D-02/D-04/D-05/D-06/D-07/D-08's fixed mechanics — not re-litigated with the user):

1. **The Set-Type Picker's exact anatomy and, critically, what each of the seven options actually does to the tapped row.** D-01 fixed "a bottom sheet, pick one, it closes"; it did not fix that three of the seven options (Drop Set, Partial, and by extension any grouping type) retype the row itself while two (Drop Set, Partial) instead add a sub-entry beneath an unchanged parent, per D-04's/D-07's own literal wording ("the parent typed `normal`", "the parent is the top set"). See **Set-Type Picker Sheet**.
2. **The generalized badge slot's exact 8-glyph map and the priority rule when a row is simultaneously grouped and per-side.** D-02 fixed "generalize the one badge slot"; it did not fix the letters or the side/type collision rule. See **Set Row — Badge & Grouping**.
3. **How a child (sub-entry) row visually distinguishes itself in the set-number column**, since CF-03 establishes `set_index` keeps incrementing through children at the storage layer, which would otherwise put a confusing real number in a "this is part of the row above" position. Resolved here: the set-number column is blank on every child row. See **Set Row — Badge & Grouping**.
4. **Individual sub-entry removal** — D-05's "one delete rule" names D-09's whole-group revert-to-normal; it does not name removing a single mistaken mini-set. Resolved here with a per-child remove glyph, mirroring the Gym Profile Editor's immediate, no-confirm plate/machine removal precedent (Phase 6). See **Set Row — Badge & Grouping**.
5. **Where the superset and per-side actions render and what they say**, extending `SessionActionSheet`'s already-conditional row pattern (Phase 6 added `equipment` the same way) with four more conditional rows. See **Superset — Session Action Sheet Extension** and **Per-Side Logging — Session Action Sheet Extension**.
6. **The Exercise Strip's superset link badge and the Exercise Page's partner chip anatomy** — D-12 fixed that a link badge and a header chip exist; it did not fix their pixels. See **Superset — Exercise Strip & Exercise Page**.

**Exceptions inherited, still binding:**
- **48×48px minimum hit target** on every interactive element — every new Pressable this phase introduces (the set-number tap target now actually opening something, the picker's seven rows, the "+ Add {type}" control, the per-child remove glyph, the four new `SessionActionSheet` rows, the strip's link badge is decorative-only and NOT a tap target of its own) holds this floor. - **The per-child remove glyph is a 48×48 Pressable containing a 16px glyph** — same "real hit target, no `hitSlop` faking" discipline `TextField`'s Show/Hide control and every Gym Profile Editor remove row already establish (Phase 6 precedent), even though the visual glyph itself is small.
- **The "+ Add {type}" control reuses the Gym Profile Editor's dashed-border chip language verbatim** (Phase 6 Spacing exceptions: "Dumbbell/plate chips use the Exercise Strip's dashed-border 'add' chip language") — not a new visual pattern, the third reuse of this exact language after Exercise Strip's own "+" chip and Gym Profile Editor's "+ Add Plate"/"+ Add Weight" chips.

## Color

Declared values (already shipped in `apps/mobile/global.css`, inherited unchanged):

| Role | Value (light) | Value (dark) | Usage |
|------|-------|-------|-------|
| Dominant (60%) | `#FFFFFF` | `#09090B` | Screen background |
| Secondary (30%) | `#F4F4F5` | `#18181B` | Cards, rows, badge fills |
| Accent (10%) | `#2563EB` | `#3B82F6` | See extended reserved-for list below |
| Destructive | `#DC2626` | `#EF4444` | Destructive actions only — the per-child remove glyph, `ChangeSetTypeDialog`'s confirm fill |
| Foreground (primary text) | `#09090B` | `#FAFAFA` | Body/heading text on Dominant or Secondary |
| Foreground (muted text) | `#71717A` | `#A1A1AA` | Labels, helper text, badge glyphs, inactive picker rows |

**Accent reserved for** (Phase 1's list, extended additively by Phases 3–6 and now this phase — never widened to "all interactive elements"):
- Primary CTA button fill, active tab bar, text links, focused input border (unchanged).
- **New this phase:** the currently-active row in the Set-Type Picker Sheet (semibold `text-accent`, mirroring the Switch Gym Sheet's active-gym-row treatment).
- **New this phase:** the "+ Add Drop" / "+ Add Myorep Set" / "+ Add Partial" control text (an add/recovery link, the same role accent already plays for every other "+ Add X" chip in this app).

**No second semantic color is introduced.** Badges (W/D/M/P/F/A/L/R) stay uniformly `bg-secondary`/`text-foreground-muted` regardless of set type — a per-type color-coding scheme (e.g. amber for drop, red for failure) was considered and rejected: it would be a new semantic-color system this app's design contract has explicitly avoided since Phase 1 (PRs stayed accent-only, not gold; rest-timer stayed neutral, not amber), and eight distinct hues at 9px glyph size would fail Dimension 3 well before it helped anyone read a badge faster. The badge's *letter*, not its color, carries the information — consistent with Phase 5's original warm-up badge doing exactly this with "W".

**Destructive is used for exactly two new surfaces this phase**, both genuine, irreversible-feeling data loss: the per-child remove glyph (deletes one logged sub-entry with real numbers in it) and `ChangeSetTypeDialog`'s confirm button (deletes every sub-entry in the group). Forming or detaching a superset, and enabling or disabling per-side mode, are **not** destructive — both are structural, reversible edits with no data loss (D-11/D-21's own framing), so their `SessionActionSheet` rows render in default foreground, matching `swap`/`reorder`/`info`/`equipment`, never `remove`'s destructive red.

## Set-Type Picker Sheet (D-01, SETS-01)

New component `SetTypePickerSheet`. Same overlay/`ScrollView`/`max-w-[400px]`/`rounded-md bg-surface p-lg` shape as every sibling sheet (`NoteSheet`, `TargetsSheet`, `SessionActionSheet`) — this codebase's "bottom sheet" is a centered overlay card, not an anchored-to-bottom native sheet, and this component does not deviate from that established vocabulary.

**Trigger:** the set-number `Pressable` every `SetRow` already renders (CF-04) gains its `onPress` handler this phase — `onLongPress` (note) is unaffected, the two gestures coexist exactly the way the field Pressables already coexist with the row's own long-press per 05-UI-SPEC Amendment A.1. Available on **every row, parent and child alike** — a child's own set-number column is blank per **Set Row — Badge & Grouping** below, so its tap target is the badge slot itself when a badge is present, or the same 24px column footprint when it is not; the picker it opens governs that row's own `set_type` only.

**Layout:** heading **"Set {N} Type"**, then seven rows in the fixed `SET_TYPES` order (CF-02: normal, warmup, drop, myorep, partial, failure, amrap — never reordered), each a 48×48-minimum row: label (Body) over its one-line descriptor (Label, muted), left-aligned; the currently-active type's row renders its label semibold `text-accent` with a trailing checkmark glyph (`Ionicons "checkmark"`, 16px, `useThemeColors()`-resolved) — mirroring the Switch Gym Sheet's active-row treatment exactly. No Cancel row is needed (tapping outside the overlay, or any row including the already-active one, dismisses — picking the active type again is a no-op close).

**What each row does — the picker's real contract, not just its list:**

| Row | Behavior on a row with no children | Behavior on a row that already has children |
|---|---|---|
| Normal | Retypes this row to `normal` | **Change Set Type confirm** (deletes children), then retypes to `normal` — this is D-09 literally |
| Warm-up | Retypes this row to `warmup` | Same confirm-then-retype (this phase's generalization of D-09, since a warm-up parent with drop/myorep/partial children is exactly the "type and group are one concept" problem D-09 names) |
| Drop Set | **Row's own type is unchanged.** Inserts one `drop`-typed child beneath it; reveals the group's "+ Add Drop" control once that child is marked complete | If the existing children are already `drop`-typed: no-op, sheet closes (mini-sets are added via "+" from here on). If they are a different grouping type: confirm-then-clear, then inserts the first `drop` child |
| Myorep | Retypes this row to `myorep` (D-07: "the parent IS the activation set"); reveals the group's "+ Add Myorep Set" control once this row itself is marked complete | Same confirm-then-retype as Normal/Warm-up when existing children are not already myorep-shaped |
| Partial | Row's own type unchanged. Inserts one `partial`-typed child beneath it; reveals "+ Add Partial" once that child is complete | Same no-op / confirm-and-clear rule as Drop Set |
| Failure | Retypes this row to `failure` | Same confirm-then-retype as Normal/Warm-up |
| AMRAP | Retypes this row to `amrap` | Same confirm-then-retype as Normal/Warm-up |

**Per-side is deliberately absent from this list** — `side` is an independent column from `set_type` (D-20), and the toggle that puts an exercise into per-side mode lives on the per-exercise action surface (D-21), not this picker. See **Per-Side Logging** below.

**Modes:** available in `live` and `editing` (both render `SetRow` through `ExercisePage`, Phase 5 D-32). Not available in `summary-correction` — the summary's expanded correction rows are the numeric-correction-only surface Phase 5 Amendment A.1 already scoped notes out of; set-type changes are out of scope there for the identical reason, stated explicitly rather than left implicit.

## Set Row — Badge & Grouping (D-02, D-05, D-06, D-07, D-08, D-09, SETS-02/03/05/06/09)

Extends `apps/mobile/components/SetRow.tsx`'s existing `renderWarmupBadge`/row anatomy (05-UI-SPEC "Set Row") in place — no new row component, no new column.

**Badge glyph map** (generalizes the existing 14px `bg-secondary` circle, 9px `text-foreground-muted` Label glyph — same visual treatment for every letter, per the Color section's "no per-type color-coding" rule):

| `set_type` / `side` | Glyph |
|---|---|
| `warmup` | **W** |
| `drop` (child only — a drop's parent stays `normal` and shows no type badge) | **D** |
| `myorep` (parent, and its children) | **M** |
| `partial` (child only — a partial's parent stays `normal` and shows no type badge) | **P** |
| `failure` | **F** |
| `amrap` | **A** |
| `side === 'left'` (always the parent, D-20) | **L** |
| `side === 'right'` (always the indented child, D-20) | **R** |
| `normal`, no `side` | *(no badge — the row is exactly as unremarkable as it was before this phase, which is the whole point of the "plain set stays no slower" success criterion)* |

**Priority when both a type badge and a side badge would apply** (a rare combination — e.g. a unilateral exercise where the lifter also takes the working side to failure): the **side glyph (L/R) wins the badge slot.** Rationale: once a set is grouped by side, which side it belongs to is the more load-bearing piece of information for reading the row correctly (weight/reps mean nothing without knowing which arm they belong to), while a type badge is a secondary annotation. This is a discretion resolution — CONTEXT does not specify the combined case, and the single-glyph badge slot (D-02's own design) forces a choice.

**Child (sub-entry) row anatomy:**
- The whole row is indented `md` (16px) — a left-padding added before the badge slot (Spacing exceptions, above).
- **The set-number column renders blank** — no digit, no tap-target chrome beyond the badge itself. CF-03 keeps `set_index` strictly incrementing at the storage layer (so a child's row does carry a real next-integer index internally), but rendering that integer in the set-number column would read as "this is a new set," directly undermining D-06's "reads as one logical set at a glance." A blank column with only the type/side badge and an indent is the resolution: grouping is signaled structurally (indent) and semantically (badge), never by a second visible number competing with the parent's.
- Field layout (weight/reps/RIR stacked-with-reference, checkmark) is otherwise pixel-identical to a parent row — same 05-UI-SPEC Set Row contract, same tap-to-autofill, same tap-to-complete/undo, same long-press-for-note (Amendment A.1 applies per-row, including children).
- **Trailing remove glyph:** every child row carries a 48×48 Pressable after its checkmark — `trash-outline`, 16px, `text-destructive`, `useThemeColors()`-resolved, `accessibilityLabel="Remove sub-entry"` — tapping it deletes that one child immediately, no confirmation (mirrors the Gym Profile Editor's plate/machine row removal, Phase 6 precedent: a single mistaken mini-set is a low-cost, obviously-corrective action, not the group-level data loss D-09's confirm exists for). Parent rows never carry this glyph — a parent cannot be individually deleted from here; removing a whole set follows whatever mechanism already governs a normal row (unaffected by this phase).

**"+ Add {type}" control** (D-08): a single row beneath the group's current last entry, indented to match child rows, dashed-border chip language (Gym Profile Editor precedent), `text-accent` label — **"+ Add Drop"** / **"+ Add Myorep Set"** / **"+ Add Partial"** depending on the group's kind. **Revealed once the group's most recently added entry (the parent itself for a fresh myorep, or the last child for drop/myorep/partial) is marked complete** — this generalizes D-08's "revealed once a sub-entry is completed" to cover myorep's activation-set-as-first-entry case explicitly, since that entry is a parent, not a sub-entry, and D-08 must still govern it. Tapping it appends one new child of the group's kind directly beneath the current last row, with the checkmark unchecked and fields blank (no reference/autofill for a mini-set — there is no meaningful "previous session" value for a drop's third rep count).

**Warm-up rows, and rows carrying any other single-glyph badge, are excluded from the Exercise Strip's completion fraction and from `shouldAutoAdvance`'s count identically** — this phase does not change Phase 5's exclusion mechanism, it extends the underlying predicate (D-17/D-19, see **Phase-Wide Rules** below) that both already read from.

## Superset — Session Action Sheet Extension (D-11, D-14, SETS-07/08)

`SessionActionSheet.tsx`'s `SESSION_EXERCISE_ACTIONS` array (currently `swap | remove | reorder | info | equipment`, the last already conditional per Phase 6) gains two more conditional entries, appended after `equipment` — never inserted, never reordered, matching the additive-only convention every closed UI list in this codebase follows:

```
{ id: 'superset', label: `Superset with ${nextExerciseName}`, icon: 'link-outline' }        // shown when: not already in a group AND a next-in-order exercise exists
{ id: 'detach-superset', label: `Detach from ${partnerExerciseName}`, icon: 'unlink-outline' } // shown when: currently in a group
```

These two are mutually exclusive by construction (an exercise is either groupable or already grouped), matching how `equipment`'s single condition already works — no new filtering pattern, the same `visibleActions = SESSION_EXERCISE_ACTIONS.filter(...)` shape Phase 6 established.

**Forming a superset requires no picker.** D-11: "the action pairs the exercise with the next adjacent one" — tapping the row is the entire interaction; there is no exercise-selection step. The row's own label names which exercise it will pair with (`Superset with {Next Exercise Name}`) precisely so the lifter knows the outcome before tapping — no confirmation dialog follows, since D-11/the reversibility note in CONTEXT frames this as low-cost and undo-able via Detach.

**Detaching is equally immediate — no confirmation.** Mirrors the Switch Gym row's precedent (Phase 6 D-18): a structural, reversible edit with no logged-set data loss gets no confirm dialog in this codebase, that pattern is reserved for Destructive-colored actions only (Remove Exercise, Discard Workout, Archive Gym, Change Set Type).

**Both rows render in default `text-foreground`** — neither is destructive (Color section, above).

**A chain of pairwise "Superset with X" taps can legitimately produce a 3+-member group** (exercise A pairs with B, then B — already paired — pairs with C) — this is expected and tolerated per D-15's "N adjacent members" requirement, not a bug; the row's per-tap "next adjacent" framing makes this an emergent, not a designed, giant-set path, consistent with the Deferred Ideas note that only the *explicit* N-way forming UI is out of scope this phase.

## Superset — Exercise Strip & Exercise Page (D-12, D-13)

**Exercise Strip link badge:** any chip belonging to a superset group renders a small chain-link glyph (`Ionicons "link-outline"`, 12px, `text-foreground-muted`, `useThemeColors()`-resolved) positioned in the chip's top-right corner, inset within the chip's existing padding — purely decorative/informational, not its own tap target (tapping anywhere on the chip still jumps the pager, Phase 5 D-12 unchanged). The chip's existing two-line content (name, fraction) and its current/completed/in-progress tone (Phase 5 `exerciseChipTone`) are entirely unaffected — the link glyph is an overlay, not a fourth chip state.

**Exercise Page partner chip:** beneath the current exercise's header (above the action bar), a `bg-secondary rounded-full` pill — `Superset with {Partner Name}` (Label, muted) for a 2-member group (the only shape this phase's forming UI produces), or `Superset ({N} exercises)` for a tolerated N≥3 group. Tapping the pill jumps the pager to the partner (2-member case) or to the next member in the group, cyclically (N≥3 case) — the identical jump mechanic the strip's own chips already use, so this is a second entry point to the same navigation, never a new one.

**Rest suppression and superset auto-advance are pure behavior — no new visual language.** D-13 (rest starts only after the group's final member completes a set) and D-14 (completing a set on a non-final member auto-advances to the next member) both drive the **existing** Header Timer Bar and pager, unchanged in appearance: through a superset, the rest column simply stays in its already-specified dormant state (`0:00`, muted, Phase 5 E1) for every non-final-member completion, and lights up on the first completion that belongs to the group's final member — exactly the same visual transition the header bar already performs for a plain single exercise, just gated on a different condition. **This phase must not introduce a "next up in your superset" banner, toast, or any second timing surface** — stated explicitly so the plain-set-stays-fast constraint is not accidentally violated by a well-intentioned notification.

## Per-Side Logging — Session Action Sheet Extension (D-20, D-21, D-22, SETS-09)

Two more `SESSION_EXERCISE_ACTIONS` rows, appended after `detach-superset` — again mutually exclusive and conditional, same pattern:

```
{ id: 'enable-per-side', label: 'Log Left/Right Separately', icon: 'git-compare-outline' } // shown when: exercise is not currently in per-side mode
{ id: 'disable-per-side', label: 'Log as One Side', icon: 'git-merge-outline' }             // shown when: exercise is currently in per-side mode
```

**Both are immediate, no confirmation** — D-22 already guarantees existing logged sets are never rewritten by the toggle in either direction, so there is nothing destructive to confirm; both rows render in default `text-foreground`.

**Visual effect of enabling per-side mode:** no change to any already-logged row (D-22). The **next** set added to this exercise renders as a parent carrying an `L` badge and, once that parent is completed, its `R`-badged child appears beneath it using the exact indentation/remove-glyph/badge contract **Set Row — Badge & Grouping** already defines — per-side reuses that mechanism verbatim, it does not introduce a second layout. There is no separate "add the right side" control distinct from the drop/myorep/partial "+" pattern's visual language, though its trigger differs: the `R` child is created automatically once the `L` parent is marked complete (not via an explicit "+" tap), since a per-side pair is always exactly two entries — never an open-ended group the lifter chooses when to stop adding to.

**Exercise Strip / prescription counting:** a completed L+R pair counts as **one** working set toward the exercise's fraction and target-sets count (D-10) — this is the same `parentSetId === null` filter drop/myorep/partial already require of the strip and of `shouldAutoAdvance` (see **Phase-Wide Rules**), applied here to the same effect: logging both sides of a unilateral movement never inflates "3/4" to "4/4" after only 2 real reps' worth of sets.

## Phase-Wide Rules

Extends Phases 1–6's R1–R12 (all still binding: wrap-and-grow, no truncation, structural validity over inline validation, 48×48 floor, `.web.tsx` platform divergence, no loading state for already-seeded local data, one named predicate governing every read path that needs it). This phase adds:

- **R13 — Every "does this row count toward the prescription" read path filters to `parentSetId === null`, and every "is this row excluded from working volume" read path uses `countsTowardWorkingVolume` (D-17).** The Exercise Strip's fraction, `shouldAutoAdvance` (D-19), and the header timer's rest-start gating for supersets (D-13) all must read through these two named predicates rather than re-deriving the rule inline — this is the identical discipline Phase 6's R11 already applied to the equipment-band predicate, extended to this phase's two new counting rules. A UI surface that inlines its own `set_type !== 'warmup'` or `parentSetId` check instead of calling the shared predicate is out of contract, even if it happens to render correctly today.
- **R14 — The badge slot renders at most one glyph, ever.** D-02 generalizes one slot, not a stack of slots; the Color section's priority rule (side wins over type) exists specifically so no row ever needs two badges. A plan that renders two badge circles side-by-side on one row is out of contract.
- **R15 — The plain-`normal`, non-grouped, non-per-side set row is pixel-identical to its Phase 5 self.** No badge, no indent, no remove glyph, no picker-opened-by-default. This is the literal contract behind the phase's own success criterion ("logging a plain working set is no slower than before this phase existed") — every new element this document specifies is additive and conditional, never rendered on the common-case row.
