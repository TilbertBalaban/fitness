<objective>
Replace the single weighted-sum slot score with D-07's tiered sort key, add D-08's primary-mapping
gate and D-06's week-level variety gate, and thread the week-level and day-level state that both
require through `generateProgram`.

Purpose: the remaining two reported root causes live here. Every primary mapping in the real catalog
carries `weight_factor` 1.00, so all 82 chest-primary candidates tie and the seeded hash decides —
an Isometric Wiper can beat a bench press by coin flip. And duplicate avoidance is rebuilt per day,
so Full Body A and Full Body B pick the same exercises.

Output: a rewritten `pickSlotExercise` taking a context object, a `generateProgram` that carries
`pickedByMuscleGroup` across days and covered movement patterns across a day, and suites pinning
each tier independently.
</objective>

    empties. Note in a comment that D-06's gate is strictly stronger than D-07's tier 5, so tier 5

    compoundness comparison rather than inverting it when `preferCompound` is false is what makes
    D-07's "the second may be an isolation movement" permissive rather than prescriptive.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| catalog data → selection scoring | `weightFactor`, `role`, `equipmentRequired` and `movementPattern` come from a synced catalog snapshot the user's device holds; scoring reads them without re-validating, so a crafted or corrupted row is the only untrusted input this plan handles. |
| `generate.ts` → `slot-fill.ts` | In-process calls over already-validated input; no I/O anywhere in this plan. |

Like the rest of this phase, this is a pure in-package algorithm change with no network, no
persistence and no new dependency. The register is integrity and determinism work; there is no
authentication, session or cryptography surface to model.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-21 | Tampering | `pickSlotExercise`'s candidate filter chain | high | mitigate | D-08's primary gate and D-06's week gate are applied as filters before the sort, never as score bonuses, so a catalog row with an inflated `weightFactor` on a `secondary` mapping cannot displace a `primary`-mapped candidate however large the number is. Task 1 pins this with a secondary-at-1.00 versus primary-at-lower case. |
| T-13-22 | Tampering | determinism of the tiered comparator | high | mitigate | `seededRank` then exercise id remain the terminal tie-break, no tier reads iteration order of a `Set` or `Map`, and the byte-identical-JSON cases in `generate.test.ts` and `determinism.test.ts` must stay green — a comparator that fell through to insertion order would fail them. |
| T-13-23 | Denial of Service | comparator cost over the full candidate pool | medium | accept | Sorting stays O(n log n) over a bounded on-device catalog snapshot (Phase 11 D-02); the added tiers are constant work per comparison and `compoundnessOf` walks one candidate's own mapping list. Accepted rather than mitigated because the pool size is already bounded upstream by `buildCandidatePool`. |
| T-13-24 | Tampering | `MODEL_EQUIPMENT_TYPES` drift | medium | mitigate | Loadability reads the array imported from `@fitness/plate-math`, matching `candidate-pool.ts`'s existing pattern, so a future member is picked up automatically; the acceptance criteria assert exactly one import from that package and no local literal. |
| T-13-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no package. 13-RESEARCH.md's Package Legitimacy Audit records "N/A — this phase installs no new packages"; every import is an existing workspace dependency. |
