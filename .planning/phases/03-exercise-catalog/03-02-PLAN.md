<objective>
**As a** lifter who wants to hide an exercise I will never do and keep my logged history intact,
**I want to** the data model to have somewhere to put that,
**so that** archiving and never-suggest are my private state rather than a change to a row every
user of the app shares.

This plan closes the four schema gaps CONTEXT.md names as "not preferences — something must be
added": `load_type` has no vocabulary, `never_suggest` has no column anywhere, per-user archive
has no owner, and bodyweight contribution has no home. All four cross both
`apps/api/src/db/schema/catalog.ts` and `apps/mobile/lib/db/schema.ts`, and one of them
(`user_exercise_preference`) also changes `ops/powersync/sync-rules.yaml`.

Purpose: make every downstream plan's write path expressible before any of them are written.
Output: the extended schema, pushed to a live database and asserted there — not merely
type-checked, because build and typecheck pass whether or not the database was ever migrated.
</objective>

  <decision>Whether `load_type` is one flat six-value enum or two orthogonal axes (what provides resistance x what the user enters).</decision>
  <context>
CONTEXT.md calls this "the phase's clearest one-way door". `load_type` is `text().notNull()`
today with no enum, no check constraint and no documented value set, on both the Postgres and
SQLite sides; ARCHITECTURE.md §1 does not list the column at all. The value lands on ~900 seeded
rows plus every custom exercise, and Phase 5's set-logging UI, Phase 8's progression rules and
Phase 9's volume math all branch on it. Changing the *shape* later (one column to two) is a
schema migration plus a contract break, not a re-seed. Adding a *value* later is additive and
cheap. So the shape is the door; the values are not.

`packages/api-contracts/src/catalog.ts` (created in 03-01) already carries the flat tuple. This
checkpoint either confirms it or sends task 2 back to change it before any CHECK constraint or
seeded row exists.
  </context>
  <options>
    <option id="flat-six">
      <name>One flat enum of six values (RESEARCH.md Pattern 4 — recommended)</name>
      <pros>A `notNull` discriminator that downstream code can `switch` on exhaustively. Forces exactly one classification per exercise, which is what ROADMAP criterion 4 means by "settled before any logging UI exists". Ambiguous cases are resolved once, here, rather than in every consumer.</pros>
      <cons>A genuinely dual-axis movement (a weighted carry is both loaded and distance-measured) must be classified by the axis that drives progression math, with the other axis captured as cue text rather than as data.</cons>
    </option>
    <option id="two-axis">
      <name>Two orthogonal columns: resistance source x measured quantity</name>
      <pros>Expresses a weighted carry honestly. No information is pushed into free text.</pros>
      <cons>Two `notNull` columns instead of one; every downstream consumer branches on a pair rather than a value; the ambiguity moves from this phase into Phase 5's UI logic, which is the direction ROADMAP criterion 4 exists to prevent.     </option>
  </options>

**`apps/api/src/db/schema/catalog.ts`.** Three changes to `exercise` and one new table.

Add `bodyweightContributionPct: numeric('bodyweight_contribution_pct', { precision: 4, scale: 3 })`
— nullable. Add to the table's third-argument array, alongside the existing
`index('exercise_userId_idx')`, a `check('exercise_load_type_check', sql\`...\`)` asserting
`load_type IN` the six literals `external_weight`, `bodyweight`, `bodyweight_plus_added`,
`assisted`, `time_based`, `distance_based` — imported as `check` from `drizzle-orm/pg-core`.
The literals must match `LOAD_TYPES` in `packages/api-contracts/src/catalog.ts` exactly; this
constraint exists because the seed script and any future direct-DB tooling bypass
`sync.service.ts`'s validator entirely, so the database is the real backstop, not a formality.

Add `userExercisePreference` as a new `pgTable('user_exercise_preference', ...)`:
- `id: text('id').primaryKey()` — **not** a composite primary key. `SyncService.applyBatch`
  resolves every row as `eq(table.id, op.id)` and PowerSync's local schema gives every managed
  table a single `id TEXT PRIMARY KEY`, so a composite PK is unwritable through the sync path.
  The id is a client-generated UUID per D-02.
- `userId: text('user_id').notNull().references(() => user.id, { onDelete: 'cascade' })`
- `exerciseId: text('exercise_id').notNull().references(() => exercise.id, { onDelete: 'cascade' })`
- `archivedAt: timestamp('archived_at')` — nullable
- `neverSuggest: boolean('never_suggest').notNull().default(false)`
- `updatedAt: timestamp('updated_at').notNull().defaultNow()`
- `serverSeq: bigint('server_seq', { mode: 'number' }).notNull().default(sql\`nextval('sync_seq')\`)`
- third argument: `unique('user_exercise_preference_user_exercise_unique').on(table.userId, table.exerciseId)`
  and `index('user_exercise_preference_userId_idx').on(table.userId)`. The unique pair is what
  makes "one preference row per user per exercise" a database invariant rather than a
  convention, while the `id` PK keeps it syncable.
Add a `userExercisePreferenceRelations` block mirroring the existing relations style.

Leave `exercise.archivedAt` in place and untouched: it stays the archive column for a user's own
custom rows only, and 03-09 reads archive state exclusively through
`user_exercise_preference` so pickers have one code path rather than two.
