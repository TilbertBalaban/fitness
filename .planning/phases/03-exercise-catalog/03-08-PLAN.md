<objective>
**As a** lifter whose gym has a machine nobody has ever put in a database,
**I want to** add it myself, or copy the closest thing and change one field,
**so that** I can log against what I actually train instead of the nearest approximation.

Phase 2 left `'exercise'` in `PUSH_DEFERRED_TABLES` for this; 03-03 moved it and made `exercise`
a sync root. This plan is the surface that uses it. There is no new REST endpoint here and there
must not be — a custom exercise is an offline-mutable per-user row, so it flows through the one
write path D-01 allows, exactly like every other synced entity.

Purpose: complete EXER-04 and EXER-05, including duplicate-from-seed, which is the natural way a
user says "same as this, but on the other machine".
Output: a pure validation and write module, a select field, and the create and edit screens.
</objective>

**`apps/mobile/lib/catalog/custom-exercise.ts` (new).** A pure-validation half and a
local-write half, in one module because they share the draft type.

`normalizeExerciseName(raw)` — Unicode-normalize to NFC, trim, collapse internal whitespace. Do
not lowercase and do not strip diacritics: this is storage normalization, not the search
normalization `search-index.ts` owns, and destroying the user's casing would be a silent edit of
their data. Count length with `[...name].length` so a code-point limit is what the user
experiences rather than a byte limit that rejects three emoji.

`validateCustomExercise(draft)` returns a `CustomExerciseErrors` record keyed by field, empty when
valid. Rules, kept deliberately in step with 03-03's server-side `hasInvalidField` so a write
never passes locally and fails at the server: `name` required and non-empty after normalization;
`load_type` required and a member of `LOAD_TYPES`; `equipment_required` optional but a member of
`EQUIPMENT_TYPES` when present; `movement_pattern` optional but a member of `MOVEMENT_PATTERNS`
when present; muscle mappings optional, but each must name a `MUSCLE_GROUPS` member and a
`MUSCLE_ROLES` role. Everything else is free text.

`createCustomExercise(db, userId, draft)` — issue the id from `lib/db/id.ts` **first**, before any
write and with no network involved (D-02: every user-authored row carries a client-generated UUID
issued before any network round-trip, so an exercise created in a basement gym has its identity
immediately). Then, in one local transaction, insert the `exercise` row with `is_custom` true,
`source` `user`, `user_id` set, `archived_at` null, `server_seq` null, plus one
`exercise_muscle_mapping` row per selected muscle with its `weight_factor` written as an exact
decimal string (`1.00` primary, `0.50` secondary unless the draft overrides).

`updateCustomExercise(db, userId, id, draft)` — validate, then update the existing row by id inside
one transaction, replacing its mapping rows wholesale. Never touch `id`, `user_id`, `is_custom`,
`source` or `archived_at`: those are exactly the fields `EXERCISE_PATCH_FIELDS` marks
non-patchable in 03-03, and writing them locally would produce an op the server rejects.

`duplicateExercise(db, userId, sourceId)` — read the source exercise and its mappings, issue a
fresh client UUID, and write a user-owned copy carrying the source's field values with
`is_custom` true, `source` `user`, `user_id` set, `variation_of_id` set to the source id (D-03: a
variation is a full `Exercise` row, never a separate table), `archived_at` null, and one copied
mapping row per source mapping preserving the exact `weight_factor` strings. The source row is
read-only throughout — a duplicate that mutates its source is the copy-on-write failure mode
CONTEXT.md rejected, and the test asserting the source is byte-identical is what pins it.

The mapping rows are `localOnly` on the client, which means a duplicate's mappings exist on the
device but do not sync. Record that limitation explicitly in the SUMMARY: a duplicated exercise's
muscle mappings are local-only until a later phase adds a per-user mapping sync path, so the same
duplicate opened on a second device shows the exercise without its mappings. Do not paper over it
by writing mapping rows into a synced table that does not exist.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user free text -> local SQLite -> sync push | Untrusted user input becomes a synced row |
| route parameter -> edit form | An arbitrary `[id]` can be typed into the edit route, including a seeded or another user's exercise |
| seeded row -> duplicate | A read of shared catalog content produces a user-owned write |
