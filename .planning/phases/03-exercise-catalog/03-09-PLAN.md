<objective>
**As a** lifter with a shoulder that hates overhead pressing,
**I want to** tell the app to stop offering it without deleting anything,
**so that** my history stays intact and the app stops suggesting the one movement I cannot do.

CONTEXT.md identified this as a schema gap, not a preference: `exercise.archived_at` sits on a row
whose `user_id` is null for all ~900 seeded exercises, so writing it would archive that exercise
for every user of the system, and no `never_suggest` column existed anywhere. 03-02 created
`user_exercise_preference` and 03-03 made it a sync root. This plan is the surface.

The two requirements are genuinely distinct. Archive removes an exercise from pickers.
Never-suggest is an exclusion list for injuries, dislikes and unavailable equipment — it must
survive without deleting anything, it leaves the exercise browsable, and it is what Phase 6's
program generator and 03-10's smart swap both read.

Purpose: complete EXER-06 and EXER-07 with exactly one archive code path for every exercise,
seeded or custom.
Output: a pure preferences module, a confirmation dialog, and the toggles on the detail screen.
</objective>

  <action>
**`apps/mobile/lib/catalog/preferences.ts` (new).** Export `readPreference(db, userId, exerciseId)`,
`setArchived(db, userId, exerciseId, archived)` and
`setNeverSuggest(db, userId, exerciseId, neverSuggest)`, with a shared internal
`upsertPreference` doing the actual write.

`upsertPreference` reads the existing row for `(userId, exerciseId)` first, then either updates it
by its existing `id` or inserts a new row with a fresh client UUID from `lib/db/id.ts`. Read-then-
write rather than a blind insert, because the local table has an `id` primary key while the
uniqueness that matters is the `(user_id, exercise_id)` pair — a blind insert would create a second
row locally that the server's unique constraint then rejects. Stamp `updated_at` on every write.

The already-archived no-op is a real branch, not an incidental consequence: when the caller asks
to archive a row whose `archived_at` is already non-null, return without writing. Re-stamping would
change `updated_at` and `server_seq`, producing a pointless sync op and — worse — moving the
recorded archive time away from when the user actually archived it.

Archive and never-suggest are independent fields and each setter writes only its own. A setter that
writes both would make "never-suggest without archiving" impossible to express, which is exactly
the distinction EXER-07 exists for.

Every write is local-first and optimistic: it goes to local SQLite and PowerSync's crud queue
uploads it whenever there is signal. There is no await on a network call, no spinner, and no
user-facing failure path — which is why the UI-SPEC dismisses the loading and error states for
these controls rather than covering them.

Never write to `exercise.archived_at` from this module. For a seeded row that column is shared
state and writing it would archive the exercise for every user; 03-03 already rejects such an op
server-side with `invalid_field`, and the test asserting `exercise.archived_at` is still null
after archiving is what pins the client half. One archive code path for every exercise regardless
of origin — PITFALLS.md §11 is explicit that archive-logic bugs are a top corruption risk, and two
code paths is how they arrive.

Also assert the preserved-reference property here rather than deferring it to a screen test:
archiving an exercise that a local `session_exercise` row points at must leave that reference
resolvable. That is ROADMAP criterion 3 in schema terms and it is the single assertion this plan
exists to make true.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user action -> `user_exercise_preference` write | A per-user flag is written against a globally-shared exercise row |
| local preference row -> sync push | The row carries a `user_id` that the server must not trust from the payload |
| archive action -> historical references | An archive must not break `session_exercise` or `personal_record` references |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-14 | Tampering | archive path for seeded exercises | high | mitigate | `preferences.ts` never writes `exercise.archived_at`; all archive state goes to `user_exercise_preference`. Pinned by a test asserting `exercise.archived_at` is still null after archiving a seeded row, and backed server-side by 03-03's `invalid_field` rejection of a direct `archived_at` PATCH on `exercise`. |
| T-03-37 | Tampering | archive breaking historical references | high | mitigate | Archive stamps a timestamp on a separate table and never deletes an `exercise` row — `personal_record.exercise_id` and `session_exercise.exercise_id` are both `notNull` and a delete would break both. Pinned by a test asserting a referencing `session_exercise` still resolves after archiving. |
| T-03-02 | Tampering | client-supplied `user_id` on a preference op | high | mitigate | The client writes its own session's `userId`, and 03-03's `toUserExercisePreferenceValues` derives `userId` from the authenticated session and ignores the payload regardless — so a tampered client cannot write a preference for another account. |
| T-03-38 | Information Disclosure | preference visibility across users | high | mitigate | The PowerSync stream query added in 03-02 is `WHERE user_id = auth.user_id()`, so a preference row is only ever delivered to its owner. Pinned client-side by the two-user independence test. |
| T-03-09 | Repudiation | no audit trail for preference changes | low | accept | v1 has no compliance requirement for preference history, and `sync_conflict_log` already covers the synced tables where losing a write would matter. Accepted at ASVS L1. |
| T-03-39 | Denial of Service | duplicate preference rows from a blind insert | medium | mitigate | `upsertPreference` reads before writing and updates by existing `id`, so the local table cannot accumulate rows the server's `(user_id, exercise_id)` unique constraint would then reject and wedge the queue on. |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package; `ArchiveDialog` is built from the existing `SignOutDialog` pattern. |
</threat_model>
