<objective>
Close G-03-3: no image in this app has ever painted. The user reported it as "I don't see thumbnail in
'5 suggested alternatives'", but the diagnosis is unambiguous — `SwapSuggestionList`, `ExerciseListRow`
and the detail hero all render the same shared `ExerciseImageTile`, and that tile gives its `<Image>` no
resolvable box. The container's height exists only through a ratio style on a percentage-width box, and the
image asks for a percentage of that. On react-native-web an `<Image>` paints nothing itself — its pixels
come from an absolutely-positioned background layer inside its own box — so a box that resolves to no
height paints nothing at all, silently: the asset resolves so the fallback never renders, nothing errors so
the failure handler never fires, and the real `<img>` is fully transparent so no broken-image glyph
appears. The tile's fill colour also matches the row it sits on, so the empty tile is literally
indistinguishable from its background.

Purpose: this is the first human observation of the shared image render path, not a regression. Both
03-07-SUMMARY.md D5 and 03-10-SUMMARY.md line 99 record "a vendored image actually paints on screen" as
never observed (WINDOWS #37), and no test in the phase asserts anything about the image element — which is
exactly why 20 scorer tests, 7 component tests, a clean typecheck and a clean web bundle all passed over a
100%-reproducible defect. EXER-03 names "static images" as part of an exercise's detail; today that
requirement is satisfied only on paper.

Output: a tile that cannot collapse, all three call sites sized through one shared contract, a placeholder
that renders behind rather than instead of the image, and the first tests in this repo that assert an
`<Image>` element exists, carries a non-null source, and sits in a non-zero box.
</objective>
