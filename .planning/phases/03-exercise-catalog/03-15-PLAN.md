## Mechanism (read this before touching anything)

Confirmed by direct read of
`node_modules/.pnpm/react-native-web@0.21.2_.../node_modules/react-native-web/dist/exports/Image/index.js`:

1. `Image` renders an outer `View` whose style array is
   `[styles.root, hasTextAncestor && styles.inline, imageSizeStyle, style, styles.undo, { boxShadow: null }]`.
2. `imageSizeStyle` is `resolveAssetDimensions(source)` — **the source's own intrinsic `{width, height}`**.
   A web-bundled `require()` asset resolves to `{ uri, width, height, scale }`, so this is populated for
   every vendored catalog image.
3. `style` (what the tile passes) is the **only later entry that can override it**. `StyleSheet.absoluteFill`
   supplies `position` and four insets and *no* width or height — so 750x500 survives untouched. CSS then
   over-constrains (`left:0` + `right:0` + `width:750px`) and drops `right`, leaving a 750x500 absolutely
   positioned box inside a 56x42 clipped parent.
4. The visible pixels come from an **inner `View` painted with `background-image`** plus
   `resizeModeStyles[resizeMode]` (`cover` → `background-size: cover`), sized `width: 100%; height: 100%`
   of that outer box. The `<img>` in the DOM is `hiddenImage` — `opacity: 0`, accessibility only.

**Consequence for the gap's own `missing:` list.** The item "confirm `resizeMode='cover'` reaches the DOM as
`object-fit: cover`" is **not achievable as stated and is not the defect**: react-native-web 0.21.2 never
emits `object-fit` for `Image` at all, and it already applies `background-size: cover` correctly. The
observation that an `<img>` carried `object-fit: fill` was a reading of the transparent accessibility
element. The real and only fault is item 1 — the missing width/height. This plan closes item 1, closes
item 3 (the Suggested-Alternatives call site), and disposes of item 2 as a misdiagnosis with the source
citation above rather than silently dropping it.

## Why 03-13's tests did not catch this

`ExerciseImageTile.test.tsx` asserts (a) exactly one `Image` element exists with the passed source,
(b) its style flattens to `position: absolute` with four zero insets, and (c) the **container** has a
finite positive numeric width and height. Every one of those passes against the defect. Nothing in the file
asserts anything about the *image's own* resolved size, and nothing models the fact that a source brings its
own width and height to the fight. The new assertion in Task 1 is written to fail on exactly that.
