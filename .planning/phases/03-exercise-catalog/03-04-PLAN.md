<objective>
**As a** lifter who trains real movements with real names,
**I want to** the catalog to know that a stiff-leg deadlift loads hamstrings hard, glutes less
and lower back less again,
**so that** every muscle-volume figure the app ever shows me is built on honest data rather than
a role-to-constant lookup.

CONTEXT.md is explicit that normalization *is* the phase: "loading 900 JSON rows into Postgres is
an afternoon. Mapping a foreign dataset's muscle vocabulary onto the fixed taxonomy, assigning
honest `weight_factor` values, inferring movement patterns, classifying load types, and finding
the duplicates is the phase." This plan does that work and commits its output as a reviewable,
deterministically re-runnable artifact — not as a one-shot script whose decisions vanish into a
database.

Purpose: produce the single artifact both the Postgres seed (03-05) and the bundled mobile
snapshot (03-05) read from, with every derived value traceable to a named rule and every
unmapped input recorded rather than dropped.
Output: a committed taxonomy mapping, a normalization script, the normalized catalog, a
normalization report, and a license record.
</objective>

**`apps/api/src/seed/catalog-taxonomy.ts` (new).** The mapping tables, as data. Nothing here
executes — this file is the reviewable record of every judgment call, so the normalization script
becomes a mechanical application of it rather than the place decisions hide.

`SOURCE_MUSCLE_TO_CANONICAL` — every one of free-exercise-db's 17 values gets an entry:
`abdominals`→`abs`, `abductors`→`abductors`, `adductors`→`adductors`, `biceps`→`biceps`,
`calves`→`calves`, `chest`→`chest`, `forearms`→`forearms`, `glutes`→`glutes`,
`hamstrings`→`hamstrings`, `lats`→`lats`, `lower back`→`lower_back`,
`middle back`→`upper_back_traps`, `neck`→`neck`, `quadriceps`→`quads`, `traps`→`upper_back_traps`,
`triceps`→`triceps`, and `shoulders`→ the sentinel `AMBIGUOUS_DELT` rather than a canonical id.
The `shoulders` bucket is the one genuinely lossy mapping: the source has one shoulder value where
the canonical taxonomy has three delt heads.

`SHOULDER_DISAMBIGUATION_RULES` — an ordered array of `{ match, primary, secondary[], why }`
records resolving `AMBIGUOUS_DELT` from the exercise's own name and `force`/`mechanic` fields.
At minimum: lateral/side raise and upright row → `side_delts`; reverse fly, rear delt row, face
pull → `rear_delts`; front raise and any overhead/shoulder press → `front_delts` primary with
`side_delts` secondary; anything unmatched → `front_delts` primary with both other heads
secondary at reduced weight, and the record is flagged `derived: true` in the report so the
guess is visible rather than indistinguishable from sourced data.

`SOURCE_EQUIPMENT_TO_CANONICAL` — all 12 source values: `body only`→`bodyweight`,
`machine`→`machine`, `other`→`other`, `foam roll`→`foam_roller`, `barbell`→`barbell`,
`kettlebells`→`kettlebell`, `dumbbell`→`dumbbell`, `cable`→`cable`,
`medicine ball`→`medicine_ball`, `bands`→`band`, `exercise ball`→`exercise_ball`,
`e-z curl bar`→`ez_bar`.

`MOVEMENT_PATTERN_RULES` — an ordered array of `{ match, pattern, why }` over exercise name plus
the source `force` (`push`/`pull`/`static`) and `mechanic` (`compound`/`isolation`) fields.
Order matters: the first match wins and the rules must be ordered most-specific first. Cover at
minimum squat/lunge/leg press → `squat`; deadlift/good morning/hip thrust/romanian → `hinge`;
bench/dip/push-up/chest press → `horizontal_push`; overhead/shoulder press → `vertical_push`;
row/face pull → `horizontal_pull`; pull-up/chin-up/pulldown → `vertical_pull`; carry/farmer/
suitcase → `carry`; twist/woodchop/rotation → `rotation`; `mechanic: 'isolation'` → `isolation`.
An exercise matching no rule gets `null`, which is a legal column value, and is listed in the
report rather than forced into a bucket.

`LOAD_TYPE_RULES` — an ordered array producing exactly one of the six `LOAD_TYPES` per exercise.
Base rule: source `equipment: 'body only'` → `bodyweight`; assisted/machine-assisted in the name
→ `assisted`; plank/hold/wall sit/isometric → `time_based`; carry/farmer/sled → the axis that
drives progression math, which is the load, so `external_weight` with distance captured in cue
text (this is the CONTEXT.md farmer's-carry case, resolved deliberately, not by omission);
weighted pull-up / weighted dip / weighted variants of a bodyweight movement →
`bodyweight_plus_added`; everything else → `external_weight`. No exercise may end up unclassified:
`load_type` is `notNull` and CHECK-constrained.

`WEIGHT_FACTOR_OVERRIDES` — a record from exercise-name family to an ordered list of
`{ muscle_group_id, role, weight_factor }`, for the families where the honest values are not the
role defaults. D-04 exists because a binary 1.00/0.50 map is the failure mode: the stiff-leg
deadlift case ARCHITECTURE.md names must appear here as primary `hamstrings` `1.00`, secondary
`glutes` `0.50`, secondary `lower_back` `0.30`. Populate at least the compound families where the
secondary contribution is clearly not half: deadlift variants, squat variants, bench variants,
row variants, overhead press, pull-up/chin-up, hip thrust, lunge/split squat. Families not
listed fall back to `1.00` primary / `0.50` secondary and are marked `derived: true` in the
report.

`BODYWEIGHT_CONTRIBUTION_DEFAULTS` — a record giving `bodyweight_contribution_pct` per load type
and per named family, as exact decimal strings, sourced from `docs/catalog-load-types.md`:
`external_weight`, `time_based` and `distance_based` → `null` unless a family override says
otherwise; `bodyweight` and `bodyweight_plus_added` and `assisted` → a family value, with at
minimum pull-up/chin-up `1.000`, dip `0.950`, push-up `0.640`, inverted row `0.600`,
split squat / lunge `0.850`, bodyweight squat `0.650`. Every value is a guess made once, in the
open, in a reviewable file — which is exactly what the first prohibition in `must_haves` demands.

**`apps/api/src/seed/normalize-catalog.ts` (new).** A plain Node script following
`generate-corpus.ts`'s shape: dotenv bootstrap, no `@Injectable()`, no Nest bootstrap, driven by
`pnpm --filter api seed:catalog:normalize`. It does not touch Postgres at all — it reads the
committed source JSON and writes two JSON files.

Export `normalizeCatalog(source)` as a pure function so the spec can drive it without running the
script, and keep the file's `main()` a thin wrapper that reads, calls, and writes. Steps:

1. **Muscle mapping.** For each source exercise, map `primaryMuscles` through
   `SOURCE_MUSCLE_TO_CANONICAL` with role `primary` and `secondaryMuscles` with role `secondary`.
   Resolve any `AMBIGUOUS_DELT` through `SHOULDER_DISAMBIGUATION_RULES`, recording the matched
   rule's `why` in the report. A source muscle value with no entry is an **exclusion**, recorded
   with its exercise id and the value — never dropped.
2. **Weight factors.** Apply `WEIGHT_FACTOR_OVERRIDES` by family match; fall back to `1.00`
   primary / `0.50` secondary and mark the fallback `derived: true`. Emit every factor as an
   exact decimal string with two decimal places so it fits `numeric(4,2)` without rounding.
3. **Movement pattern and equipment.** Apply `MOVEMENT_PATTERN_RULES` (first match wins) and
   `SOURCE_EQUIPMENT_TO_CANONICAL`. An unmatched pattern yields `null` and a report entry; an
   unmapped equipment value is an exclusion.
4. **Load type.** Apply `LOAD_TYPE_RULES`. Every exercise must end with exactly one value; if any
   exercise reaches the end unclassified, throw rather than defaulting — a silent default here is
   the `notNull` CHECK violation that would surface much later as a seed failure.
5. **Bodyweight contribution.** Apply `BODYWEIGHT_CONTRIBUTION_DEFAULTS` by load type then by
   family override. Emit as an exact decimal string with three decimal places, or `null`.
6. **Duplicate detection and merge.** Normalize names for comparison (lowercase, strip
   punctuation, collapse whitespace, drop a trailing equipment qualifier) and group. Within a
   group, keep the row with the richest instructions as canonical, fold every other name into its
   `aliases`, union their muscle mappings, and record the merge in the report. Do **not** delete
   anything without recording it: PITFALLS.md §11 calls duplicate merging a near-certain need and
   prescribes preserving references rather than deleting.
7. **Variation grouping.** Where a merged family has a clear parent movement present in the
   source, set `variation_of_id` on the children to the parent's id (D-03 — a variation is a full
   `Exercise` row, never a separate table). Where no parent exists, leave it `null`.
8. **Ids.** Derive each exercise id deterministically from the source record's own id (prefixed
   `seed_`) so re-running produces stable ids and a re-seed is an upsert, not a duplicate insert.
   Derive each mapping id as `{exercise_id}:{muscle_group_id}`.
9. **`catalog_version`.** `computeCatalogVersion` returns the first 16 hex characters of the
   SHA-256 of the canonically-serialized artifact body (keys sorted, no `generated_at`). Content-
   addressed, so an unchanged input yields an unchanged version and the client's version handshake
   is meaningful. Set `generated_at` from the source file's own recorded fetch date, never from
   `Date.now()`, or the artifact stops being byte-reproducible.
10. **Write.** `catalog-normalized.json` (shape: `CatalogSnapshot`) and
    `catalog-normalization-report.json` (shape: counts, exclusions with reasons, merges,
    per-field provenance flags). Serialize both with sorted keys and a trailing newline so a
    re-run produces a byte-identical file and the diff is reviewable.
