<diagnosis_already_done>
Do not re-investigate the root cause. `.planning/debug/exercise-catalog-load-failure.md` establishes it and
records the probes. Treat the following as given:

- Every PowerSync-managed table — `localOnly` ones included — is a SQLite VIEW over `ps_data__*` /
  `ps_data_local__*` with INSTEAD OF triggers. `local_only` only switches the backing-table prefix; it does
  not opt a table out of the view mechanism. Confirmed by string extraction from the exact wasm served at
  `:8081`.
- SQLite refuses to prepare an upsert clause against a view. Probed at the engine level against a
  PowerSync-shaped view: the drizzle-emitted statement returns `Error: in prepare, cannot UPSERT a view`;
  the same INSERT without the clause succeeds.
- The "do nothing" form is **not** an escape hatch — separately probed, same refusal. SQLite rejects the
  whole upsert grammar against a view, not just the update form.
- `@powersync/drizzle-driver` 0.8.0 rewrites no SQL and propagates the rejection to the caller.
- Not a 03-11 regression and not an environment problem: the worker and wasm assets are served (200s
  verified), the bundled artifact validates, and the load path makes no network call before it fails.
</diagnosis_already_done>

<fix_direction_decided>
The gap's `missing` list leaves the direction open between `INSERT OR REPLACE INTO <view>` and
read-existing-ids-then-branch. **The direction is decided here: read-existing-ids-then-branch.** Do not
re-litigate it, and do not spend a browser run probing the replace form. Two independent facts settle it,
neither of which needs an engine probe:

1. **Drizzle cannot express it.** The installed `drizzle-orm@0.45.2` SQLite insert builder exposes exactly
   two conflict methods and no replace modifier — verified in
   `node_modules/.pnpm/drizzle-orm@0.45.2_*/node_modules/drizzle-orm/sqlite-core/query-builders/insert.d.ts`.
   Taking that route means hand-written raw SQL with hand-written snake_case column names for all four
   tables, abandoning the typed schema on the one write path that most needs it.

2. **It is a correctness regression, not merely an unproven one.** REPLACE is DELETE-then-INSERT. The
   `seededExercise` values object deliberately omits `archivedAt`, and `load-snapshot.ts:58-61` states
   exactly why: omitting it means re-seeding a row the archive-drift pass previously archived never silently
   un-archives it. A replace rewrites the whole row and resets that column to NULL, so **every archived
   exercise would silently come back on every catalog refresh.** That mirrors `seed-catalog.ts`'s
   server-side rule being broken on the client.

Read-then-branch, by contrast, is built only from single-row `INSERT INTO <view>` and
`UPDATE <view> SET ... WHERE id = ?` — the two statement shapes PowerSync's INSTEAD OF triggers exist to
serve. It depends on no unverified engine behaviour, and it fits the archive-drift diff already in the
function, which is itself a read-then-branch computed in JS rather than in a compound WHERE clause.

Task 1 still runs before Task 2, but not as a probe of the chosen direction. Its job is to reproduce the
diagnosis end-to-end in a real browser — closing the debug session's own stated blind spot ("not executed
against the real @powersync/web engine") — and to stand up the regression gate before the code it guards
exists, so the gate is provably capable of failing.
</fix_direction_decided>

    **The shape.** For each of the four tables, replace the single conflict-clause statement with:
    read the existing ids for that table into a `Set` before the loop; inside the loop, `UPDATE ... WHERE
    id = ?` when the set already holds the id, otherwise plain `INSERT` — and add the id to the set. Build
    one values object per row for the insert and derive the update's set object from it by omitting `id`.

    Everything stays inside the transaction the caller opens. Do not open a second transaction, and do not
    collapse the loops into multi-row `VALUES` inserts — see the first trap.

    **Trap 1 — duplicate ids inside one artifact.** The committed snapshot carries 3,177 mapping rows that
    collapse to 3,134 unique composite ids: 43 duplicates, upstream data-quality debt that
    `seed-catalog.ts` also handles server-side. The old per-row conflict clause absorbed them as
    last-write-wins. The `Set` must therefore be mutated as inserts happen — if it only ever holds the ids
    that existed *before* the loop, the second occurrence of a duplicate is classified as an insert and the
    view's trigger raises a uniqueness failure on statement ~3,100 of the load. This is also why a
    multi-row insert is off the table: it turns last-write-wins into a hard failure.

    **Trap 2 — an archived row is still an existing row.** The seeded-exercise existence set must include
    archived rows. The archive-drift block reads with `isNull(archivedAt)`; reusing that filtered result as
    the existence set would classify an archived row as new and raise a uniqueness failure on the first
    refresh after any archive. Hoist a single read of `{ id, archivedAt }` from `seededExercise` to the top
    of the exercise section and derive both sets from it: all ids for the existence check, and the subset
    whose `archivedAt` is null to feed the drift diff. Reading before the writes instead of after gives the
    identical `vanishedIds`, because every row this pass touches is in the artifact and therefore excluded
    by the `currentIds` filter regardless. Keep the `exerciseIds.length > 0` guard.

    **Trap 3 — the update must keep omitting the archive column.** Deriving the update's set object from
    the same values object the insert uses preserves the existing behaviour exactly: `archivedAt` is absent
    from both, so a re-seed never un-archives a row. That omission is the same property the old conflict
    clause's set object had, and `load-snapshot.ts:58-61` already explains why it matters. Do not "fix" it

    **Trap 4 — never put `id` in the update set.** The WHERE clause already pins the row, and PowerSync's
    INSTEAD OF UPDATE trigger takes a distinct branch when the new id differs from the old one. Excluding
    the column means that branch is never entered at all.

    **Trap 5 — no generic write helper.** Four explicit selects and four explicit loops. A single helper
    generic over drizzle table types needs casts this codebase's strict config will reject, and the four
