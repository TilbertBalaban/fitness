<objective>
**As a** lifter standing in a basement gym with no signal on a phone I only just installed,
**I want to** open the exercise catalog and read what a movement targets,
**so that** I can decide what to do next without the app needing the internet.

This is the phase's tracer: the thinnest complete path from a committed catalog artifact,
through the bundled asset, into PowerSync-managed local SQLite, out to a list screen and a
detail screen — with the network never touched. It proves the one architectural assumption
RESEARCH.md flags as unverified (Assumption A4: `DrizzleAppSchema` accepting a mixed map of
plain and `localOnly`-wrapped tables, read back through the same `db` handle every existing
screen uses) before any of the ~900-row normalization work is built on top of it.

Purpose: settle the catalog delivery mechanism — the phase's central unsolved problem — with
running code rather than a design note, and establish the shared vocabulary
(`load_type`, muscle groups, movement patterns, equipment) that every later plan imports.
Output: a working offline read path carrying three real exercises, plus the contract package
that the server validator, the seed script and the custom-exercise form all read from.
</objective>

      <name>First-install REST download only (the literal D-01 carve-out)</name>
