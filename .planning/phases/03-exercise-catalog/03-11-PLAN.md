<diagnosis_already_done>
Do not re-investigate the root cause. It is confirmed:

- Better Auth emits no CORS response headers of its own. Its official Express and Hono integration docs
  both show the **host framework** registering CORS middleware with `credentials: true` and an explicit,
  non-wildcard origin, *and separately* listing that same origin in `trustedOrigins`.
- `trustedOrigins` drives only Better Auth's own origin/CSRF check and its `redirectTo`/`callbackURL`
  allowlist. It never produces an `Access-Control-Allow-Credentials` header.
- The comment at `apps/api/src/auth/auth.ts:10-14` asserts the opposite. That is why the gap survived
  Phase 01 and Phase 02 verification.

Two facts about the installed middleware were verified directly against `node_modules` and are
load-bearing for the tasks below — treat them as given:

1. `app.enableCors(opts)` resolves to `httpAdapter.enableCors` → `this.use(cors(opts))`, registering on the
   Express instance **in call order**, exactly like `app.use()`. `AuthModule` attaches its own middleware
   later, during `app.init()` inside `listen()`.
2. In `cors@2.8.6`, `configureCredentials` emits `Access-Control-Allow-Credentials: true` **unconditionally**
   whenever `credentials: true` — including for origins that are *not* on the allowlist. Only
   `Access-Control-Allow-Origin` is withheld for a non-allowed origin. Task 3 depends on this distinction.
</diagnosis_already_done>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser origin → API | An untrusted, attacker-controllable `Origin` header crosses here on every cross-site request; the CORS allowlist is the only thing deciding whether the browser hands the response back to that page. |
| environment → CORS allowlist | `WEB_ORIGINS` is operator-supplied configuration that becomes a security control at startup. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-44 | Spoofing | `app.enableCors` origin option in `main.ts` | high | mitigate | Explicit origin array from `resolveWebOrigins()` with `credentials: true`. No wildcard (the browser itself rejects `*` with credentials) and no origin-reflecting callback, either of which would let any site issue credentialed requests. Task 3 asserts a non-listed origin receives no `Access-Control-Allow-Origin`. |
| T-03-45 | Information Disclosure | Shared/intermediary HTTP caches | medium | mitigate | `Vary: Origin` asserted present on preflight responses, so a cache cannot replay one origin's allow-origin header to a different origin. |
| T-03-46 | Tampering | Drift between the CORS allowlist and Better Auth `trustedOrigins` | medium | mitigate | Single `web-origins.ts` parser is the sole reader of the environment variable; Task 1's file-list gate fails if a second reader appears. |
| T-03-47 | Denial of Service | Preflight requests bypassing the client-version floor | low | accept | CORS is registered ahead of `minClientVersionMiddleware`, so an OPTIONS preflight is answered before the floor check. Browsers do not attach `X-Client-Version` to preflights, so the floor was never enforceable there; the actual request that follows is still checked. |

No package-manager install occurs in this plan — `app.enableCors()` uses middleware already vendored inside
`@nestjs/platform-express`. No `T-03-SC` supply-chain checkpoint is therefore required.
</threat_model>
