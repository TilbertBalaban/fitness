<objective>
**As a** lifter who invents a machine variation nobody has named,
**I want to** create it on my phone in a basement gym and have it reach my account,
**so that** I can log against it everywhere without the app inventing a second way to write data.

Phase 2 left a deliberate stub for this plan: `packages/api-contracts/src/sync.ts` already lists
`'exercise'` in `PUSH_DEFERRED_TABLES` with the comment `// Phase 3 — Exercise Catalog`, and
`SyncService`'s `TABLE_MAP` does not handle it. Custom-exercise create/edit/duplicate is
therefore **not** a new REST controller — it is an extension to the existing sync push pipeline,
and that pipeline's aggregate logic is currently built entirely around `workout_session` as the
one root type.

Purpose: make `exercise` and `user_exercise_preference` second and third *singleton* root types
without weakening the ownership check that protects every existing table. The nullable-owner
case is the crux and the single most safety-critical change in the phase.
Output: an extended sync service, an exhaustive patch-field map for both new tables, and two
e2e specs — including the lone-`PUT exercise` regression case RESEARCH.md calls the highest-value
test this phase can write.
</objective>

**`SINGLETON_ROOT_TYPES` (new const).** `new Set(['exercise', 'user_exercise_preference'])` —
the two types that are their own aggregate root and have no synced children. Every branch below
keys off this set rather than repeating two string comparisons.

**`AGGREGATE_RANK`.** Add both types at rank `0`. This is safe because aggregates are keyed by
distinct root id: an `exercise` aggregate and a `workout_session` aggregate never share a key,
so their ranks never compete inside one sort.

**Root resolution (the Pitfall 2 trap).** The existing loop has three branches and the third is
an `else` that assumes every remaining type is a `logged_set` chaining through
`session_exercise_id`. An `exercise` op falling into it resolves `undefined` and lands in the
`missing_parent` bucket with a reason that gives no signal about the real cause. Extend the first
branch so it reads `op.type === 'workout_session' || SINGLETON_ROOT_TYPES.has(op.type)` and sets
`rootByOpId.set(op.op_id, op.id)` — self-root, exactly as `workout_session` already does.

**`healRoot`.** The current derivation heals an unresolvable op onto the batch's single known
root. A batch containing only `exercise` ops would make an exercise id the sole resolved root,
and an orphaned `logged_set` in that batch would then heal onto it. Restrict the heal-candidate
set to roots contributed by `workout_session` ops only: build the candidate set from
`rootByOpId` entries whose op type is `workout_session`, and leave singleton-root ids out of it.

**Ownership resolution.** Track the root's *type* alongside its id when building the `aggregates`
map, so the ownership lookup can pick the right table. The existing `existingRoots` query
selects specifically from `workoutSession`; add two parallel batched queries — one selecting
`{ id, userId }` from `exercise` for exercise-rooted aggregates, one from
`userExercisePreference` for preference-rooted aggregates — and merge them into
`existingOwnerByRoot`. Keep them batched (`inArray`), never per-row: the query-count assertion
in `seeded-corpus-perf.e2e-spec.ts` fails on an N+1 shape.

The null-owner case is the crux. `exercise.userId` is nullable and is `NULL` for every seeded
row. A row whose stored `userId` is `null` must fall into the existing `owner !== userId`
rejection branch, **not** the `owner === undefined` "treat as a fresh insert" branch — because
`undefined` means "no such row" while `null` means "a shared row exists and nobody owns it".
Since `Map.get` returns `undefined` for a missing key and the stored value for a present one,
a present-but-null entry already yields `null`, which is `!== userId` and therefore rejects.
Confirm that is what actually happens rather than assuming it: an explicit
`if (owner === null) reject not_owner` before the `owner === undefined` test makes the intent
unambiguous and is what the e2e test in task 3 pins. Do not add a path that adopts a null-owner
row for the pushing user; that is the data-integrity trap this whole design avoids.
