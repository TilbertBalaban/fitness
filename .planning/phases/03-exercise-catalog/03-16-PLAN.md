<objective>
Close G-03-6. A cold deep link to `/exercises/{id}` renders "Exercise not found — This exercise may have been
removed." and stays that way: polled at 3, 6, 10, 15, 20, 30 and 40 seconds, unchanged. Visiting `/exercises`

Purpose: URL-addressable web routes are a stated reason this project chose Expo Router. A deep link that
resolves only if you happened to visit a different screen first is broken for the medium it was chosen for.
Output: a single hydration seam the whole `exercises` segment goes through, and a detail route that can no

**As a** lifter who opened a link to an exercise directly,
**I want to** see that exercise,

## Diagnosis

`grep -rn "snapshot" apps/mobile/app/exercises/` returns exactly one hit: `loadCatalogSnapshot` is imported
by `apps/mobile/app/exercises/index.tsx:25` and by no other route. The list screen's `useEffect` (index.tsx
lines 134-162) is therefore the *sole* owner of catalog hydration into the localOnly `seededExercise` table.

`apps/mobile/app/exercises/[id].tsx:147` calls `loadExerciseDetail(db, id)` directly. On a cold start that
table is empty, `loadExerciseDetail` returns `null`, `resolveDetailScreenState` maps `null` to `not-found`,
and the screen renders its terminal state. Nothing ever hydrates, so nothing ever corrects it.

`apps/mobile/app/exercises/edit/[id].tsx:127` has the identical exposure — `loadExerciseDetail` with no
hydration ahead of it, mapping a null result to its own `not-found` branch.

## Where the fix belongs, and why not the segment layout

Four routes share the segment and `app/exercises/_layout.tsx` already exists and already covers all four, so
it looks like the natural owner. It is not, for a concrete reason: a layout renders its children immediately.
Firing an async hydrate from the layout would leave each route's own effect racing it, and the detail route
would still reach `loadExerciseDetail` against an empty table and still render not-found — the exact bug,
now with a second moving part. Making the layout *block* its children on hydration would gate the create
form (which needs no catalog at all) behind an 880-row transaction and would put an async data concern into
a file whose current job is route hoisting for the signed-in guard (T-03-58) and header chrome. That file is
load-bearing for authorization; it stays minimal.

A React context provider was the other candidate. It would work, but it buys nothing here: the state being
shared is one idempotent promise, not reactive data, and every consumer is an `async` function inside an
effect that can simply `await` it. A provider would add a component layer, a hook, and a second place for a
route to forget to subscribe.

The chosen owner is a **shared module-level single-flight function**, `ensureCatalogLoaded(db)`, in
`apps/mobile/lib/catalog/ensure-catalog.ts`. It matches this codebase's established shape — pure-ish
functions with an injected `db` and an injected test seam (`loadCatalogSnapshot(db, snapshotOverride)`,
`log-set.ts`'s `db` parameter) — it is directly unit-testable with no renderer, and it makes hydration an
explicit `await` at the top of each route's effect rather than an ambient assumption.

`new.tsx` was examined and needs no change: it reads no catalog table, sourcing `MUSCLE_GROUPS`,
`LOAD_TYPES`, `EQUIPMENT_TYPES` and `MOVEMENT_PATTERNS` from `@fitness/api-contracts` constants.

## The conflation, stated precisely

Today `not-found` means two different things and the user sees only one of them. After this plan:

| Catalog load | Detail lookup | Screen |
|---|---|---|
| in flight | not attempted | hydrating skeleton |
| threw, or returned `invalid` | **never called** | error — "Exercise catalog couldn't load" |
| `loaded` / `current` | returned a detail | found |
| `loaded` / `current` | returned `null` | not-found — "Exercise not found" |
| `loaded` / `current` | threw | error |

`not-found` is now unreachable without a completed successful catalog load. That is the whole fix.

  now-generalized intent.
