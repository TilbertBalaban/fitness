<objective>
Close G-03-4. From `http://localhost:8081/exercises/seed_90_90_Hamstring` the user can neither reach the
Edit form nor navigate back. These are two independent deterministic defects, both fully diagnosed in
`.planning/debug/detail-screen-no-back-nav-no-edit.md`.

**(A) No Edit.** The Edit link exists but renders only under an ownership-gated visibility flag, and every
seeded exercise resolves to a null owner — so Edit is hidden by design on every one of the ~870 seeded
rows, a contract pinned by `preferences.test.ts`. The intended path is the always-visible Duplicate button,
but nothing on screen says so. Worse, the not-permitted screen written for exactly this case
(`edit/[id].tsx:188-200`) is dead UI: the only link to the edit route is itself behind that same gate, so a
non-owner can reach it only by typing the URL. UAT test 2 required that state and passed on 33 unit tests
that structurally could not detect it was unreachable.

**(B) No back.** `app/_layout.tsx:109` hides the header for every root-stack screen, and there is no
`app/exercises/_layout.tsx` — so per expo-router's own hoisting rule all four exercises routes are siblings
in the root stack with no override point, and a repo-wide search for any back affordance returns zero hits.
Compounding it, no anchor route is declared anywhere, so loading the reported URL directly (or refreshing
it) yields a single-entry stack where react-navigation's own back predicate is false: simply showing the
header would render a back-LESS header on that exact URL.

Purpose: this is the last open functional gap in Phase 03 and it blocks EXER-04 and EXER-05 from being
reachable in practice, not just implemented. Fixing it also closes, deliberately, a security hole the
diagnosis surfaced as a secondary finding: because the root `<Stack.Screen name="exercises" />` matches
only the list route, the detail, create and edit routes never enter the protected-screen set and mount
regardless of session state. Adding the segment layout collapses them into one guarded route.

Output: a headered, back-navigable exercises segment with native swipe-back; an Edit control that is always
visible and routes to a screen that explains itself; and a design contract that records what "swipe back"
does and does not mean on each platform.
</objective>

Do NOT re-diagnose. These facts were established by a full debug session and verified against the installed
`expo-router@57.0.12` source. Re-deriving them wastes the plan's budget.

1. `app/exercises/_layout.tsx` does not exist. The four routes are `exercises/index`, `exercises/[id]`,
   `exercises/new`, `exercises/edit/[id]`, hoisted into the root stack
   (`expo-router/build/getRoutes.js:15-16`: routes in directories without `_layout` files are hoisted to
   the nearest `_layout`).
2. `useScreens.js:77` matches a declared screen by `child.route === name || child.route === name + '/index'`.
   That is why the root `<Stack.Screen name="exercises" />` configures and protects the LIST route only,
   and why setting options on it can never reach the detail route.
3. `useScreens.js:117` appends every unmatched child verbatim, and the protected-screen filter is keyed on
   declared names — so the three unmatched routes mount regardless of `signedIn`. This is the secondary
   finding, closed here on purpose.
4. On web, `expo-router/build/react-navigation/native-stack/views/NativeStackView.js` derives the header's
   default back control from the previous stack entry and contains **no gesture code at all**.
   `gestureEnabled` exists only in the native fork
   (`fork/native-stack/createNativeStackNavigator.js:86-101`). A web pan-gesture back is not achievable and
   must not be promised. Browser history is the only web back gesture, and Expo Router does drive it.
5. In that same web view, a **function-valued `headerLeft` is rendered unconditionally** — the
   previous-entry check only guards the DEFAULT back button. This is why the fix supplies an explicit
   `headerLeft` rather than relying on showing the header.
6. `expo-router@57.0.12` supports `export const unstable_settings = { anchor: 'index' }` in a layout file
   (`getRoutesCore.js:653-655` reads `unstable_settings.anchor ?? unstable_settings.initialRouteName`).
   No `unstable_settings` or `initialRouteName` exists anywhere in `apps/mobile/app` today.
7. Both `gestureEnabled` and `fullScreenGestureEnabled` are declared options on this version's native-stack
   options type (`react-navigation/native-stack/types.d.ts:527,547`), so both typecheck on every platform.
8. `apps/mobile/app/exercises/edit/[id].tsx` is complete and correct — 294 lines with loading, not-found,
   not-permitted and form branches, and `resolveEditAccess(ownerUserId, currentUserId)` already returns
   `not-permitted` for any non-owner. Nothing in the edit screen needs repair; it needs to become
   reachable.

**Design decision taken here, not left open.** The UAT gap offers two options for Edit discoverability.
This plan takes option (a) — always render an Edit control and let the existing not-permitted screen
explain — because it is the smaller change, it resurrects already-written and already-tested UI, and it
makes UAT test 2's not-permitted state reachable by navigation instead of only by typing a URL. Option (b)
(keeping Edit hidden and relabelling Duplicate) was rejected: it leaves the not-permitted branch dead, and
it asks a label to carry an explanation a whole screen was already written to give.
