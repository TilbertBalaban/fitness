<objective>
Expand plan 01-01's two tracer forms into the complete auth surface D-06 admits, built from one shared
component set and matching the UI-SPEC's state matrix exactly.

The tracer proved the happy path end-to-end. This plan adds everything around it: inline per-field
validation, submitting states that keep their labels, form-level error banners, keyboard-avoiding layout,
the enumeration-safe forgot-password success state, and the third screen the tracer did not need.

D-06 bounds this precisely — sign-up, sign-in, sign-out, and password reset, with no email verification, no
OAuth provider, and no account deletion. Sign-out ships in plan 01-05; password reset's server half and web
page ship in plan 01-04; this plan owns the three in-app screens.

Purpose: PLAT-05 becomes a surface a person can actually use rather than a path a test can traverse.
Output: three finished auth screens and the reusable form primitives every later phase inherits.
</objective>

    Build four components, all styled with the token utility classes rather than literal colour or size
    values, so both appearances resolve from one class.

    `TextField` renders a Label-role label, a `TextInput` in the Body role, and an inline error slot beneath
    the field. The error slot renders nothing when the field has no error, so an untouched field shows no
    error text and occupies no error space. The focused state gets an Accent border — one of only four
    places the accent colour is allowed. A `secure` variant renders a show-and-hide control whose hit area

    is binding and inherited by every later phase. Do not set a font-scaling cap on any text.

    `disabled` and renders a spinner glyph alongside the label while leaving the label text in place — the
    UI-SPEC is explicit that the label is never replaced by the spinner alone. The control is at least 48px
    tall.

    `ErrorBanner` renders form-level error copy in the Destructive role above the CTA, and renders nothing
    when there is no error. It grows to as many lines as its message needs.

    `AuthScreenLayout` is the shared shell: a keyboard-avoiding scroll container so the focused field is
    never obscured by the OS keyboard on native, a single column capped at 400px and centred on wide desktop
    viewports, and `lg` horizontal padding on narrow ones. Content scrolls rather than clipping.

    Use only core React Native primitives and Ionicons from `@expo/vector-icons` — the UI-SPEC records that
    no component library applies to this project, because shadcn is a web-only Radix registry and this
    codebase renders to native and web from one tree.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-02 | Information Disclosure | sign-in and forgot-password copy | medium | mitigate | Sign-in renders one generic rejection message for every credential failure, and forgot-password renders one success message regardless of whether the address is registered. | T-01-01 | Spoofing | password entry field | high | mitigate | The password field is a secure input; the show-and-hide control is an explicit, person-initiated action rather than a default. No credential is placed in a query string or a navigation parameter. |
| T-01-23 | Information Disclosure | validation performed only on the client | medium | mitigate | Inline validation is a convenience layer; Better Auth's server-side `minPasswordLength` and email format checks remain authoritative, so bypassing the screen cannot create an account the server would reject. |
| T-01-24 | Elevation of Privilege | reset `redirectTo` value | high | mitigate | The `redirectTo` is built from the configured web origin rather than from any person-supplied input, and Better Auth's `trustedOrigins` from plan 01-01 rejects an unlisted origin, so the reset link cannot be redirected to an attacker-chosen host. |
