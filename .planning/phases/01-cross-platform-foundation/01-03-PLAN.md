<objective>
Make the API's version contract explicit and enforceable from its first request, so a months-old mobile
build in the field can never be broken by a server deploy — success criterion 4.

Two mechanisms, deliberately separate. `VersioningType.URI` routes a request to the controller matching
its version; that shipped in plan 01-01's tracer so nothing was ever served unversioned. This plan adds
the second, orthogonal mechanism: a minimum-supported-client-version floor that answers "is this client
still supported at all," which NestJS's versioning does not know or care about.

CONTEXT.md left the versioning strategy to Claude's discretion. `01-RESEARCH.md` §"Architecture Patterns"
Pattern 3 settled URI versioning; Open Question 1 settled the floor as a `CanActivate` guard rather than a
custom versioning extractor, because an extractor that finds no matching version yields a generic 404 the
client cannot distinguish from a missing route. Assumption A3 flagged the hard-block policy as a proposal
to confirm rather than a locked fact; this plan resolves it by shipping the mechanism with an
environment-sourced floor that defaults to blocking nothing, so the enforcement path is real and tested
while no build in the field is stranded by turning it on.

Purpose: ARCHITECTURE.md §3 requires the wire contract to stay additive while any client version is in the
field, and requires breaking changes to be gated behind a floor. Both halves exist after this plan.
Output: a versioned API with a working, proven, configurable support floor.
</objective>

  <action>
    `client-version.constants.ts` exports `CLIENT_VERSION_HEADER` set to the literal `X-Client-Version`,
    `MIN_CLIENT_VERSION_REASON` set to the literal `client_version_below_minimum`, a `compareSemver(a, b)`
    returning a negative, zero, or positive number, and `resolveMinClientVersion()` reading
    `process.env.MIN_CLIENT_VERSION` and defaulting to `0.0.0`. Defaulting to `0.0.0` means the floor is
    live and exercised from the first deploy while stranding no build — raising it is a single environment
    variable change once a real breaking change ships, which is the point of resolving Assumption A3 this
    way rather than either hard-coding a number or deferring the mechanism.

    `MinClientVersionGuard` implements `CanActivate`. It reads the request header named by
    `CLIENT_VERSION_HEADER`. When the header is absent, it allows the request — an absent version means an
    older or non-app caller and must not be treated as hostile. When the header is present and
    `compareSemver` places it below `resolveMinClientVersion()`, it throws an `HttpException` with status
    426 whose body carries `{ reason: MIN_CLIENT_VERSION_REASON, minimum: <floor> }` so the client can
    branch on the reason code rather than parsing prose. When the header is present and at or above the
    floor, it allows the request. A malformed version string is treated as absent, not as below the floor —
    a parse failure must not strand a caller.

    `HealthController` is decorated `@Controller({ version: VERSION_NEUTRAL })` and exposes `GET /health`.
    It must remain reachable by any client version, including one the floor blocks, so a blocked client can
    still discover why. Do not apply the guard to it.

    Register the guard globally in `app.module.ts` with an `APP_GUARD` provider, and import `HealthModule`.
    Add `MIN_CLIENT_VERSION` to `.env.example` with the value `0.0.0` and a one-line note in `README.md`
    under an "API versioning" heading explaining that raising it returns 426 to older builds and that the
    version-neutral health route stays reachable regardless.
