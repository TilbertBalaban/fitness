<objective>
**As a** person whose phone holds a live session for this app, **I want to** know that my session
cookie is only ever sent to this project's own API — **so that** a URL that merely *looks* like my
API, on a different port or an attacker-registered subdomain, cannot collect a credential that lets
it act as me.

This plan closes the single code gap in `01-VERIFICATION.md` (`status: gaps_found`, 6/8). Plan 01-09
declared the prohibition "MUST NOT attach the session credential to a request whose destination is
not this project's own API origin" as `status: resolved`. The verifier rejected that claim on direct
evidence: `apps/mobile/lib/api-client.ts:29` implements the guard as a string-prefix test against
`API_URL`, which is not an origin check. `String.prototype` prefix matching has no concept of where a
host or port boundary falls, so any URL that is textually longer than `API_URL` but begins with the
same characters passes the gate and receives the user's live session cookie.

**This is not a hypothetical.** Four independent bypass classes were reproduced directly against the
project's own values while writing this plan — each one is a URL where the prefix test says "this is
our API" and a parsed-origin comparison says it is not:

| # | class | request URL | API origin | prefix test | origin comparison |
|---|-------|-------------|------------|-------------|-------------------|
| 1 | port extension | `http://localhost:30000/v1/auth/get-session` | `http://localhost:3000` | accepts | rejects (`http://localhost:30000`) |
| 2 | subdomain suffix | `https://api.fitness.app.evil.com/v1/auth/get-session` | `https://api.fitness.app` | accepts | rejects (`https://api.fitness.app.evil.com`) |
| 3 | separator-less suffix | `https://api.fitness.appevil.com/x` | `https://api.fitness.app` | accepts | rejects (`https://api.fitness.appevil.com`) |
| 4 | userinfo confusion | `https://api.fitness.app@evil.com/x` | `https://api.fitness.app` | accepts | rejects — real origin is `https://evil.com` |

Class 1 fires under the project's **shipped default configuration** with no attacker infrastructure
at all. Classes 2-4 fire the moment `EXPO_PUBLIC_API_URL` names a real deployed host.

**Why the existing green suite proved nothing.** `session-refresh.test.ts` has one negative case for
this guard, asserting against `https://not-this-project.example.com/...`. That URL fails a *correct*
origin check **and** fails the broken prefix check, so it cannot distinguish the two implementations.
All 42 tests pass and the suite is genuinely green; a green suite here was simply not evidence about
this prohibition. Closing the gap therefore means two things, not one: fix the comparison, and
replace a test that cannot fail with tests that *would have* failed against the shipped code.

**Two verified runtime findings reshape the fix.** Neither is in `01-RESEARCH.md`, `01-PATTERNS.md`,
or `01-REVIEW.md` — all three were written without inspecting the installed packages.

**Finding A — the global `URL` on device is spec-compliant, and it is not React Native's.** React
Native 0.86.2 installs its own regex-based `URL` (`Libraries/Core/setUpXHR.js` calls
`polyfillGlobal('URL', ...)` over `Libraries/Blob/URL.js`), whose constructor never throws and whose
`origin` getter is a regex. Expo SDK 57 then **replaces** it: `expo/src/winter/runtime.native.ts`
runs `install('URL', () => require('./url').URL)` after `InitializeCore`, and `expo/src/winter/url.ts`
re-exports the WHATWG-conformant `URL` from `whatwg-url-minimum`. `installGlobal` overwrites any
configurable descriptor, and RN's polyfill is configurable, so Expo's wins. `expo/src/Expo.fx.tsx`
imports `./winter` as its first statement, so this is installed before any app module evaluates. The
practical consequence: `new URL(...)` **throws `TypeError` on a malformed URL on device**, exactly as
it does under Jest. The try/catch is load-bearing on every target, not Jest-only defensive style.

**Finding B — the Jest environment and the device agree, which is why this plan can be trusted.** A
throwaway probe run through `apps/mobile`'s own `jest-expo` config confirmed the test process sees a
spec-compliant `URL`: `new URL('http://localhost:30000/x').origin` is `http://localhost:30000`, and
`new URL('not-a-url')` throws `TypeError`. Both bypass classes reproduce identically in Jest and on
device, so a Jest assertion here is real evidence rather than an environment artifact. This matters
because the failure being fixed is precisely one where a check looked right and tested green.
