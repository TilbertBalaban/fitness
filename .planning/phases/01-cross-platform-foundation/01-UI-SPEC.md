# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn does not apply. shadcn is a Radix/web-only React component registry; this project is React Native + Expo Router targeting iOS/Android/RN-Web from one codebase, so the shadcn init gate is not applicable and was skipped rather than declined. |
| Preset | not applicable |
| Component library | none — hand-built components on top of core RN primitives (`View`, `Text`, `Pressable`, `TextInput`) styled with NativeWind v4 utility classes, per `01-RESEARCH.md`'s styling evaluation (NativeWind chosen over Unistyles/Tamagui specifically to stay Expo-Go-compatible for this phase) |
| Icon library | `@expo/vector-icons` (Ionicons subset) — bundled with Expo SDK 57, zero extra native dependency, renders on native and RN Web from the same import, and Ionicons includes gym-appropriate glyphs (`barbell-outline`) for the Workout tab |
| Font | System default (RN `Platform` font — San Francisco on iOS, Roboto on Android, the OS default `system-ui` stack on web via RN Web's font fallback). No custom font family is introduced in Phase 1 — adding one is a zero-value dependency this phase, and every later phase inherits whatever is decided here, so defer that decision until there is an actual brand/typography need. |

**NativeWind config contract (binding for the executor):**

```js
// tailwind.config.js — darkMode MUST be 'class', not 'media'
// Reason: PLAT-09 requires a persisted three-state override (system/light/dark),
// not OS-follow-only. NativeWind's Appearance.setColorScheme() throws
// "Cannot manually set color scheme, as dark mode is type 'media'" if darkMode
// stays at its 'media' default — this is a trap, not a preference.
module.exports = {
  darkMode: 'class',
  content: ['./app/**/*.{ts,tsx}', './components/**/*.{ts,tsx}'],
  theme: {
    extend: {
      colors: {
        background: 'rgb(var(--color-background) / <alpha-value>)',
        surface: 'rgb(var(--color-surface) / <alpha-value>)',
        accent: 'rgb(var(--color-accent) / <alpha-value>)',
        destructive: 'rgb(var(--color-destructive) / <alpha-value>)',
        foreground: 'rgb(var(--color-foreground) / <alpha-value>)',
        'foreground-muted': 'rgb(var(--color-foreground-muted) / <alpha-value>)',
      },
    },
  },
};
```

The three-state toggle calls `Appearance.setColorScheme('system' | 'light' | 'dark')` per `01-RESEARCH.md`'s documented API (`useColorScheme` from `react-native`, not the deprecated NativeWind re-export); the choice is persisted to `@react-native-async-storage/async-storage` and re-applied on cold start before first paint to avoid a flash of the wrong theme.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (form field internal padding, chip padding) |
| md | 16px | Default element spacing (form field gaps, card padding) |
| lg | 24px | Section padding (screen horizontal margins, auth form top spacing) |
| xl | 32px | Layout gaps (space between form and footer link on auth screens) |
| 2xl | 48px | Major section breaks; also doubles as the minimum touch-target dimension (see exception below) |
| 3xl | 64px | Page-level spacing (space above the auth screen's hero heading) |

**Exceptions:**
- **Minimum touch target: 48x48px on every interactive element** (buttons, tab bar items, icon-only controls, checkboxes, the password show/hide toggle) — a hard floor, not a suggestion. This covers both Apple HIG's 44pt and Material's 48dp minimums with one number, chosen deliberately because the core value proposition is one-handed, possibly-sweaty, in-gym use, and this token layer is inherited by all 11 remaining phases including the set-logging surface. Where the visual glyph is smaller than 48px (e.g., a 24px icon), pad the hit area to 48px rather than shrinking the target — do not rely on `hitSlop` as a substitute for real layout padding, since `hitSlop` doesn't grow the visible focus/pressed-state indicator.
- No other exceptions to the 4px-multiple rule in this phase.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 (regular) | 1.4 (20px) — form field labels, tab bar labels, helper/caption text |
| Body | 16px | 400 (regular) | 1.5 (24px) — input text, body copy, placeholder-screen description text |
| Heading | 20px | 600 (semibold) | 1.2 (24px) — screen titles, placeholder-screen headings ("Home", "Programs", …) |
| Display | 28px | 600 (semibold) | 1.2 (34px) — auth screen hero heading ("Welcome back", "Create your account") |

Exactly 4 sizes, exactly 2 weights (400/600), per contract. Do not introduce a third weight (e.g. bold 700) anywhere in this phase — semibold at 600 carries every emphasis need at this UI's complexity.

**Accessibility floor:** body text must hold WCAG AA contrast (4.5:1) against its background in both themes; do not cap `allowFontScaling` — every text element must respect the OS-level font-scaling setting, since a legible-at-default-size app that breaks under iOS/Android accessibility font scaling fails the same in-gym-legibility intent the touch-target floor above serves.

## Color

| Role | Value (light) | Value (dark) | Usage |
|------|-------|-------|-------|
| Dominant (60%) | `#FFFFFF` | `#09090B` | Screen background |
| Secondary (30%) | `#F4F4F5` | `#18181B` | Cards, nav/tab bar, input field fills, dividers |
| Accent (10%) | `#2563EB` | `#3B82F6` | See reserved-for list below — narrow, not a general interactive color |
| Destructive | `#DC2626` | `#EF4444` | Destructive actions only (sign-out-with-pending-writes confirmation) |
| Foreground (primary text) | `#09090B` | `#FAFAFA` | Body/heading/display text on Dominant or Secondary surfaces |
| Foreground (muted text) | `#71717A` | `#A1A1AA` | Labels, helper text, placeholder-screen description copy, inactive tab labels |

**Accent reserved for** (explicit list — never "all interactive elements"):
- Primary CTA button fill (Sign In / Create Account / Send Reset Link / Reset Password)
- Active tab bar icon + label (native `NativeTabs` tint, web `TabTrigger` active state)
- Text link color (Create account / Sign in / Forgot password / Back to sign in)
- Focused input field border and the theme-toggle segmented control's selected segment

Everything else — secondary buttons, unselected tabs, icons, borders, disabled states — uses Foreground/Foreground-muted/Secondary, never Accent. This keeps the 10% budget real rather than aspirational.

**Assumption flagged:** no brand color was specified upstream (CONTEXT.md left styling to research/discretion, and research settled the styling *engine*, not the palette). Blue-600/500 is chosen as a neutral, legible, unclaimed default — this is the single highest-leverage undecided call in this document since it propagates to all 11 remaining phases' accent usage. If the project owner has a brand color preference, it is a low-cost swap (one CSS variable pair) before Phase 2 locks in more UI, but is not currently blocking — flagging per the "explicit judgement call" requirement, not blocking on it.

## Navigation Shell (D-09)

One Expo Router route tree renders two platform-specific tab chrome implementations, per `01-RESEARCH.md` Pattern 2 — this is the documented pattern, not a workaround:

| Platform | Implementation | Visual contract |
|----------|-----------------|-------------------|
| Native (iOS/Android) | `expo-router/native-tabs` (`NativeTabs`) | OS-native tab bar chrome (bottom, 5 items, platform-default height/blur/safe-area handling — do not override native tab bar styling with NativeWind classes, `NativeTabs` renders real native tab-bar controllers). Active tab icon + label tinted Accent; inactive tabs tinted Foreground-muted. |
| Web (desktop browser) | `expo-router/ui` (`Tabs`, `TabList`, `TabTrigger`, `TabSlot`) resolved via `_layout.web.tsx` | Horizontal tab bar, top of viewport, Secondary-color background, real `<a href>`-backed navigation (deep-linkable URLs per success criterion 3) — not a client-side-only pseudo-router. Active `TabTrigger` gets Accent icon/label + a 2px Accent bottom border; inactive tabs use Foreground-muted. Tab bar height 56px (14 × 4), horizontal padding `lg` (24px) at the bar's outer edges, `md` (16px) gap between items. |

## Screen Inventory

Every screen this phase ships real, shipped UI for or a labelled placeholder for. States use the copy defined in **Copywriting Contract** below by reference — do not restate copy here.

### Auth screens (real UI, PLAT-05)

| Screen | Route | Key elements | States |
|--------|-------|---------------|--------|
| Sign in | `(auth)/sign-in` | Display heading, email field, password field (with 48px show/hide toggle), primary CTA, "Forgot password?" link, "Create account" link | default, field-validation-error (inline, per-field), submit-error (banner above CTA), submitting (CTA shows a spinner glyph + disabled state, label unchanged — never replace the label text with the spinner alone, per the 2-tap-friction ethos this project inherits even here) |
| Sign up | `(auth)/sign-up` | Display heading, email field, password field, confirm-password field, primary CTA, "Already have an account?" link | default, field-validation-error, submit-error (incl. "email already exists"), submitting |
| Forgot password | `(auth)/forgot-password` | Heading, email field, primary CTA, "Back to sign in" link | default, field-validation-error, submit-success (replaces form with a confirmation message, does not silently reveal whether the email exists — copy is identical whether or not the account exists), submitting |
| Reset password (web-only, D-07) | web route at the app's own domain, e.g. `/reset-password?token=…` | Heading, new-password field, confirm-password field, primary CTA | default, invalid-or-expired-token (replaces the form entirely — never show a form bound to a dead token), field-validation-error, submit-success (redirects/links back to native app sign-in with a short confirmation message), submitting. This page is a **web-only surface** — it is served by the web build regardless of which platform's client requested the reset, per D-07, and does not need a native-tabs equivalent. |

All four auth screens: single-column form, max content width 400px centered on wide (desktop web) viewports, `lg` (24px) horizontal screen padding on narrow viewports, keyboard-avoiding layout so the focused field is never obscured by the OS keyboard on native.

Selecting a segment calls `Appearance.setColorScheme(...)`, persists the choice to `AsyncStorage`, and must survive an app restart (this is the behavior `01-VALIDATION.md`'s `theme.test.ts` asserts against).

## Session & Loading States (D-02, visual contract)

D-02 requires cold start to render authenticated UI immediately with no network wait. This is a UI contract, not only an auth-logic one — the two platforms need different treatments because they have structurally different session-restore mechanisms (`01-RESEARCH.md` Pitfall 1):

| Platform | Mechanism | Visual treatment |
|----------|-----------|-------------------|
| Native (iOS/Android) | Session read synchronously from `expo-secure-store` on launch (Better Auth Expo plugin's cache) | **No loading state ever appears on the native launch path.** The root layout renders the tab scaffold (if a cached session exists) or the sign-in screen (if not) on the very first frame. The background token-refresh call is invisible — its failure is a silent no-op (D-01/D-03), never a spinner, toast, or banner on the happy path. |
| Web (desktop browser) | No local session cache to read — the browser's cookie jar is sent automatically, but confirming validity still costs one `get-session` round trip | A **non-blocking, non-full-screen skeleton** is permitted, and only here: render the tab scaffold's chrome (tab bar, screen frame) immediately, with a neutral Secondary-colored placeholder block (no shimmer animation needed for this phase's UI complexity) in place of anything session-dependent, for the duration of that one request. This must never be a full-screen spinner or blank white screen — the research-flagged Clerk-style 10-15s black screen is exactly the failure mode this project structurally rejects (D-02), and a web skeleton that overstays a fast same-origin request would recreate that failure mode in miniature. If `get-session` resolves unauthenticated, redirect to sign-in; the skeleton-to-redirect transition should not itself flash a second loading state. |

**Explicit user-triggered auth actions** (submitting sign-in, sign-up, forgot-password, or reset-password) are different from cold start — these legitimately require the network and show a normal submitting state (CTA spinner + disabled, per Screen Inventory above) and a normal error state if the device is offline: "Can't reach the server. Check your connection and try again." (see Copywriting Contract). This is not a violation of D-02/D-03 — those decisions govern passive session validation on the launch path and background refresh, not an explicit form submission the user is actively waiting on.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Screen-dependent — see the per-screen table below. There is no single phase-wide CTA since this phase ships four distinct auth screens plus a settings control, not one primary flow. |
| Empty state heading | Not applicable this phase — the tab placeholders use "Heading" copy from Screen Inventory above (they are labelled placeholders, not empty-data states; there is no data model yet to be empty of). |
| Empty state body | See Screen Inventory's placeholder body copy table. |
| Error state | See per-screen error copy below. |

### Per-screen CTA and link copy

| Screen | Primary CTA | Secondary actions |
|--------|-------------|---------------------|
| Sign in | "Sign In" | "Create account" (link), "Forgot password?" (link) |
| Sign up | "Create Account" | "Already have an account? Sign in" (link) |
| Forgot password | "Send Reset Link" | "Back to sign in" (link) |
| Reset password (web) | "Reset Password" | "Back to sign in" (link, shown only on the success state) |

### Validation and error copy

| Case | Copy |
|------|------|
| Invalid email format (inline, on blur or submit) | "Enter a valid email address." |
| Password too short (inline) | "Password must be at least 8 characters." |
| Confirm-password mismatch (inline) | "Passwords don't match." |
| Sign-in failure (wrong email/password) | "Incorrect email or password. Try again." — deliberately generic; never confirms or denies whether the email is registered, to avoid account enumeration on the *sign-in* path specifically. |
| Sign-up: email already registered | "An account with this email already exists. Sign in instead." (with "Sign in instead" as a tappable link to the sign-in screen) — disclosure here is an accepted, ordinary sign-up UX pattern, unlike sign-in. |
| Forgot-password submit (always, regardless of whether the email exists) | "If an account exists for that email, we've sent a reset link." — identical copy either way, so this path never leaks account existence. |
| Reset-password: expired or already-used token | "This reset link has expired or already been used. Request a new one." (with a link back to Forgot Password) |
| Any auth action attempted while offline / unreachable server | "Can't reach the server. Check your connection and try again." |

### Destructive confirmation

| Action | Confirmation approach |
|--------|-------------------------|
| Sign out, zero pending unsynced writes (the only real case in Phase 1 — D-04) | **No confirmation dialog.** Signing out proceeds immediately; a 0-count does not warrant an interruption. |
| Sign out, N > 0 pending unsynced writes (the hook D-04 requires exist now, wired to a real count starting Phase 2) | Confirmation dialog: heading "Sign out?", body "You have {N} unsynced changes. Signing out will discard them.", destructive-styled confirm button labelled "Sign Out Anyway" (Destructive color fill), cancel labelled "Cancel" (Foreground-muted, no fill). |

There is no account-deletion or other destructive action in Phase 1's scope (D-06).
