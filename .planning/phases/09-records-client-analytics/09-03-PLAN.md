<objective>
**As a** lifter who has been training for months, **I want to** browse the records I actually hold and
switch between the four ways of measuring them, **so that** the achievements the app celebrated in passing
are still there when I go looking for them.

This plan ships the Records screen (S3), its entry point on the History tab, and the two narrow corrections
to shipped Phase 5 code that this phase's requirements make load-bearing. ANLY-01 and ANLY-02 are otherwise
already delivered: `personal_record` is a persisted, PowerSync-synced table and
`apps/mobile/lib/db/personal-record.ts` already detects idempotently. This plan reads that table; it does
not fork the rules, does not recompute records, and does not restyle the shipped badge beyond its label.

Deliberately NOT in this plan, and each is a later plan's whole subject rather than a gap here: the History
tab's trend card and its `ListHeaderComponent` (09-05 — this plan touches ONLY the header action row of
`history.tsx`), the two other tab cards (09-04, 09-05), and the performance screen's range switch (09-06).

Purpose: make the records a lifter holds browsable, and make the badge that announced them say which one it
means.
Output: a working Records route, a truthful PR badge, an honest estimated-1RM cell, and executed browser
evidence for both.
</objective>

   - The same defaulted last `db` parameter that makes every reader injectable for tests and for the
     durability harness.
   - The same signed-in-only guard returning a neutral empty page, and the same deliberate absence of a
     `user_id` row filter, for the same documented reason: that column is stamped server-side on sync push,
     so an offline-written row carries a null locally.
   - A keyset cursor over `(achieved_at, id)` descending, never an offset. Carry the shipped reader's
     reasoning across rather than restating it thinly: an offset counts from the top of the current result
     set on every call, so a row arriving between two page fetches silently duplicates or skips a row at
     the boundary.

     N+1 shape the sibling readers' comments already forbid.
   - `formatRecordValue(row, unit)` producing the UI-SPEC's four row-value formats. **The stored value's
     meaning differs per metric and this is the single most likely defect in this task**: it is a weight

     set volume, and a REP COUNT for most-reps. All four are persisted through the same three-decimal
     string convention, so the rep count must be rounded back to a whole number before it is rendered, and
     it must be joined with the weight of the set that achieved it — which is NOT stored on the record row
     and must come from the originating logged set. Comment all of this at the function; a reader who
     assumes the column always holds kilograms will produce a plausible, wrong number.
   - When the originating set is absent or carries no weight, render the rep count alone. Do not render a
     dash in place of the weight — the dash convention means "no value", and here the value simply is not
     part of what this row records.
   - An exercise id with no name resolves through the same unknown-exercise fallback the shipped program
