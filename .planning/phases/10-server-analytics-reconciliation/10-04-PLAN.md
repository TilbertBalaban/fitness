<objective>
**As a** lifter who has been training for years, **I want to** the app's server to stay as fast on my
thousandth workout as on my first, **so that** editing an old session never turns into a wait.

Criterion 5 says history holds its query count as data grows, "enforced by assertions against a
realistically-sized dataset". D-08 is blunt about what that means: an executable test that seeds a
real corpus, counts the statements a request actually issues, and fails on regression — not a comment
claiming the read is batched. Without the assertion the criterion is unfalsifiable and rots silently.

This plan also closes the single biggest gap 10-RESEARCH found: the shipped corpus generator inserts
its ten `seed-ex-*` exercises with **zero** `exercise_muscle_mapping` rows. Left alone, every rollup
computation against that corpus joins to nothing, produces no cells, and a query-count assertion over
it would pass trivially — a green test asserting nothing, which is exactly the failure mode this
repository's suite-integrity reporter exists to catch and which this specific case would slip past,
because the suite is not empty, only its subject is.

It runs in the same wave as 10-05 because the two share no file: this plan is entirely `apps/api`,
10-05 is entirely `apps/mobile`.

Deliberately NOT in this plan: any change to the reconciliation logic itself (10-01 and 10-02 own it).
If a budget assertion fails, the correct response is to report the measured number and the reason,
not to loosen the ceiling and not to reach into the service.

Purpose: make "fast as data grows" a falsifiable claim.
Output: a corpus that exercises real muscle-volume maths, and an executable ceiling on recompute cost.
</objective>

## Flagged planner assumptions

- **[ASSUMED] `PERF_BUDGET.maxQueriesPerReconcile`'s numeric value.** No prior art exists in this repo
  and no external spec exists. The reasoned starting point is the statement count the design predicts:
  roughly seven for the rollup half (four batched reads, one delete, one insert, one watermark upsert)
  plus roughly six for the record half (three batched reads, one update family, one insert, one
  delete), plus headroom — so **24**. Tag it `[ASSUMED]` in the same style every existing `PERF_BUDGET`
  entry already carries, and treat the first real run against the seeded corpus as the calibration
  point, exactly as the existing budgets were established. If the measured count exceeds it, record
  the measured number and the reason in the SUMMARY and in `.planning/WINDOWS.md` before adjusting —
  a silently widened ceiling is a budget that has stopped budgeting.
- **[ASSUMED] The corpus's muscle-mapping table is a plausible strength-training taxonomy, not a
  clinical one.** It exists to make the join non-empty and the weighting non-trivial, with at least
  one exercise carrying a secondary mapping at a fractional weight factor so D-04's weighting is
  genuinely exercised. It is not the shipped catalog and does not need to agree with it.

## Grep-gate hygiene

Every **negative** grep in this plan's acceptance criteria (a count that must be 0) is evaluated over
**comment-stripped** source. Strip first, then count — for TypeScript and TSX use
`grep -vE "^\s*(//|\*|/\*)" <file> | grep -c "<token>"`, and for YAML use
`grep -v "^\s*#" <file> | grep -c "<token>"`.

This matters because several tasks below deliberately ask for a comment that names the very thing a
gate forbids in code. An unstripped count would make the explanation self-invalidating, and the only
way to satisfy it would be to delete the explanation — exactly backwards. Positive greps (a count
that must be at least N) are evaluated over the raw file.
