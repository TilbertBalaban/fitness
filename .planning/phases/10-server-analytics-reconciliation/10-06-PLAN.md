<objective>
**As a** lifter looking at a muscle that has taken far more work than I expected, **I want to** see
which exercises actually put it there, **so that** I can decide what to change rather than guess.

This plan is ANLY-05 end to end on the client: a bounded, local, single-muscle read presented in the
sheet idiom this app already uses for exactly this shape of interaction. It is deliberately its own
plan rather than part of 10-05: the drill-down is a distinct requirement, a distinct surface with its
own seven UI states, and it attaches to a press target 10-05 already shipped complete with its
accessible name.

Deliberately NOT in this plan: any change to `MuscleVolumeRow` or `MuscleHeatmap` (10-05 owns both),
any change to the read layer (10-03 owns it), and the Playwright evidence (10-07).

Purpose: answer "which exercises put the work there" without leaving the map.

## Grep-gate hygiene

Every **negative** grep in this plan's acceptance criteria (a count that must be 0) is evaluated over
**comment-stripped** source. Strip first, then count — for TypeScript and TSX use
`grep -vE "^\s*(//|\*|/\*)" <file> | grep -c "<token>"`, and for YAML use
`grep -v "^\s*#" <file> | grep -c "<token>"`.

This matters because several tasks below deliberately ask for a comment that names the very thing a
gate forbids in code. An unstripped count would make the explanation self-invalidating, and the only
way to satisfy it would be to delete the explanation — exactly backwards. Positive greps (a count
that must be at least N) are evaluated over the raw file.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a tapped `muscleGroupId` -> `loadMuscleDrilldown`'s WHERE clause | A value crosses from a rendered row into a query parameter. |
| `loadMuscleDrilldown` output -> the sheet's rows | Numbers become a set count and a volume a lifter reads as their own training; a disagreement with the map above would be visible and would undermine both. |
| a tapped exercise id -> a route push | A value crosses from a rendered row into navigation. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-10-31 | Input Validation | `muscleGroupId` reaching the drill-down query | medium | mitigate | Typed as `MuscleGroupId`, sourced only from the points array the pure package emits, and passed to Drizzle as a bound parameter — never concatenated into SQL (ASVS V5). |
