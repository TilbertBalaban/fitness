## Flagged planner assumptions

- **[ASSUMED] The overlay predicate is `local_date > computed_through_date` OR `user_id IS NULL`.**
  D-01 specifies the date half literally. The `user_id IS NULL` half is an addition, not a
  contradiction: `workout_session.user_id` is stamped server-side on push only (documented in
  `history-query.ts` and `weekly-progress-query.ts`), so a null owner locally means "the server has
  never seen this session". Without it, a session **backfilled offline with a past date** — LOG-21's
  whole flow — would sit below the watermark, be absent from the rollup, and be silently missing from
  the map. With it, the same session is overlaid exactly once. The two clauses cannot double-count,
  because a session the server has rolled up necessarily has a non-null `user_id` and a date at or
  below the watermark.
- **[ASSUMED] Known residual: an offline EDIT of an already-synced session dated on or before the
  watermark shows its pre-edit contribution until the edit reaches the server.** That session has a
  non-null `user_id` and a date below the watermark, so neither clause overlays it; the rollup holds
  the last server-known totals. This is disclosed rather than hidden, it self-corrects on the next
  sync, and it never fabricates a number — it shows an older true number. The named follow-up, if
  this ever matters, is to derive the overlay set from PowerSync's pending crud queue instead of from
  a date comparison. **Record this as a `.planning/WINDOWS.md` entry via the `gsd-tools windows` CLI
  when the plan lands.**
- **[ASSUMED] Untrained is `setCount === 0`, not `weightedVolumeKg === 0`** — a refinement of the
  UI-SPEC's `trainingVolumeKg: number | null` contract, which did not consider a muscle trained only
  by bodyweight or time-based work. Under the UI-SPEC's rule such a muscle would render identical to
  one never trained at all, which is precisely the confusion D-10 exists to prevent. The refinement
  keeps `null` meaning untrained and lets a real zero be a real zero.

## Grep-gate hygiene

Every **negative** grep in this plan's acceptance criteria (a count that must be 0) is evaluated over
**comment-stripped** source. Strip first, then count — for TypeScript and TSX use
`grep -vE "^\s*(//|\*|/\*)" <file> | grep -c "<token>"`, and for YAML use
`grep -v "^\s*#" <file> | grep -c "<token>"`.

This matters because several tasks below deliberately ask for a comment that names the very thing a
gate forbids in code. An unstripped count would make the explanation self-invalidating, and the only
way to satisfy it would be to delete the explanation — exactly backwards. Positive greps (a count
that must be at least N) are evaluated over the raw file.
