<objective>
**As a** lifter deciding what to train next, **I want to** see at a glance where my work has actually
been going across the last week, month or quarter, **so that** I can tell which muscles I have been
quietly neglecting.

This plan ships ANLY-04's user-facing half: two schematic body figures, a window switch, and a
nineteen-row breakdown, all fed by the reads 10-03 landed. It performs no aggregation of its own —
the screen is a renderer, exactly as `exercise-performance.tsx` and `TrendChart` established in
Phase 9.

plan is entirely `apps/mobile`.

Deliberately NOT in this plan: the drill-down sheet and its wiring (10-06, whose whole subject is
ANLY-05), and the Playwright evidence (10-07). The rows this plan ships are already pressable and
already carry their accessible names; 10-06 attaches a destination to that press without changing the
row's shape. That is a functionality gap, never an architectural one.

Purpose: turn the phase's numbers into the one surface a lifter actually reads.
Output: a working, tested `/muscle-map` route reachable from the History tab.
</objective>

## Flagged planner assumptions

- **[ASSUMED] The row value line has three branches, not two.** The UI-SPEC pins `{volumeLabel}` when
  trained and `Untrained` when not. A muscle trained only by bodyweight or time-based work is trained
  with a genuinely zero kilogram figure, which the UI-SPEC did not consider and which
  `"0 kg"` copy is explicitly forbidden from expressing. The third branch renders the set count
  instead — `"{n} sets"` — for a muscle whose set count is above zero and whose volume is zero. It
  fabricates nothing, invents no adjective, and keeps `Untrained` meaning exactly one thing.
- **[ASSUMED] Figure geometry is a schematic zone diagram**, per the UI-SPEC's own design decision 1:
  one `<Rect>` or `<Circle>` per muscle group on a torso/limb grid, the same primitive-shapes
  discipline `TrendChart` already established. No anatomical illustration, no asset pipeline.

## Grep-gate hygiene

Every **negative** grep in this plan's acceptance criteria (a count that must be 0) is evaluated over
**comment-stripped** source. Strip first, then count — for TypeScript and TSX use
`grep -vE "^\s*(//|\*|/\*)" <file> | grep -c "<token>"`, and for YAML use
`grep -v "^\s*#" <file> | grep -c "<token>"`.

This matters because several tasks below deliberately ask for a comment that names the very thing a
gate forbids in code. An unstripped count would make the explanation self-invalidating, and the only
way to satisfy it would be to delete the explanation — exactly backwards. Positive greps (a count
that must be at least N) are evaluated over the raw file.
