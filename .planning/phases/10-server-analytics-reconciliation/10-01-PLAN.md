<objective>
**As a** lifter with years of logged history, **I want to** have the expensive per-muscle volume
maths computed once on the server and shipped to my devices, **so that** a long-horizon body map
opens instantly instead of re-adding up thousands of sets every time I look at it.

This plan is the phase's **tracer**: one completed workout, pushed through the shipped sync ingress,
producing real materialized rollup rows in Postgres, delivered down the existing PowerSync stream
into a real client table. It is production-quality, not a prototype — every table, module and hook
it lands is what the finished phase ships.

It is deliberately first because this is the only place in the phase where the architecture could be
wrong. `apps/api` has never had a business-logic module; it has never imported a `@fitness/*` rules
package at runtime; `SyncService` has never had a collaborator; and no table in this project has ever
been server-written-only. If the recompute cannot live inside `applyBatch`'s existing aggregate
transaction, or if a server-only-written table cannot ride the `user_data` stream, every later plan
in this phase changes shape — and this plan must be the one that finds out.

Deliberately NOT in this plan, each being a later plan's whole subject rather than a gap here:
the PR replay and the vacated-cell invalidation on edit (10-02), the client read layer and the D-01
overlay (10-03), the query-count budgets and the corpus muscle mappings (10-04), and every pixel of
UI (10-05, 10-06). `reconcileSession` in this plan handles the *forward* case only — a session's
sets are re-summed onto its current `local_date`. That is a functionality gap 10-02 fills without
changing the call site's shape, never an architectural one.

Purpose: prove the whole server vertical — pure maths, Postgres table, recompute hook, sync stream,
client mirror — before any of it is built out.
Output: a materialized muscle-volume rollup that a real push writes and a real client can hold.

## Worktree bootstrap (run before anything else)

This plan runs in a fresh worktree. Run `corepack enable`, then `pnpm install`, then
`npx turbo run build --filter="./packages/*"`. Without the build step every `@fitness/*` import
fails resolution and reads as a code error that is not one. This plan makes that failure mode worse
than usual: it is the first time `apps/api`'s **production** code imports a workspace rules package,
so an unbuilt `packages/pr-rules/dist` or `packages/analytics-engine/dist` breaks `nest build`, not
just a Jest run.

`apps/api`'s e2e suites need a live Postgres reachable at `DATABASE_URL` (`.env` at the repo root or
in `apps/api`). `pnpm --filter @fitness/api test:e2e` runs `db:push && nest build && jest` — the
push is part of the command, which is why Task 2 asserts the pushed result rather than repeating it.

## Grep-gate hygiene

Every **negative** grep in this plan's acceptance criteria (a count that must be 0) is evaluated over
**comment-stripped** source. Strip first, then count — for TypeScript and TSX use
`grep -vE "^\s*(//|\*|/\*)" <file> | grep -c "<token>"`, and for YAML use
`grep -v "^\s*#" <file> | grep -c "<token>"`.

This matters because several tasks below deliberately ask for a comment that names the very thing a
gate forbids in code. An unstripped count would make the explanation self-invalidating, and the only
way to satisfy it would be to delete the explanation — exactly backwards. Positive greps (a count
that must be at least N) are evaluated over the raw file.

1. **`packages/analytics-engine/src/muscle-volume.ts`** — a pure module in the exact style of
`weekly-progress.ts`: no database import, no clock read, only `countsTowardWorkingVolume` and
`SetType` imported from `@fitness/api-contracts`, plus `MUSCLE_GROUPS` for the deterministic sort.
Export `MuscleVolumeSetInput` with fields `setType: SetType`, `completed: boolean`,
`weightKg: number | null`, `reps: number`; `MuscleVolumeMappingInput` with `muscleGroupId: string`
and `weightFactor: number`; `MuscleVolumeExerciseInput` with `exerciseId: string`,
`muscleMappings: MuscleVolumeMappingInput[]`, `sets: MuscleVolumeSetInput[]`;
`MuscleVolumeSessionInput` with `sessionId: string`, `localDate: string`, `exercises`; and
`MuscleVolumeCell` with `muscleGroupId: string`, `localDate: string`, `weightedVolumeKg: number`,
`weightedSets: number`, `setCount: number`. Export
`muscleVolumeCells(sessions: MuscleVolumeSessionInput[]): MuscleVolumeCell[]`.
Rules the function applies, and nothing else: a set qualifies when `completed` is true AND
`countsTowardWorkingVolume(setType)` is true; a qualifying set contributes
`(weightKg ?? 0) * reps * weightFactor` to `weightedVolumeKg`, `weightFactor` to `weightedSets`, and
1 to `setCount`, once per mapping the exercise carries — secondary mappings included, which is the
whole of D-04. Both the mapping list and the caller are responsible for resolving muscle ids; this
module holds no muscle vocabulary of its own beyond `MUSCLE_GROUPS` for ordering, and performs no
lookup. Drop a cell entirely when its `setCount` is 0 rather than returning it as a zero (D-10 in the
data layer, not just the UI). Sort the result by `localDate` ascending then by index in
`MUSCLE_GROUPS`; a muscle id outside `MUSCLE_GROUPS` sorts last, by id, rather than throwing.
Append `export * from './muscle-volume';` as ONE new line at the END of
`packages/analytics-engine/src/index.ts`.

3. **`apps/api/src/analytics/muscle-volume.ts`** — the bounded Drizzle read. Export
`loadSessionsForDates(tx, userId, localDates: string[]): Promise<MuscleVolumeSessionInput[]>`
issuing exactly four selects regardless of row counts, in this order: completed `workout_session`
rows where `user_id` equals `userId` and `local_date` is `inArray(localDates)`; `session_exercise`
rows `inArray(session_id, sessionIds)` with `removed_at` null; `logged_set` rows
`inArray(session_exercise_id, sessionExerciseIds)`; `exercise_muscle_mapping` rows
`inArray(exercise_id, exerciseIds)` selecting `exercise_id`, `muscle_group_id` and `weight_factor`.
Never issue a query per session, per exercise or per set. Parse `weight_kg` and `weight_factor` from
their Drizzle string form with `Number(...)` at this one boundary and drop non-finite values rather
than coercing them. Also export
`writeRollupCells(tx, userId, localDates: string[], cells: MuscleVolumeCell[])`, which first DELETEs

supplied cells in ONE batched insert with `serverSeq: sql\`nextval('sync_seq')\`` — delete-then-insert
over the affected dates is what makes a vacated cell disappear instead of lingering, and it keeps the
statement count invariant in the number of cells. Skip the insert entirely when `cells` is empty.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client push payload -> `SyncService.applyBatch` | Untrusted input crosses here. `userId` is resolved from the authenticated session, never from the payload; the payload's own `user_id` fields are never trusted. |
| `applyBatch`'s ownership verdict -> `reconcileSession` | A trusted verdict crosses an internal boundary. Re-deriving it inside reconciliation would create a second, weaker answer to the same question. |
| Postgres rows -> `muscleVolumeCells` | `weight_kg` and `weight_factor` arrive as Drizzle decimal strings. A non-finite parse produces a NaN that propagates silently into a stored aggregate. |
| `muscle_volume_rollup` rows -> PowerSync `user_data` stream -> every device | Derived per-user data leaves the server. The only filter is the stream query's `auth.user_id()`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-10-01 | Elevation of Privilege | `reconcileSession` invoked for an aggregate root the caller does not own | critical | mitigate | The call sits strictly after `applyBatch`'s existing `owner !== userId` rejection branch and inside the same transaction; `userId` is the server-resolved session id, never a payload field. Reconciliation performs no ownership lookup of its own — grep-gated in Task 1's acceptance criteria. |
| T-10-02 | Information Disclosure | cross-user rollup read via the sync stream | high | mitigate | Both new stream queries are `WHERE user_id = auth.user_id()`, resolved from the sync token minted as `mintSyncToken(session.user.id)`. | T-10-03 | Tampering | `weight_kg` / `weight_factor` numeric parse boundary | high | mitigate | Both are parsed once, at `loadSessionsForDates`, with non-finite values dropped rather than coerced; a set with a null weight contributes zero volume but a real set count, so a bodyweight muscle is never mislabelled untrained. |
| T-10-04 | Tampering | rollup rows surviving a rolled-back push | high | mitigate | `reconcileSession` runs inside the push's own `db.transaction`, with no inner try/catch, so a throw rolls back the rollup write together with the ops it derived from.
