### The 5 `sync` failures — a real regression in the `logged_set` upload path

All five cases in `e2e/sync.spec.ts` fail. This is **not** an environment problem. The
decisive evidence is what did and did not reach Postgres for the accounts each run
created:

| Test account | `workout_session` | `session_exercise` | `logged_set` |
|---|---|---|---|
| Runs from 2026-08-19 | 1 | 1 | **2** ✓ |
| All 6 runs from 2026-08-31 | 1 | 1 | **0** ✗ |

The session and its exercise upload and persist correctly. Only the logged sets never
arrive — and they did arrive on 2026-08-19. The client's crud queue drains to `0` either
way, so the client believes the upload succeeded.

**Root cause: still undetermined.** An earlier revision of this report named the
`isValidOptionalBoolean` check added by `144b3ee` (2026-08-25) as the confirmed cause. That
was **wrong and has been retracted** — see the disproof table below.

What is established:

- `workout_session` and `session_exercise` push and persist normally. Only `logged_set`
  never arrives. Verified repeatedly against fresh accounts.
- The client's crud queue drains to `0`, so the client believes the upload succeeded.
- The ops are **not** being rejected by the op validator. Instrumenting
  `hasInvalidField` to log every op it inspected produced **zero lines** across a full
  run, while a `workout_session` row for that same run appeared in Postgres 24 seconds
  earlier. `hasInvalidField` is therefore not on the code path that applies these ops.

So the logged_set ops are lost somewhere between the client's crud queue and the apply
path — not at field validation. The aggregate-grouping and dependency-ordering logic
(`sync.service.ts` ~1237–1360, which resolves `logged_set` against its parent
`session_exercise`) is the next place to look, but that was not confirmed.

Hypotheses tested and **disproved**:

| Hypothesis | How it was ruled out |
|---|---|
| API not running | It was up on `:4000` the whole time; a second start failed `EADDRINUSE` |
| API/client port mismatch | Started the API on the default `:3000`, verified sign-up `200`, reran with pure defaults — identical failure |
| API and spec read different databases | Same DB: `logged_set` holds 340,403 rows and every e2e account from these runs is present |
| Stale `@fitness/api-contracts` build | `dist/` (Aug 31) is newer than `src/` (Aug 28); `SET_TYPES` matches |
| Op validator rejecting a field (`completed` as SQLite 1/0) | Instrumented `hasInvalidField` to log every inspected op: **zero** ops logged during a full failing run. The validator never runs on this path. A candidate fix accepting 0/1 was written, tested (36 assertions green) and then **reverted**, because it corrected a defect that is not this one |

The 116 `durability` cases pass against a real browser and a real `@powersync/web`
database with no API dependency, so the **offline-write half** of the local-first
guarantee is proven today. The **server round-trip half is broken.**

**Next step:** `/gsd-debug` on the `logged_set` sync-push path. The fastest probe is to
log or hard-fail the drop in the sync service's op validator instead of discarding
silently, then run one case and read which field fails.

## Verdict

**Do not tag v1.0 yet.**

Everything that can be checked from the planning record and the build checks out: 105/105
requirements satisfied with named evidence, 12/12 phases verified, typecheck and 2321 unit
tests green, and 116/116 durability E2E cases passing against a real browser and a real
local database.

The blocker is a **live regression**, not an evidence gap: logged sets no longer survive
the sync push. A workout's session and its exercise reach Postgres; the sets are silently
dropped by the sync service's op validator and the client is told the upload succeeded.
The same test wrote its sets correctly on 2026-08-19.

This breaks the project's stated non-negotiable constraint — "writes must succeed offline
and reconcile on sync" — in the worst possible shape: **silent data loss**. The user logs
a set in the gym, the app shows it locally and reports itself synced, and the set never
reaches the server.

Tagging `v1.0` on this would publish a release whose headline guarantee is broken.

### To close this gap

1. `/gsd-debug` the `logged_set` push path. The validator is ruled out; start by logging
   the raw `batch` as it enters the push controller to establish whether `logged_set` ops
   are even present in the request. That single fact splits the search space in half:
   absent means the loss is client-side (crud queue / connector), present means it is in
   the apply path.
2. If present, walk the aggregate-grouping and parent-resolution logic in
   `sync.service.ts` (~1237–1360), which resolves `logged_set` against its parent
   `session_exercise` and is the only stage that treats these rows differently from the
   session and exercise rows that do persist.
3. Re-run `cd apps/mobile && EXPO_PUBLIC_DURABILITY_HARNESS=1 npx playwright test --project=sync`
   (the API must listen on `:3000` — the browser bundle's default; `webServer.env` does
   not forward `EXPO_PUBLIC_API_URL`, so the port is not overridable from the shell).

Independently worth fixing: an op that fails validation is discarded rather than surfaced,
and the push returns 2xx regardless. Whatever the trigger turns out to be, a total sync
failure of the app's most important table should not be able to look like success.

Then re-run this audit, and only then `/gsd-complete-milestone 1.0`.

## Resolution (2026-09-02)

**Root cause.** The client stores every boolean column as a SQLite integer and PowerSync's crud
queue ships the raw `0`/`1`. The WR-03 validator added on 2026-08-25 (`144b3ee`) required
`typeof value === 'boolean'`, so every op carrying a boolean was rejected `invalid_field`; the
client treats that as terminal and completed the transaction. Every boolean-bearing table was
affected (logged_set, dashboard_widget, user_preference, equipment_profile, routine,
excluded_exercise, exercise), not only logged_set. The API e2e suites never caught it because
they POST real JS booleans over HTTP. The 2026-08-31 instrumentation that "cleared" the
validator ran against an API process that was never restarted after the edit.

**Fix.** Quick task 260902-fei: one shared accept/coerce rule for SQLite booleans on the push
path, a 66-case regression spec, and a server-side warn log for every rejected op.

**Evidence.** `playwright test --project=sync`: 5/5 passed (API on `:3000` with
`AUTH_RATE_LIMIT_MAX=100`, Expo started with `EXPO_PUBLIC_API_URL=http://localhost:3000`).
Two of the five need the rate-limit override because the suite creates five accounts inside
Better Auth's 3-per-10s sign-up window.
