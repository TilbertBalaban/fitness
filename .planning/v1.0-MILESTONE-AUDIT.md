### The 5 `sync` failures — a real regression in the `logged_set` upload path

All five cases in `e2e/sync.spec.ts` fail. This is **not** an environment problem. The
decisive evidence is what did and did not reach Postgres for the accounts each run
created:

| Test account | `workout_session` | `session_exercise` | `logged_set` |
|---|---|---|---|
| Runs from 2026-08-19 | 1 | 1 | **2** ✓ |
| All 6 runs from 2026-08-31 | 1 | 1 | **0** ✗ |

The session and its exercise upload and persist correctly. Only the logged sets never
arrive — and they did arrive on 2026-08-19. The client's crud queue drains to `0` either
way, so the client believes the upload succeeded.

**Root cause — confirmed.** Commit `144b3ee` (2026-08-25, *"fix(05): WR-03 validate
logged_set completed/side/parent_set_id/rest_taken_seconds shape"*) added this to the
`logged_set` branch of the op validator in `apps/api/src/sync/sync.service.ts`:

```js
function isValidOptionalBoolean(value) {
  return value === undefined || typeof value === 'boolean';
}
if (!isValidOptionalBoolean(d.completed)) return true;  // true = invalid = drop the op
```

But `completed` is never a JavaScript boolean on the wire. The client declares it
`integer('completed', { mode: 'boolean' })` (`apps/mobile/lib/db/schema.ts:58`) — an
SQLite INTEGER. Drizzle's `mode: 'boolean'` converts only at Drizzle's own read/write
boundary; PowerSync's `CrudEntry.opData` reads **raw SQLite**, and `connector.ts` forwards
it untouched (`data: entry.opData ?? null`). So the server receives `completed: 1` or
`completed: 0`, `typeof` is `"number"`, and **every logged_set op is rejected**. The column
is `.notNull()` and the insert always sets it, so no set can ever sync.

The op is then discarded rather than retried, the transaction completes, and the crud queue
drains — which is why the client reports success while the data is gone.

**The same bug is live on a second table.** Line ~1133 applies the identical predicate to
`dashboard_widget.enabled`, also an `integer(..., { mode: 'boolean' })` column
(`schema.ts:286`). Postgres currently holds **0 rows** in `dashboard_widget`, consistent
with Phase 12's widgets never having synced either.

Nine other `mode: 'boolean'` columns exist in the client schema; any that acquire a
`isValidOptionalBoolean` check will break the same way.

**Fix:** accept SQLite's integer representation at the sync boundary (`value === 0 ||
value === 1` alongside real booleans), or normalize booleans in `toSyncCrudOp` before
upload. The first is minimal and matches what the wire format actually is.

**Secondary defect, worth fixing regardless of the trigger:** an op that fails validation
is dropped silently. That is what let a total sync failure of the app's most important
table go unnoticed for six days.

Hypotheses tested and **disproved**:

| Hypothesis | How it was ruled out |
|---|---|
| API not running | It was up on `:4000` the whole time; a second start failed `EADDRINUSE` |
| API/client port mismatch | Started the API on the default `:3000`, verified sign-up `200`, reran with pure defaults — identical failure |
| API and spec read different databases | Same DB: `logged_set` holds 340,403 rows and every e2e account from these runs is present |
| Stale `@fitness/api-contracts` build | `dist/` (Aug 31) is newer than `src/` (Aug 28); `SET_TYPES` matches |

The 116 `durability` cases pass against a real browser and a real `@powersync/web`
database with no API dependency, so the **offline-write half** of the local-first
guarantee is proven today. The **server round-trip half is broken.**

**Next step:** `/gsd-debug` on the `logged_set` sync-push path. The fastest probe is to
log or hard-fail the drop in the sync service's op validator instead of discarding
silently, then run one case and read which field fails.

## Verdict

**Do not tag v1.0 yet.**

Everything that can be checked from the planning record and the build checks out: 105/105
requirements satisfied with named evidence, 12/12 phases verified, typecheck and 2321 unit
tests green, and 116/116 durability E2E cases passing against a real browser and a real
local database.

The blocker is a **live regression**, not an evidence gap: logged sets no longer survive
the sync push. A workout's session and its exercise reach Postgres; the sets are silently
dropped by the sync service's op validator and the client is told the upload succeeded.
The same test wrote its sets correctly on 2026-08-19.

This breaks the project's stated non-negotiable constraint — "writes must succeed offline
and reconcile on sync" — in the worst possible shape: **silent data loss**. The user logs
a set in the gym, the app shows it locally and reports itself synced, and the set never
reaches the server.

Tagging `v1.0` on this would publish a release whose headline guarantee is broken.

### To close this gap

1. `/gsd-debug` the `logged_set` sync-push path. Make the op validator in
   `apps/api/src/sync/sync.service.ts` log or hard-fail instead of silently discarding,
   run one sync case, and read which field rejects. Silent-drop-on-invalid is itself the
   reason this went unnoticed for ~12 days and is worth fixing independently of the
   trigger.
2. Suspect Phase 07's additions to `logged_set` (`side`, `parent_set_id`, `set_type`)
   first — that phase landed inside the regression window. Also note the validator checks
   a `notes` field that is not a column on `logged_set`.
3. Re-run `cd apps/mobile && EXPO_PUBLIC_DURABILITY_HARNESS=1 npx playwright test --project=sync`
   (API must be on `:3000` — the browser bundle's default; `webServer.env` does not
   forward `EXPO_PUBLIC_API_URL`, so the port is not overridable from the shell).

Then re-run this audit, and only then `/gsd-complete-milestone 1.0`.
