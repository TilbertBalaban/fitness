### The 5 `sync` failures

All five cases in `e2e/sync.spec.ts` — the entire `sync` project — fail.

**Cause undetermined. This is the milestone's one genuinely open question.**

Investigation actually performed, in order:

1. First run: all 5 failed instantly with `TypeError: fetch failed`. Postgres, the
   PowerSync Service and Mailpit were all up (`/probes/liveness` → `200`), but nothing
   listened on `:3000`.
2. The API in this environment runs on **:4000** (`main.ts` uses `process.env.PORT ?? 3000`;
   `PORT=4000` is set here). A second start attempt failing with `EADDRINUSE :::4000`
   proved an instance had been up the whole time. So the initial reading — "the API was
   never started" — was **wrong**.
3. Re-ran with `EXPO_PUBLIC_API_URL=http://localhost:4000`. Cases still failed, but now
   slowly (36s) and on a real assertion rather than a connection error.
4. Found that `playwright.config.ts`'s `webServer.env` forwards only
   `EXPO_PUBLIC_DURABILITY_HARNESS` and `CI` — never `EXPO_PUBLIC_API_URL` — so the
   browser bundle always targets its default regardless of the shell.
5. Started a second API on `PORT=3000` (verified listening, sign-up returns `200`) and
   re-ran with pure defaults. **Case 1 failed identically (36.4s).** So the port
   hypothesis is disproved too.

The real assertion is the end of the drain: after reconnect the client's crud queue
reaches `0`, but `SELECT count(*) FROM logged_set` stays `"0"` instead of `"2"` — the
queue drains without the rows appearing in the database the spec reads. That is
consistent with an API/spec database-target divergence, but this was not confirmed (the
API's own `.env` was not readable in this session).

The 116 `durability` cases that passed run against a real browser and a real
`@powersync/web` database with no API dependency, so the **offline-write half** of the
local-first guarantee is genuinely proven today. The **server round-trip half is not**.
It was proven when Phase 02 executed (see `02-VERIFICATION.md`, status `passed`); it
could not be reproduced now.

## Verdict

**Do not tag v1.0 yet.**

Everything that can be checked from the planning record and the build checks out: 105/105
requirements satisfied with named evidence, 12/12 phases verified, typecheck and 2321 unit
tests green, and 116/116 durability E2E cases passing against a real browser and a real
local database.

The blocker is narrower and specific: the `sync` E2E project — the suite that proves an
offline write actually reaches Postgres, which is this project's stated non-negotiable
constraint and Phase 02's headline claim — fails 0/5 today, and three runs did not
establish why. Two plausible explanations were tested and disproved (API not running;
API/client port mismatch). The surviving hypothesis is that the API and the spec are
reading different databases, which was not confirmed because the API's `.env` was not
readable in this session.

That is an evidence gap, not a known defect. But archiving the milestone would collapse
ROADMAP.md, delete REQUIREMENTS.md, and cut a `v1.0` tag on the claim that the local-first
round-trip works — a claim that cannot be demonstrated right now. Resolve the sync suite
first, then re-run this audit.

### To close this gap

1. Confirm which database the API writes to versus the `DATABASE_URL` the spec reads
   (`postgresql://postgres:dev@localhost:5432/fitness`). A divergence explains the exact
   symptom: queue drains to `0`, `logged_set` stays empty.
2. Re-run `cd apps/mobile && EXPO_PUBLIC_DURABILITY_HARNESS=1 npx playwright test --project=sync`
   with the API on the port the browser bundle actually targets.
3. Consider adding `EXPO_PUBLIC_API_URL` to `webServer.env` in `playwright.config.ts` so
   the browser bundle's API target is controllable from the environment — its absence is
   what made this take three runs to isolate.

Then: `/gsd-complete-milestone 1.0`.
