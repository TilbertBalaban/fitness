# Quick 260902-i0n — Issue the session cookie cross-site when the API is served over https

## Problem

`apps/api/src/auth/auth.ts` passes no `advanced` block, so Better Auth falls through to its own
hardcoded cookie defaults. In `better-auth@1.6.26`, `createCookieGetter` builds every cookie as:

```
{ secure: !!secureCookiePrefix, sameSite: "lax", path: "/", httpOnly: true,
  ...options.advanced?.defaultCookieAttributes, ...overrideAttributes, ...attributes }
```

`SameSite=Lax` means the browser withholds the cookie on any cross-**site** subresource request.
`fitness-web-boo.pages.dev` and `fitness-umcg.onrender.com` are different registrable domains, so
the deployed web app's `get-session` fetch carries no cookie at all. Better Auth answers it with a
null session, the router keeps the user outside `Stack.Protected`, and the screen never changes —
even though the preceding `sign-in/email` POST returned 200 with a valid `Set-Cookie`. The symptom
looks like a broken sign-in; the sign-in is fine and the second request is the one that fails.

The fix is `advanced.defaultCookieAttributes`, which lands in that spread *after* the `sameSite: "lax"`
default and *before* only `overrideAttributes` (which is `{ maxAge }` for the session token) and the
per-cookie `advanced.cookies[name].attributes` (unset here). Our values therefore win.

## Approach

**The gate is `API_BASE_URL.startsWith('https://')`, not `NODE_ENV`.** Three reasons, in order of
weight:

1. It is the identical condition Better Auth already applies internally — `createCookieGetter`
   derives `secureCookiePrefix` from `baseURLString.startsWith("https://")`. Gating on the same
   signal means `Secure` and `SameSite=None` can never disagree about which environment they are in.
2. `API_BASE_URL` is already read on the very next line of `auth.ts` (`baseURL:`), is documented in
   README's env table, and is set as a workflow literal in CI (`http://127.0.0.1:3000`) — so the
   e2e suite keeps `SameSite=Lax` with no change to any test or workflow.
3. `NODE_ENV` is read nowhere in `apps/api`. Introducing it here would add a second, unestablished
   environment signal that could drift from `baseURL`.

**Why `Partitioned`.** Chrome's CHIPS model double-keys the cookie to the top-level site, so it is
sent only when `fitness-web-boo.pages.dev` is the page the request originates from — narrower than
plain `SameSite=None`, and the shape that survives third-party cookie deprecation. `better-call`'s
`CookieOptions` declares `partitioned?: boolean` and better-auth spreads it through untouched
(verified against the installed 1.6.26, whose runtime output for an https base URL is
`__Secure-better-auth.session_token` with `{ secure: true, sameSite: 'none', path: '/', httpOnly: true, partitioned: true }`).

**Why a separate module.** `auth.ts` imports `../db/drizzle.module`, which throws on a missing
`DATABASE_URL` and opens a `pg.Pool` at import time — so no Jest unit spec can import `auth.ts`. A
three-branch environment gate whose failure mode is "production login silently stays broken" earns a
test, so the gate lives in its own dependency-free module beside `auth.ts`, following the
`src/common/web-origins.ts` precedent for a tiny pure env reader.

**Native is unaffected.** The `expo()` plugin's client captures the `set-cookie` string into
SecureStore and replays it as a `Cookie` header itself; `SameSite` and `Partitioned` are browser
attributes with no meaning in that path.

## Deployment preconditions

Neither is changed by this task, and the fix is inert without both:

- `API_BASE_URL` on Render must be `https://fitness-umcg.onrender.com`. If it is unset or http, the
  gate does not fire and nothing changes.
- `WEB_ORIGINS` on Render must contain `https://fitness-web-boo.pages.dev` — `main.ts` feeds it to
  `enableCors({ credentials: true })` and `auth.ts` to `trustedOrigins`. The reported 200 on sign-in
  implies this is already correct.

## Post-deploy check (manual, not part of this commit)

After the API redeploys, confirm the header directly rather than by clicking:

```
curl -si https://fitness-umcg.onrender.com/v1/auth/sign-in/email \
  -H 'content-type: application/json' -H 'origin: https://fitness-web-boo.pages.dev' \
  -d '{"email":"...","password":"..."}' | grep -i set-cookie
```

Expect `__Secure-better-auth.session_token=...; SameSite=None; Partitioned; Secure; HttpOnly`.

## Threat model

Trust boundary: browser → API, cross-site. No packages are installed, so the package-legitimacy gate
does not apply.

| Threat ID | Category | Component | Severity | Disposition | Mitigation |
|-----------|----------|-----------|----------|-------------|------------|
| T-I0N-01 | Spoofing (CSRF) | Session cookie on state-changing auth routes | medium | mitigate | `SameSite=None` removes the browser's ambient CSRF defence, so the defence must be the one already configured: Better Auth's origin check against `trustedOrigins` (app scheme + `WEB_ORIGINS` + `WEB_APP_ORIGIN`), which rejects a state-changing request from an untrusted origin. `disableOriginCheck` is not set and must stay unset. `Partitioned` narrows the exposure further: a third site embedding the API is a different partition and gets no cookie sent at all. |
| T-I0N-02 | Information disclosure | Session cookie over plaintext | low | mitigate | The attributes are emitted only when `API_BASE_URL` is https, and always carry `Secure`, so the cookie can never be issued for a plaintext transport. A misconfigured http production URL degrades to today's behaviour rather than to a cookie sent in the clear. |
| T-I0N-03 | Elevation of privilege | Cross-origin response reads | low | accept | `main.ts` already pins `enableCors({ origin: resolveWebOrigins(), credentials: true })`, so a foreign origin cannot read an authenticated response body. Unchanged by this task. |

## Tasks

### Task 1 — Gate the cross-site cookie attributes on an https API base URL

**Files:** `apps/api/src/auth/cookie-attributes.ts` (new), `apps/api/src/auth/auth.ts`,
`apps/api/src/auth/__tests__/cookie-attributes.spec.ts` (new)

**`cookie-attributes.ts`.** No imports from `../db`, `../mailer` or anything else in the app — the
module must stay loadable with an empty environment. Export one function:

```
resolveDefaultCookieAttributes(apiBaseUrl?: string | undefined)
```

It defaults its argument to `process.env.API_BASE_URL` so the production call site passes nothing and
the spec passes an explicit string. It returns a frozen module-level `as const` object when
`apiBaseUrl` starts with `https://`, and `undefined` otherwise. The `as const` is load-bearing: a
widened `string` for `sameSite` will not satisfy better-call's
`"Strict" | "Lax" | "None" | "strict" | "lax" | "none"` union and `typecheck` will fail. The three
attributes are `sameSite: 'none'`, `secure: true`, `partitioned: true`.

Carry one comment above the constant, and only this one — it is the trap a reader cannot infer from
the code. State that the deployed web build and the API are different registrable domains, that the
`Lax` default therefore withholds the cookie on the app's `get-session` call, and that the gate is
the https base URL because a `Secure` cookie is rejected by browsers over plaintext localhost. Do not
add a comment restating what `startsWith` does, and do not add a JSDoc header to the function.

**`auth.ts`.** Import the helper and pass its result through the new `advanced` block:

```
advanced: { defaultCookieAttributes: resolveDefaultCookieAttributes() },
```

Place `advanced` immediately after `trustedOrigins` and before `session`. Passing `undefined`
explicitly is correct — the option is declared `CookieOptions | undefined` and better-auth spreads
it, so `...undefined` is a no-op. If `typecheck` rejects the explicit `undefined`, fall back to the
conditional-spread form the `rateLimit` block in this same file already uses, rather than adding a
non-null assertion. Add no comment in `auth.ts`; the explanation lives in the helper.

Change nothing else in `auth.ts` — not `baseURL`, not `trustedOrigins`, not `session`, not
`rateLimit`.

**Behavior (what the spec asserts):**

- `resolveDefaultCookieAttributes('https://fitness-umcg.onrender.com')` returns
  `{ sameSite: 'none', secure: true, partitioned: true }`.
- `resolveDefaultCookieAttributes('http://127.0.0.1:3000')` returns `undefined`.
- `resolveDefaultCookieAttributes('http://localhost:8081')` returns `undefined`.
- `resolveDefaultCookieAttributes(undefined)` returns `undefined`.
- Feeding the https result into better-auth's own `createCookieGetter` from `better-auth/cookies`
  with `baseURL: 'https://fitness-umcg.onrender.com'` yields a `session_token` whose attributes are
  `sameSite: 'none'`, `secure: true`, `partitioned: true`, `httpOnly: true`, and whose name carries
  the `__Secure-` prefix.
- The same call with `baseURL: 'http://127.0.0.1:3000'` and the http-gated result yields
  `sameSite: 'lax'` and no `partitioned`.

**Spec placement and the one permitted fallback.** The file goes at
`apps/api/src/auth/__tests__/cookie-attributes.spec.ts`, matching the `src/**/__tests__/*.spec.ts`
layout `src/sync/__tests__` established; `jest.config.js` roots at `src` and matches `\.spec\.ts$`,
so it is picked up with no config change. It must import only `../cookie-attributes` and
`better-auth/cookies` — never `../auth`, which would pull in the pg pool.

`better-auth/cookies` resolves to an ESM-only subpath (`dist/cookies/index.mjs`). A plain CommonJS
`require` of it succeeds on this machine's Node 24, so ts-jest's `module: commonjs` output is
expected to load it. If Jest nonetheless refuses the ESM subpath, delete the two
`createCookieGetter` cases, keep the four pure-function cases, and record the dropped coverage in the
SUMMARY. Do not switch the suite to ESM, do not add a transform, and do not add a moduleNameMapper —
none of that is in scope for this task.
